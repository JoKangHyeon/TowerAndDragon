# 특수형 몬스터 시스템 계획

작성일: 2026-07-21 · 대상: 특수형 몬스터(보호·치유·자폭·감전·속성·지배 등) 구현 계획
상세 기획은 `Docs/기획종합_v2.md`(13. 적)를 우선하며, 현재 구현 현황은 `Docs/적시스템_현황.md`를 참고합니다. 이 문서는 **아직 구현 전인 특수형 시스템의 설계 방향과 진행 계획**만 정리합니다.

## 1. 목적

기존 적 시스템은 "경로(지상/공중) × 행동(일반/공격)"의 조합으로 기본 4종을 데이터만으로 만들 수 있게 되어 있습니다. 여기에 보호·치유·자폭·감전·속성·지배 같은 **특수 행동**을 얹어, 코드 수정 없이 애셋 조합만으로 다양한 적을 구성하는 것이 목표입니다.

핵심은 기존과 동일한 원칙, **상속이 아닌 조합**입니다. 특수형마다 새 클래스를 상속받는 대신, `MonsterData`에 특수 행동 애셋 목록을 담고 런타임에 조립합니다.

## 2. 현재 몬스터 분류 (기준선)

특수형을 얹기 전, 현재 몬스터는 다음 2축으로 분류합니다.

| 축 | 결정 주체 | 값 |
|---|---|---|
| 경로 | 프리팹 (이동 컴포넌트) | 지상(`GroundSplineMovement`) / 공중(`AirDirectMovement`) |
| 행동 | `MonsterData.EnRouteTargetTypes` | 일반(`None`, 성 도착 시만 공격) / 공격(`Tower`, 경로 위 타워 + 성 공격) |

- 근접/원거리는 "공격형"의 하위 변형으로, `MonsterData`의 `ProjectilePrefab` 유무로 갈립니다. 별도 대분류가 아닙니다.
- 탱커형·신속형 같은 변형은 별도 시스템이 아니라 `MaxHealth`·`MoveSpeed` 수치 차이로 표현합니다.

> 주의: 현재 공격형 에셋(`MD_Ground_Attack`, `MD_Ground_Ranged`)의 `EnRouteTargetTypes`가 `Everything(-1)`으로 저장되어 있습니다. 나중에 `Dragon` 같은 플래그를 enum에 추가하면 이 에셋들이 자동으로 새 대상까지 공격하게 되므로, 의도한 값(`Tower`)으로 명시하는 정리가 필요합니다.

## 3. 설계 원칙 — SO는 "공유 데이터", 실행 상태는 분리

기존 `AttackSO`/`AttackEffectSO`는 여러 유닛이 공유하는 **무상태(stateless) 애셋**입니다. 반면 특수형 대부분(치유 오라, 자폭 도화선 카운트다운 등)은 **몬스터마다 다른 런타임 상태**를 가집니다. 따라서 `AttackEffectSO`처럼 "SO가 직접 실행"하는 구조를 그대로 쓸 수 없습니다.

해결책은 **SO를 팩토리로 두는 것**입니다.

```
SpecialBehaviorSO (abstract, 공유 데이터)
   └─ CreateInstance() → ISpecialBehavior (몬스터별 런타임 상태)
```

- `SpecialBehaviorSO` : 설정값만 담고 여러 몬스터가 공유 (예: 치유 반경, 틱당 치유량)
- `ISpecialBehavior` : 몬스터 한 마리에 붙는 런타임 인스턴스. 쿨다운·타이머 등 상태 보관

## 4. 구조 (뼈대)

프리팹을 전혀 건드리지 않도록, 별도 MonoBehaviour 대신 **`BaseMonster`가 소유하는 순수 C# 실행기**로 구성합니다. `AddComponent`도 쓰지 않습니다. 특수형은 오직 `MonsterData`의 `SpecialBehaviorSO[]` 조합으로만 표현되므로, 미션 요건인 데이터 기반 설계에 부합합니다.

| 요소 | 종류 | 역할 |
|---|---|---|
| `ISpecialBehavior` | 인터페이스 | 런타임 인스턴스 계약 (`Initialize`/`Tick`/`Dispose`) |
| `SpecialBehaviorSO` | 추상 SO | 공유 설정값 + 인스턴스 팩토리(`CreateInstance`) |
| `SpecialBehaviorRunner` | 순수 C# 클래스 | 인스턴스들의 생성·매 프레임 갱신·정리 |
| `MonsterData` (수정) | SO | `SpecialBehaviorSO[]` 슬롯 추가 |
| `BaseMonster` (수정) | MonoBehaviour | 실행기 소유, `Setup`에서 조립, `Update`에서 위임, `OnDestroy`에서 정리 |

연결 흐름은 기존 생명주기에 자연스럽게 얹힙니다: `Setup`에서 `SpecialBehaviorRunner.Build`로 특수 행동을 조립하고, `Update`에서 `Tick`을 위임하며, `OnDestroy`에서 `Dispose`로 정리합니다.

이 뼈대는 **구체 행동이 하나도 없어도 컴파일·동작**합니다. `SpecialBehaviorSO[]`가 비어 있으면 아무 일도 하지 않으며, 이후 `HealAuraBehaviorSO : SpecialBehaviorSO` 같은 구현체 하나만 추가하면 바로 연결됩니다.

> 참고: `BaseMonster`에 `Update`가 신설됩니다. 특수 행동이 없는 몬스터도 매 프레임 빈 순회를 돌지만 비용은 사실상 없습니다.

## 5. 특수형 메커니즘 분류

기획의 특수형을 나열식이 아니라 **작동 원리가 같은 것끼리** 묶어야 재사용이 됩니다.

| 버킷 | 해당 타입 | 공통 메커니즘 | 필요한 외부 의존 |
|---|---|---|---|
| A. 오라(지속) | 보호형, 치유형 | 주기적으로 주변 아군 탐색 → 효과 부여 | 치유: `Health.Heal` 추가 / 보호: 방어막 부여 방식 결정 |
| B. 근접 트리거 | 자폭형, 감전형 | 타워 근접 → 정지 → 도화선 → 폭발(범위 피해) | 감전: 타워 일시 비활성화 API |
| C. 데미지 파이프라인 | 속성형, 속성면역형 | 들어오는 데미지의 속성 검사 | 속성 시스템(별도 트랙) |
| D. 제어(복잡) | 지배형 | 타워 하나 점거 → 아군 타워 공격 유도 | 타워 제어 API `[미정]` |

## 6. 속성(버킷 C)은 특수 행동이 아니다

속성형/속성면역형은 매 프레임 실행되는 "행동"이 아니라, `TakeDamage`가 피해를 받을 때 검사하는 **규칙**입니다. `적시스템_현황.md`에도 속성은 "추후 `DamageInfo` 확장으로 붙일 예정"이라고 명시돼 있습니다. 따라서 `SpecialBehaviorSO`에 억지로 끼워넣지 않고 다음과 같이 데미지 파이프라인 확장으로 별도 진행합니다.

- `DamageInfo`에 속성(`Element`) 필드 추가
- `MonsterData`에 취약/면역 속성 지정
- `BaseMonster.TakeDamage`에서 상성 검사

## 7. 자폭형은 기존 AttackSO를 재사용

자폭형의 "폭발 피해"는 결국 범위 공격입니다. 행동 인스턴스는 트리거·도화선·정지만 관리하고, **실제 피해는 `AttackSO`(사거리=폭발 반경, 효과=[`DamageEffect`])에 위임**하면 코드 중복 없이 기존 효과 시스템을 그대로 씁니다. 감전형은 여기에 "타워 비활성화 효과"만 추가로 얹습니다.

## 8. 진행 순서

1. **뼈대** — `ISpecialBehavior` + `SpecialBehaviorSO` + `SpecialBehaviorRunner`, `MonsterData`에 슬롯 추가, `BaseMonster` 연결. (외부 의존 없음)
2. **치유형** — 가장 단순(외부 의존은 `Health.Heal`뿐). 오라(지속) 패턴의 검증 케이스.
3. **자폭형** — 트리거 + `AttackSO` 위임 패턴 확립.
4. **보호형 / 감전형** — 각각 "방어막 부여 방식", "타워 비활성화 API" 결정 선행.
5. **속성** — 별도 트랙(`DamageInfo` 확장).
6. **지배형** — 마지막, `[미정]` 유지.

## 9. 미정 / 선결 과제 (`[미정]`)

- **방어막 부여 방식(보호형)** — 방어막 없는 대상에게 어떻게 임시 방어막을 부여할지. `MonsterShield`를 전 몬스터에 비활성 상태로 두는 방식 등 검토 필요.
- **타워 일시 비활성화 API(감전형)** — 인구 On/Off(비활성화) 시스템과 연동하는 방식 확정 필요.
- **타워 제어 API(지배형)** — 타워가 아군 타워를 공격하도록 유도하는 인터페이스 미정.
- **지속(상태) 효과 시스템** — `IStatusReceiver` 등 상태 지속/틱/해제 시스템은 여전히 미도입(`적시스템_현황.md` 참고).
- **속성 시스템 전반** — 속성 종류·상성표 미확정.
