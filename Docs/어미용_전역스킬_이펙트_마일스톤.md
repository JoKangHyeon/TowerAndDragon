# 어미용 스킬 이펙트 마일스톤 (2026-09-01 ~)

작성일: 2026-09-01
설계 원본: [어미용 스킬 이펙트 설계](./어미용_전역스킬_이펙트_설계.md) — **수치·자산 경로·표는 전부 그쪽이 기준이다.**
이 문서는 **순서·작업 항목·완료 조건·진행 상태**만 담는다. 설계 문서의 표를 복제하지 않는다.

---

## 이 문서를 처음 여는 에이전트에게

1. 브랜치는 `feature/motherDragon-effect`. 이 작업은 **문서 2개만 있고 코드·자산은 아직 0**인 상태에서 시작했다.
2. **「진행 현황」 표를 믿지 말고 아래 「현재 상태 확인 명령」을 먼저 돌린다.**
   표는 사람이 손으로 갱신하므로 밀릴 수 있고, 명령은 저장소의 실제 상태를 본다.
3. 한 번에 마일스톤 **하나만** 완료 처리한다. 끝나면 「진행 현황」 표와 해당 M 절의 「작업 로그」를 갱신한다.
4. **작업 전에 「뒤집힌 결정」 절을 반드시 읽는다.** 옛 판의 문장("성 앵커", "타워수리", "4종")을 보고
   되돌리지 말 것. 근거는 설계 문서 §0의 정정 표다.
5. 씬·프리팹 작업과 플레이 테스트는 **먼저 사용자에게 직접 할지 물어본다.**
6. 이 작업의 전체 그림은 딱 두 계층이다 — **스킬 발동 시 뜨는 화면 배경 이펙트(A)** 와
   **각 스킬의 대상에 뜨는 이펙트(B)**. 그 이상을 늘리지 않는다.

## 작업 원칙

- `.asset` / `.prefab` / `.unity`를 텍스트 편집기로 직접 고치지 않는다. Unity가 열려 있으면 재직렬화로
  덮어쓰고, GUID 사고 이력도 있다. 에디터 스크립트 또는 Coplay MCP로만 배선한다.
- Coplay의 **생성형 기능은 사용 금지**(3D·텍스처·이미지·음악·SFX·TTS 생성, 오토 리깅, 애니메이션
  라이브러리 검색). 자산이 필요하면 기존 팩 조합 또는 팀 요청.
- **`Assets/Imported`는 수정 금지 원본**이다. 팩 프리팹을 직접 고치지 말고 **파생본**을 만든다.
  완성 프리팹은 `Assets/Imported`(별도 저장소)에 커밋한다.
- 비동기는 **UniTask**. `StartCoroutine`/`IEnumerator` 금지, `async void` 금지,
  fire-and-forget은 `.Forget()`, 취소 토큰은 `this.GetCancellationTokenOnDestroy()`.
- 이벤트 구독은 `OnEnable`/`Awake`, 첫 발화는 `Start` 이후.
- 코드 본문에 문자열·리터럴 상수를 넣지 않는다(`_LOC_KEY`, `Defines`, 상수는 UPPER_SNAKE_CASE).
- **이펙트는 자식 이름으로 판단하지 말고 렌더해서 확인한다.** 이름과 실제 그림이 어긋난 전례가 있다.
- **커밋은 사용자가 직접 한다.** 각 M의 커밋 메시지만 이 문서에 적어 둔다.
- 검증은 Test Runner가 아니라 `OnValidate` + 플레이 확인으로 한다.
- 이펙트 생성기 스크립트(`CoplayScripts/`)는 작업이 끝나면 삭제 예정인 **임시 도구**다. 결과물은 프리팹이다.

### 왜 이 순서인가

- **M1이 맨 앞** — 신규 자산 0개로 **오늘 당장 가능**하고, 그 결과 숫자가 M5·M7의 경량화 목표치를 정한다.
- **M2가 M3보다 먼저** — 설계 §3-2의 변환 3개(무한 루프 → 페이드, 파티클 1000×3 경량화, 정렬 미설정)가
  이 작업 **최대의 미지수**다. 파일럿에서 깨지면 A계층 형태 자체를 다시 정해야 하므로,
  배선을 다듬기 전에 먼저 깨 본다.
- **M4가 M5보다 먼저** — B 대상이 성 **1개**라 5종 중 가장 싸고, A와 B가 화면상 같은 위치에 겹치는
  유일한 케이스라 두 계층이 서로를 가리지 않는지 최소 비용으로 확인된다.
- **M4~M7은 서로 독립**이다. M3만 끝나 있으면 순서를 바꿔도 된다.

## M1 — 빙결 N-동시발동 실측

**신규 자산 0개. 코드 0줄. 오늘 당장 가능하다.** 설계 §4의 `[미정]`을 숫자로 바꾸는 것이 목적이다.

선행: 없음.

작업:

- 밤 웨이브에서 몬스터가 **20마리 이상**일 때 전역 빙결을 눌러 관찰한다
- 관측 항목
  - 화면에 동시에 뜬 `FX_Status_IceFreeze` 개수
  - 겹쳐서 개별 몬스터 판독이 되는지 (개체를 구분할 수 없으면 그게 상한이다)
  - 프레임 하락 정도
  - `Projectile` 레이어에 뎁스 정렬이 없어 앞뒤가 뒤섞이는 정도 (설계 §4)
- 가능하면 녹화해서 다시 본다. 플레이 중 판정은 부정확하다

⚠️ **한 프레임 스냅샷이 아니라 누적 중첩을 본다.** 빙결 B는 3/4/5초 지속이라

⚠️ 이 실측은 **B계층의 상한**을 재는 것이다. A 오버레이는 항상 1개라 여기에 안 걸린다.

완료 판정:

## M2 — A 오버레이 기반 · 빙결 A 파일럿

**이 작업 최대의 미지수를 여기서 깬다.** 나머지 4속성이 같은 틀을 탈 수 있는지 확인하는 게 목적이다.

작업:

- **자산 1개** — Hovl `Snow.prefab`(설계 §3-2 얼음 1순위)에서 오버레이용 파생 프리팹을 만든다.

  1. `looping: 1` → 페이드 인/아웃으로 끝나게 (호스트가 제어)

  3. `m_SortingLayer: 0`(Default) → 화면 최상단 레이어로 재지정
- **코드 1개** — 신규 호스트 컴포넌트. 설계 §3-3의 `TowerBuffOrbCoordinator` 자가등록 패턴

  `:49` `OnEnable` 대입 / `:56` `OnDisable` 해제). 페이드는 UniTask
- **씬** — 오버레이를 카메라 자식으로 배치

### M2에서 결정할 것 2개 (결과를 이 칸에 적는다)

**① 어느 속성 오버레이를 띄울지 아는 방법** — 결정: `_______`

- 권고: 호스트가 `DragonTreeManager` 참조를 갖고 `ActiveAttribute`를 읽는다.
  `SkillHudBinder.cs:104`가 증명하듯 HUD는 `SkillManager.AvailableSkills`(해금 + **활성 속성 일치**)만
  노출하므로, 발동 가능한 액티브는 항상 활성 속성의 것이다
- 대안: `SkillData`에 `DragonType` 필드 추가 — 공용 데이터 클래스 + 에셋 5개를 건드린다

**② 호스트를 씬에 놓을지, 첫 사용 시 자동 생성할지** — 결정: `_______`

- 권고: **씬 배치**(카메라 자식) + `[SerializeField]`로 5속성 프리팹 참조, `OnValidate`로 누락 검사
- `ProjectilePool`에 자동 생성 선례가 있으나(`타워_투사체_연출_마일스톤.md` M2), 오버레이는 프리팹
  5개를 참조해야 해서 직렬화 소스가 필요하다

### ⚠️ 함정

- ⚠️ **`scalingMode: 0`(Hierarchy)** — 카메라 자식으로 붙으면 카메라의 스케일이 파티클에 곱해진다.
  화면을 안 채우거나 거꾸로 폭발하면 여기부터 본다
- ⚠️ **`MinMaxCurve.constant`는 `constantMax`의 별칭이다.** 경량화하면서 `constant`·`constantMin`·
  `constantMax`를 다 곱하면 배수가 **제곱으로** 걸린다 (작업노트 3-10 ★)
- ⚠️ **`UI_CameraInputBlocker`를 붙이지 않는다.** 오버레이는 창이 아니다. 붙이면 밤 전투 중 카메라가 죽는다
- ⚠️ **이 시점의 배선은 임시다.** `SkillUsed`에 무조건 물려 그림만 검증한다.
  **M3을 건너뛰면 아무 일도 안 일어난 시전(고칠 타워 0개, 몬스터 0마리, 성 만피)에도 화면 전체에
  오버레이가 뜬 채로 남는다.** M2를 커밋하더라도 M3 전에는 완성이 아니다
- ⚠️ Hovl 프리팹 원본을 고치지 않는다. `Assets/Imported`는 수정 금지 원본이다 — 파생본을 만든다

- 파티클 총량이 M1에서 정한 목표치 이하

## 뒤집힌 결정 (되돌리지 말 것)

옛 판의 문장을 보고 원복하는 사고를 막기 위한 절이다. 근거는 전부 설계 문서에 있다.

1. **A계층은 성 앵커가 아니라 화면 오버레이다.** 초판 §3("어미용은 성에 앵커")은 폐기됐다 —
   성에 붙은 월드 이펙트는 카메라가 성에서 멀면 화면에 안 보여서, §3 자신이 세운 요구를 만족하지 못했다.
   근거: 설계 §3-1
2. **"타워수리"가 아니라 "즉시 재활성화"다.** 타워는 파괴되지 않고 비활성화된다(CLAUDE.md).
   스트링테이블도 "즉시 재활성화"다. 근거: 설계 §2-3
3. **성벽 재생은 범위 안이다.** "4종"이라고 적힌 옛 문장은 폐기됐다. 기획·스트링테이블·에셋·코드 모두
   확정 상태였다. 근거: 설계 §2-5
4. **`ProjectilePool`에 오버로드를 추가할 필요가 없다.** 정렬·지연이 필요한 계층엔 이미 호스트가 있다
   (A=신규 컴포넌트 / 타워=`Tower` / 방벽=`StoneBarricade`). 추가하려거든 왜 필요한지 먼저 적을 것.
   근거: 설계 §1-1
5. **`Castle.Repair`와 `DS_FireBurn`에 연출을 걸지 않는다.** 둘 다 다른 기능(연구 회복 / 각성 패시브)과
   공유하는 경로라, 걸면 스킬을 안 써도 연출이 뜬다. 근거: 설계 §2-5, §2-2
6. **A계층 자산은 속성별로 개별 제작한다.** 하나의 파라미터화 프리팹을 색만 바꿔 재사용하는 안은
   검토했다가 반려됐다. 근거: 설계 §3-2
