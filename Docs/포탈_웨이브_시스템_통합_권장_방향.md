이 문서는 현재 9-feature-portal-system 브랜치와 master에서 리베이스된
웨이브·적 공격 코드를 기준으로, 중복 구현을 제거하고 장기 확장 가능한
정식 웨이브 시스템으로 통합하기 위한 권장 방향을 정리한다. 다른 AI나
팀원이 이어서 작업할 때는 이 문서를 출발점으로 삼되, 실제 코드와 씬을
다시 확인한 뒤 작업한다.

# 0. 문서 사용 규칙

-   \[확정\]은 현재 기획서 또는 코드에서 확인된 사실이다.

-   \[권장\]은 현재 구조와 확장성을 고려한 설계 제안이다.

-   \[미정\]은 팀 합의 전 임의로 확정하거나 구현하지 않는다.

-   코드 작업 전 Docs/기획종합_v2.md, 현재 브랜치, 관련 씬과
    > ScriptableObject 에셋을 대조한다.

-   한 단계의 컴파일·Inspector·플레이 검증이 끝나기 전 다음 단계 기능을
    > 한꺼번에 추가하지 않는다.

# 1. 결론 요약

\[권장\] 데이터 구조는 현재 포탈 브랜치의 다중 포탈 설계를 기준으로
통일하고, 실제 실행 로직은 master의 WaveSpawner에서 검증된 UniTask
흐름을 이전한다. 적 공격 시스템은 master 구현을 유지하며 웨이브 시스템은
BaseMonster.Setup 호출까지만 책임진다.

-   정식 데이터 타입은 SpawnGroupData, PortalWaveData, WaveDefinitionSO
    > 세 종류로 통일한다.

-   씬에는 WaveDirector 하나를 두고 여러 Portal을 PortalId로 조회한다.

-   Portal은 ID·스폰 위치·지상 경로·메인 성·활성 상태를 제공하는 씬 구성
    > 요소로 유지한다.

-   WaveDirector는 포탈별 편성을 병렬 실행하고, 각 포탈 내부의 그룹은
    > 순차 실행한다.

-   기존 WaveData_Test는 새 구조 검증이 끝날 때까지 보존하고 이후 참조를
    > 이전한 뒤 제거한다.

-   MonsterAttack, MonsterData, 타워 공격 로직은 웨이브 통합 과정에서
    > 수정하지 않는다.

# 2. 현재 코드 기준선

## 2.1 master에서 리베이스된 동작 코드

-   Assets/Scripts/WaveData_Test/SpawnGroup.cs: 적 프리팹, MonsterData,
    > 수량, 간격, 시작 지연을 직렬화한다.

-   Assets/Scripts/WaveData_Test/WaveData.cs: SpawnGroup 배열을 가진
    > 실제 ScriptableObject다.

-   Assets/Scripts/WaveData_Test/WaveSpawner.cs: UniTask로 그룹을 순차
    > 실행하고 Instantiate 후 BaseMonster.Setup을 호출한다.

-   Assets/Data/WaveData/WD_Sample.asset 등 실제 테스트 데이터가
    > 존재한다.

-   Sangwook_EnemyWaveTest와 Sangwook_EnemyAttackTest 씬이 WaveSpawner를
    > 사용한다.

## 2.2 포탈 브랜치에서 추가된 구조

-   Assets/Scripts/Portal/PortalId.cs: None, North, East, South, West를
    > 정의한다.

-   Assets/Scripts/Portal/Portal.cs: 포탈별 스폰 위치, SplineContainer,
    > 메인 성, 활성 상태를 제공한다.

-   Sangwook_PortalScene에 포탈 4개, 스플라인 4개, 메인 성 참조가
    > 연결되어 있다.

-   Assets/Scripts/Wave/ 아래에 SpawnGroupData, PortalWaveData,
    > WaveDefinitionSO 초안이 존재한다.

## 2.3 확인된 중복

-   SpawnGroup과 SpawnGroupData는 프리팹·MonsterData·수량·간격 책임이
    > 거의 완전히 겹친다.

-   WaveData와 WaveDefinitionSO는 최상위 웨이브 에셋 역할이 겹친다.

-   WaveSpawner의 반복 실행은 계획된 WaveDirector의 일부와 겹친다.

-   WaveSpawner의 Instantiate와 Setup 호출은 계획된 MonsterFactory
    > 책임과 겹친다.

-   WaveSpawner가 직접 보관하는 path·spawnPoint·mainCastle은 Portal이
    > 제공하는 참조와 겹친다.

## 2.4 현재 코드의 주의사항

-   기존 SpawnGroup 생성자에서 \_monsterData 대입이 주석 처리되어 있어
    > 생성자로 만든 데이터는 MonsterData가 null이 될 수 있다.

-   기존 WaveSpawner는 Start에서 자동 실행하므로 실제 낮·밤 흐름에 직접
    > 사용하기 어렵다.

-   신규 SpawnGroupData와 PortalWaveData는 현재 MonoBehaviour라 중첩
    > 직렬화 데이터로 부적합하다.

-   신규 WaveDefinitionSO도 현재 MonoBehaviour라 실제 ScriptableObject
    > 에셋으로 사용할 수 없다.

-   PortalWaveData의 \_startDay, PortaId, SpawnGroup 명칭은 의도와
    > 일치하지 않는다.

-   BaseMonster.HandleArrivedAtCastle은 비어 있어 적의 최종 메인 성
    > 공격은 아직 미구현이다.

# 3. 시스템 책임 경계

## 3.1 WaveDefinitionSO

\[권장\] 한 번의 밤에 실행할 포탈별 적 편성 전체만 보관한다. 현재
날짜·주기·난이도 계산은 포함하지 않는다.

## 3.2 PortalWaveData

\[권장\] 특정 PortalId에서 실행할 시작 지연과 SpawnGroupData 목록을
보관한다.

## 3.3 SpawnGroupData

\[권장\] 특정 적 프리팹과 MonsterData를 몇 마리, 어떤 간격으로 생성할지
표현한다. 지연 필드는 DelayBeforeGroup으로 통일하는 것을 권장한다.

## 3.4 Portal

\[권장\] 씬의 공격로 한 개를 표현한다. 포탈 자체는 날짜·주기·웨이브
선택·밤 종료를 판단하지 않는다.

## 3.5 WaveDirector

\[권장\] 웨이브 실행의 단일 오케스트레이터다. WaveDefinitionSO를 받고
PortalId에 맞는 Portal을 찾으며 스폰 작업을 시작·취소한다.

## 3.6 적 공격 시스템

\[확정\] 웨이브 시스템은 적 생성 후 BaseMonster.Setup(data, path,
mainCastle)을 호출한다. 체력, 방어막, 이동 중 타워 탐색과 공격은 기존
BaseMonster·MonsterAttack·MonsterData가 담당한다.

# 4. 목표 데이터 모델

\[권장\] 최종 데이터 계층은 다음과 같이 통일한다.

WaveDefinitionSO

PortalWaveData\[\]

PortalId

StartDelay

SpawnGroupData\[\]

MonsterPrefab

MonsterData

SpawnCount

SpawnInterval

DelayBeforeGroup

## 4.1 지연 시간 의미

-   PortalWaveData.StartDelay: 밤 시작 후 해당 포탈 편성이 처음
    > 실행되기까지의 지연이다.

-   SpawnGroupData.DelayBeforeGroup: 해당 포탈 안에서 그 그룹이 시작되기
    > 전의 지연이다.

-   SpawnInterval: 같은 그룹 안에서 개별 적 사이의 간격이다.

-   DelayAfterGroup은 DelayBeforeGroup과 의미가 겹치므로 동시에 유지하지
    > 않는다.

## 4.2 날짜와 주기 분리

\[권장\] WaveDefinitionSO에는 DayIndex나 CycleIndex를 넣지 않는다. 이후
별도의 WaveSchedule 또는 진행 시스템이 오늘 실행할 WaveDefinitionSO를
선택한다. 주기당 일수가 \[미정\]이므로 현재 데이터 모델에서 공식을
확정하지 않는다.

## 4.3 적 정의 확장

초기에는 MonsterPrefab과 MonsterData를 SpawnGroupData가 직접 참조한다.
잘못된 조합이 반복되거나 적 종류가 늘어나면 두 참조를 묶는
MonsterDefinitionSO 도입을 별도 단계에서 검토한다.

# 5. 목표 런타임 흐름

낮 종료 → 밤 상태 확정 → WaveDefinitionSO 선택 → WaveDirector 실행 →
활성 Portal 조회 → 포탈별 작업 병렬 실행 → 그룹별 적 순차 생성 →
BaseMonster.Setup → 모든 예약 스폰 완료 → 생존 적 전멸 대기 → 웨이브
완료 → 밤 종료

## 5.1 포탈별 병렬·그룹별 순차

-   서로 다른 포탈의 편성은 UniTask.WhenAll 등으로 동시에 실행할 수
    > 있다.

-   한 포탈 내부의 SpawnGroupData는 목록 순서대로 실행한다.

-   비활성 또는 봉인된 포탈은 실행 대상에서 제외한다.

-   웨이브에 지정된 PortalId가 씬에 없으면 조용히 무시하지 않고 검증
    > 오류를 남긴다.

## 5.2 웨이브 상태

\[권장\] Idle → Spawning → WaitingForEnemies → Completed 상태를 기본으로
하고 어느 상태에서든 Cancelled로 전환할 수 있게 한다.

## 5.3 완료 이벤트 구분

-   AllSpawnsCompleted: 예약된 모든 적을 생성한 상태다.

-   WaveCompleted: 모든 예약 스폰이 끝나고 생존 적도 0인 상태다.

-   두 이벤트를 하나로 합치면 마지막 적 생성 즉시 밤이 끝나는 오류가
    > 발생한다.

# 6. 기존 코드 재사용과 정리 기준

## 6.1 유지할 구현

-   WaveSpawner의 UniTask 기반 지연 및 destroyCancellationToken 사용
    > 방식

-   그룹 순차 처리와 개별 적 스폰 간격 처리

-   스폰 위치·회전을 적용한 Instantiate 흐름

-   BaseMonster.Setup 호출 계약

-   master의 MonsterAttack, MonsterData, IMonsterTarget, Tower 공격
    > 시스템

## 6.2 변경할 구현

-   단일 WaveData 대신 다중 포탈 WaveDefinitionSO를 사용한다.

-   기존 SpawnGroup과 신규 SpawnGroupData를 하나의 정식 타입으로
    > 통일한다.

-   실행 중복 방지와 명시적 취소 수단을 추가한다.

## 6.3 검증 후 제거할 항목

# 7. 단계별 마이그레이션 계획

## 단계 0 · 기준선 고정

-   현재 master와 포탈 브랜치의 관련 파일·에셋·씬 참조를 목록화한다.

-   기존 테스트 씬이 정상 진입하는지 확인한다.

-   코드 삭제 없이 정식 타입과 구형 타입의 대응표를 확정한다.

## 단계 1 · 정식 데이터 계약 완성

-   SpawnGroupData를 \[Serializable\] 일반 클래스로 변경한다.

-   PortalWaveData를 \[Serializable\] 일반 클래스로 변경한다.

-   WaveDefinitionSO가 ScriptableObject를 상속하게 한다.

-   \_startDay를 \_startDelay로, PortaId를 PortalId로, SpawnGroup을
    > SpawnGroups로 정리한다.

-   XML summary와 Inspector Tooltip을 추가한다.

-   수량·간격·누락 참조·중복 PortalId 검증을 추가한다.

## 단계 2 · WaveDirector 골격

-   WaveSpawner의 UniTask 코드를 기반으로 명시적 실행 메서드를 만든다.

-   WaveDefinitionSO와 Portal 목록을 주입받는다.

-   PortalId 매핑과 활성 상태 검사를 구현한다.

-   포탈별 실행 취소와 중복 실행 방지를 추가한다.

-   이 단계의 완료 조건은 모든 예약 스폰 완료까지다.

## 단계 3 · 단일 포탈 수직 슬라이스

-   테스트 포탈 하나만 임시 활성화한다.

-   테스트용 WaveDefinitionSO 에셋 한 개를 만든다.

-   기본 지상 적 한 종류를 지정 수량과 간격으로 생성한다.

-   포탈의 SplineContainer와 MainCastle이 BaseMonster.Setup에 전달되는지
    > 확인한다.

-   기존 이동 중 타워 공격이 그대로 동작하는지 확인한다.

## 단계 4 · 복수 포탈

-   포탈별 StartDelay를 검증한다.

-   두 개 이상 포탈의 동시 실행을 검증한다.

-   포탈별 경로가 뒤바뀌지 않는지 확인한다.

-   비활성 포탈 제외와 잘못된 PortalId 오류를 확인한다.

## 단계 5 · 생존 적 추적

-   생성 시 적을 등록하고 사망·제거·풀 반환 시 해제한다.

-   예약 스폰 수와 생존 적 수를 분리해 관리한다.

-   AllSpawnsCompleted와 WaveCompleted 이벤트를 분리한다.

-   WaveCompleted가 한 번만 발생하는지 확인한다.

## 단계 6 · 낮·밤 연결

-   CycleManager의 상태 변경과 이벤트 호출 순서를 정리한다.

-   RunData.currentCycle의 의미를 DayIndex와 CycleIndex 관점에서
    > 확정한다.

-   밤 시작 시 오늘의 WaveDefinitionSO를 선택해 실행한다.

-   웨이브 완료 후에만 밤 종료를 요청한다.

-   패배·씬 종료·밤 취소 시 남은 스폰 작업을 취소한다.

## 단계 7 · 구형 구조 제거

-   기존 두 테스트 씬을 신규 WaveDirector 구조로 전환한다.

-   WD_Sample 데이터를 신규 WaveDefinitionSO 에셋으로 재작성한다.

-   모든 참조가 이전된 것을 검색과 씬 검증으로 확인한다.

-   그 이후 WaveData_Test 폴더와 중복 타입을 제거한다.

# 8. 적 공격 시스템과의 통합 경계

-   웨이브 시스템은 MonsterAttack의 타깃 선정이나 공격 간격을 직접
    > 제어하지 않는다.

-   SpawnGroupData는 MonsterData를 전달하고 BaseMonster가 공격
    > 컴포넌트를 초기화한다.

-   이동 중 타워 공격은 master 구현을 그대로 사용한다.

-   메인 성 도착 후 공격은 BaseMonster.HandleArrivedAtCastle과
    > MonsterAttack의 최종 대상 모드에서 별도로 완성한다.

-   메인 성 공격이 미완성이라고 해서 웨이브 데이터 통합을 멈출 필요는
    > 없다.

-   적 사망 이벤트를 웨이브 추적에 노출할 때 전투 시스템의 내부 책임을
    > 침범하지 않는 계약을 정의한다.

# 9. 장기 확장 설계

## 9.1 포탈 상태

향후 bool IsActive는 Locked, Active, Sealed 상태로 확장할 수 있다.
포탈은 상태를 보관하되 주기 계산이나 승리 판정은 별도 진행 시스템이
담당한다.

## 9.2 보스와 특수 그룹

보스 여부를 WaveDirector 분기로 하드코딩하지 않는다. SpawnGroupData 또는
별도 그룹 정책으로 표현하고 보스 고유 행동은 MonsterData·프리팹 조합이
담당한다.

## 9.3 자동 웨이브 생성

기획 공식 확정 후 현재 주기, 일차, 활성 포탈, 점령 가치, 난이도를
입력받아 WaveDefinitionSO와 동일한 런타임 정의를 생성하는 전략을
추가한다. 실행기는 수동 에셋과 자동 생성 결과를 구분하지 않는다.

## 9.4 오브젝트 풀링

초기에는 Instantiate와 Destroy를 유지한다. 프로파일링에서 병목이
확인되면 적 생성 책임을 MonsterFactory 또는 스폰 서비스로 추출하고 풀
구현으로 교체한다.

## 9.5 저장과 불러오기

프로토타입은 낮 시작 체크포인트 저장을 우선한다. 밤 도중 저장은 포탈별
남은 그룹, 다음 스폰 시간, 생존 적 상태와 이동 진행도를 요구하므로 별도
이슈로 관리한다.

## 9.6 UI와 연출

스폰 예고 UI는 WaveDefinitionSO 또는 읽기 전용 조회 모델을 사용한다.
UI가 WaveDirector의 코루틴이나 씬 오브젝트를 직접 조사하지 않도록 한다.

# 10. 검증 기준

## 10.1 데이터 검증

-   PortalId.None 또는 중복 PortalId를 검출한다.

-   적 프리팹과 MonsterData 누락을 검출한다.

-   SpawnCount가 유효하지 않은 값을 검출한다.

-   음수 StartDelay, DelayBeforeGroup, SpawnInterval을 검출한다.

-   웨이브에 지정된 포탈이 씬에 없으면 명확한 오류를 제공한다.

## 10.2 플레이 검증

-   명시적 실행 전에는 적이 생성되지 않는다.

-   지정 수량과 간격이 일치한다.

-   포탈별 경로가 섞이지 않는다.

-   공중 적은 메인 성을 직접 목표로 삼는다.

-   취소 후 추가 적이 생성되지 않는다.

-   마지막 적 생성만으로 WaveCompleted가 발생하지 않는다.

-   낮·밤 반복 실행에서 이전 웨이브 상태가 남지 않는다.

## 10.3 완료 기준

-   Unity 컴파일 오류 0

-   플레이 모드 진입 가능

-   단일 포탈 수직 슬라이스 통과

-   복수 포탈 동시 실행 통과

-   기존 적 공격 기능 회귀 없음

-   구형 WaveData_Test 참조 제거 확인

-   문서의 진행 상태와 현재 코드 일치

# 11. 마이그레이션 위험과 대응

-   기존 WaveData와 신규 WaveDefinitionSO는 직렬화 계층이 달라
    > FormerlySerializedAs만으로 자동 이전하기 어렵다.

-   현재 샘플 에셋 수가 적다면 복잡한 변환기보다 신규 에셋 재작성이
    > 안전하다.

-   구형 클래스와 에셋을 먼저 삭제하면 테스트 씬의 MonoBehaviour 또는
    > ScriptableObject 참조가 끊어진다.

-   클래스·파일 이름 변경 시 .meta GUID 보존 여부와 씬 직렬화 참조를
    > 확인한다.

-   리베이스 이후 master의 후속 변경을 받을 가능성이 있으므로 큰 삭제는
    > 새 구조 검증 후 별도 커밋으로 분리한다.

-   WaveDefinitionSO와 WaveData를 동시에 정식 데이터로 운용하는 기간을
    > 길게 유지하지 않는다.

# 12. 다른 AI와 이어서 작업하는 규칙

-   첫 답변 전에 현재 브랜치, git status, master\...HEAD 변경 파일을
    > 확인한다.

-   Docs 문서만 믿지 말고 WaveData_Test, Wave, Portal, BaseMonster와
    > 관련 씬을 직접 확인한다.

-   현재 단계에서 변경할 파일 목록과 제외 범위를 먼저 선언한다.

-   기존 테스트 에셋과 씬 참조가 남아 있는지 검색한 뒤 타입을 삭제한다.

-   작업 후 컴파일 결과, 씬 wiring, 테스트 결과와 미검증 항목을 구분해
    > 보고한다.

-   기획서의 \[미정\] 항목을 테스트용 수치와 혼동하지 않는다.

-   적 공격 이슈와 포탈·웨이브 통합 이슈의 책임 경계를 유지한다.

-   문서의 현재 상태 표와 다음 작업 체크리스트를 구현과 함께 갱신한다.
