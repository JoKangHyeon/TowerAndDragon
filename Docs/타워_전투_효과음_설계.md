# 🔊 타워 전투 효과음 설계

작성일: 2026-08-23 · 전체 현황: [구현 현황](./구현현황.md)
· 연출 설계: [타워 투사체 연출 설계](./타워_투사체_연출_설계.md)
· **선행 필독: [타워 이펙트 작업 노트](./타워이펙트_작업노트.md)**

타워가 **발사할 때마다 타워 종류별로 다른 효과음**을, 암석·불·얼음 타워는 **명중 지점의 파열음**을
함께 내기 위한 설계 문서입니다. 기획은 `기획종합_v2.md`가 우선합니다.

> **이 문서는 설계안입니다.** 코드·에셋 작업은 아직 시작하지 않았습니다.
> 클립은 이미 프로젝트에 있습니다 — `Assets/Imported/Gamemaster Audio - Pro Sound Collection/`
> (8,266개). 새로 생성하지 않고 여기서 고릅니다.

---

## 1. 요구사항

| # | 요구 | 대상 |
|---|---|---|
| R1 | 투사체가 발사될 때 **타워 종류마다 다른** 효과음 | 공격 타워 7종 |
| R2 | 명중 임팩트 파티클이 터지는 **그 시점**에 파열음 | 암석 · 불 · 얼음 3종 |
| R3 | 밤 웨이브에서 타워가 여러 개여도 소리가 뭉개지지 않을 것 | 전역 |

**범위 밖**: 새끼용(`BD_*`) · 몬스터 · 용 스킬 · 타워 파괴/부활. 아래 설계는 이들에 소리를
**추가하지 않되**, 나중에 같은 필드를 채우는 것만으로 붙일 수 있게 열어 둡니다.

## 2. 현재 구조

### 2-1. 사운드 (`Assets/Scripts/Sound/`)

```
SoundId (enum, 14종)
   │  ※ SoundCatalog.asset에 int로 직렬화된다 (_id: 0 ~ 13)
   ▼
SoundCatalog.asset  ─ SoundEntry { Clip, Volume, PitchRange, MinInterval }
   ▼
SoundManager (씬 오브젝트, 정적 진입점 SoundManager.Play(SoundId))
   └ AudioSource ×12 (spatialBlend 0 = 2D, AudioMixer "SE" 그룹)
```

이미 갖춰져 있어 이번에 **새로 만들 필요가 없는 것들**:

- `SoundEntry.NextPitch` — 재생마다 피치를 무작위로 뽑는다. 연사 타워의 기계음을 없애는 장치.
- `SoundEntry.MinInterval` — 같은 id의 최소 재생 간격. 같은 종류 타워 여러 개가 겹치는 것을 막는다.
- `SoundManager.TakeSeSource()` — 소스 12개를 돌려 쓰고, 다 차면 가장 오래된 것을 덮어쓴다.
- 클립이 비어 있으면 **경고 없이 조용히 넘어간다** — 애셋 미수급이 정상 상태로 취급된다.

### 2-2. 발사·명중 흐름

```
[TowerAttack.Fire]  ← 여기서 지금 SoundManager.Play(SoundId.TowerFire) 하나만 울린다
   │
   ├─(투사체 없음)→ AttackSO.Execute  즉시 피해
   │
   └─(투사체 있음)→ ProjectilePool.Spawn → Projectile.Launch
                        │
                        ▼ MoveTowards 추적
                     [명중] ─ ApplyHit()            피해
                            ─ _visual?.OnHit(...)   ← 임팩트 파티클이 터지는 지점
                            ─ Release()             풀 반납
```

## 3. 지금 막혀 있는 것

1. **발사음이 전 타워 공통 1종이다.** `TowerAttack.Fire`가 `SoundId.TowerFire`를 하드코딩한다.
2. **명중 시점을 아는 쪽에 소리를 낼 근거가 없다.** 명중은 `Projectile`이 판정하는데,
   `Projectile`은 자기를 쏜 타워가 무엇인지 모른다(`AttackSO`와 `AttackContext`만 받는다).
3. **`SoundId`가 int로 직렬화된다.** `SoundCatalog.asset`이 `_id: 0`~`13`을 그대로 들고 있어
   **enum 중간에 값을 끼워 넣으면 카탈로그 배선이 통째로 밀린다.** → 새 값은 반드시 끝에 추가.
5. **enum의 기본값은 0(`UiButtonClick`)이다.** 새 필드를 `SoundId`로 그냥 두면, 값을 채우지 않은
   `TowerData`·`BabyDragonData` 에셋이 **발사할 때 버튼 클릭음을 낸다.**

## 4. 설계 — 사운드 id를 어디에 두는가

세 후보를 비교했습니다.

| 안 | 위치 | 판정 |
|---|---|---|
| **A** | `TowerData`에 필드 추가 | **채택** |
| B | 투사체 프리팹의 `ProjectileVisual`에 필드 추가 | 기각 |
| C | 새 SO(`TowerSfxSet`)를 만들어 타워↔사운드 매핑 | 기각 |

**A를 고른 이유**

1. **투사체가 없는 타워도 발사음이 필요하다.** `TowerAttack.Fire`는 `HasProjectile`이 false면
   투사체를 만들지 않고 `Attack.Execute`로 바로 떨어진다. 그 경로에는 프리팹이 존재하지 않는다.
   `TowerData`가 두 경로의 유일한 공통 지점이다.
2. **`AssignTowerProjectiles`가 발사체 클론을 매번 다시 만든다.** 생성기 주석에 그대로 적혀 있다 —
   "Muzzle·Projectile은 손튜닝이 없으므로 늘 다시 만든다"(손튜닝이 얹힌 Impact만 건너뛴다).
   `ProjectileVisual`에 사운드를 배선하면 `BuildAssignAndValidate`를 한 번 돌릴 때마다 날아간다.
   작업 노트가 `Apply*DecalTuning`에 대해 "생성기를 다시 돌리면 다시 걸어야 한다"고 적어 둔 것과
   같은 함정이고, **손으로 다시 거는 항목을 하나 더 늘리는 셈이다.**
   반대로 `TowerData`는 생성기가 `_projectilePrefab` 속성 하나만 건드리므로 안전하다(§10 참고).
3. **몬스터도 같은 `Projectile`·풀을 쓴다**(`MonsterAttack`). 소리를 프리팹에 심으면 프리팹을
   공유하게 되는 순간 몬스터가 타워 소리를 낸다. 데이터에 두면 id를 넘기지 않는 쪽은 조용하다.
4. **배선이 두 저장소로 갈리지 않는다.** 코드·`SoundCatalog`·`TowerData`가 전부 메인 저장소에
   있으므로 하나의 커밋에서 리뷰되고 하나의 되돌리기로 되돌아간다. 프리팹에 심으면 사운드 한 벌이
   메인과 `Imported` 두 저장소에 나뉘어, 한쪽만 되돌렸을 때 어긋난 상태가 된다.

- `AttackSO`는 안 된다 — `TA_Arrow`를 궁수 타워와 시간 새끼용이 공유한다. 한쪽 소리를 바꾸면
  다른 쪽이 조용히 따라 바뀐다.
- `AttackContext`도 안 된다 — 전투 판정 데이터에 연출을 섞는 자리다.
- C는 매핑 SO를 하나 더 만들고 그것을 누가 들고 있을지(씬? 매니저?)를 새로 정해야 한다.
  타워 1개 = 데이터 1개인 지금 구조에서 얻는 것이 없다.

> **B를 기각한 이유가 "프리팹은 버전관리가 안 돼서"는 아니다.**
> `Assets/Imported`는 버려지는 폴더가 아니라 **팀이 공유하는 별도 private 저장소**다
> (`TowerAndDragon_Imported`. 메인의 `.gitignore`에서만 빠져 있고 `Assets/Imported/.git`에
> 히스토리가 따로 있다 — [작업 노트 §0](./타워이펙트_작업노트.md)).
> 거기 커밋한 프리팹은 팀원 전원이 그대로 받아 쓴다. B가 걸리는 것은 위 1~4이지 저장소가 아니다.

### 4-1. 기본값이 "무음"이어야 한다 — `OptionalSoundId`

§3-4 때문에 `SoundId`를 그대로 필드로 쓸 수 없습니다. `SoundEntry`가 "클립이 비면 조용히 넘어간다"를
정상 상태로 두는 것과 **같은 규칙을 데이터 쪽에도** 둡니다.

```csharp
/// <summary>
/// "지정하지 않음"을 표현할 수 있는 SoundId. enum은 기본값이 0(UiButtonClick)이라 값을 채우지 않은
/// 에셋이 엉뚱한 소리를 내는데, 이 래퍼는 기본값이 무음이다.
/// SoundEntry가 클립 미수급을 조용히 넘기는 것과 같은 규칙이다.
/// </summary>
[System.Serializable]
public struct OptionalSoundId
{
    [Tooltip("끄면 이 사운드는 재생되지 않는다. 값을 채우지 않은 기존 에셋의 기본 상태다.")]
    [SerializeField] private bool _isEnabled;

    [SerializeField] private SoundId _id;

    public SoundId? Value => _isEnabled ? _id : null;
}
```

**기존 사운드에는 영향이 없습니다.** 자주 나오는 오해라 못박아 둡니다 — UI 버튼음은 인스펙터 필드가
아니라 코드에 `SoundManager.Play(SoundId.UiButtonClick)`으로 직접 박혀 있고(40여 곳), 프로젝트에서
`SoundId`를 직렬화하는 필드는 `SoundEntry._id` 하나뿐인데 카탈로그 14줄이 전부 값을 갖고 있습니다.
이 래퍼는 **새로 추가하는 `TowerData` 필드 2개에만** 쓰이므로, 막는 대상은 "버튼 소리"가 아니라
"배선하지 않은 타워가 발사할 때 나는 버튼 소리"입니다.

> **대안(승인 필요)**: `SoundId`에 `None = 0`을 넣고 나머지를 한 칸씩 밀 수도 있습니다. 더 깔끔하지만
> 공용 데이터인 `SoundCatalog.asset`의 `_id` 14개를 전부 마이그레이션해야 하므로, 팀 승인 전에는
> 하지 않습니다. 위 래퍼는 공용 자산을 건드리지 않고 같은 안전성을 얻습니다.

## 5. 코드 변경 (4개 파일 · 신규 1개)

### 5-1. `Assets/Scripts/Sound/OptionalSoundId.cs` (신규)

§4-1 그대로.

### 5-2. `TowerData.cs` — 필드 2개 추가

```csharp
[Header("Sound")]
[Tooltip("발사 순간 재생할 효과음. 투사체가 없는 즉시 적용 타워도 여기서 소리를 낸다.")]
[SerializeField] private OptionalSoundId _fireSound;

[Tooltip("명중 지점에서 재생할 파열음. 투사체 타워만 쓴다. 비워 두면 명중은 무음이다.")]
[SerializeField] private OptionalSoundId _impactSound;

public SoundId? FireSound => _fireSound.Value;
public SoundId? ImpactSound => _impactSound.Value;
```

`ElementalTowerData`·`BabyDragonData`가 상속하므로 필드가 자동으로 따라오고, 켜지 않으면 무음이라
**새끼용은 지금과 똑같이 동작**합니다.

### 5-3. `TowerAttack.Fire()` — 하드코딩된 한 줄 교체

```csharp
- SoundManager.Play(SoundId.TowerFire);
+ if (_towerData.FireSound is SoundId fireSound)
+ {
+     SoundManager.Play(fireSound);
+ }
```

`SoundId.TowerFire`는 **지우지 않습니다** — 뒤 값들이 밀려 카탈로그가 어긋납니다(§3-3).
배선에서만 빠지고, 나중에 새끼용 공용 발사음으로 재사용할 수 있습니다.

### 5-4. `TowerAttack.LaunchProjectile()` — 명중음을 실어 보낸다

```csharp
- projectile.Launch(target, Attack, in context, _towerData.ProjectileSpeed);
+ projectile.Launch(target, Attack, in context, _towerData.ProjectileSpeed, _towerData.ImpactSound);
```

### 5-5. `Projectile.cs` — 명중음 보관 + 재생

```csharp
 private SoundId? _impactSound;

 public void Launch(
     IAttackTarget target,
     AttackSO attack,
     in AttackContext context,
     float speed,
+    SoundId? impactSound = null)
 {
     ResetState();          // ← 이 줄이 첫 줄이다. 그래서 별도 Setter로 미리 넣어 둘 수 없다.
     ...
     _isLaunched = true;
+    _impactSound = impactSound;   // 실패 경로(위쪽 Release)를 다 지난 뒤에 넣는다
 }

 private void ResetState()
 {
     ...
+    _impactSound = null;   // 풀에서 재사용될 때 지난 발사의 소리가 남지 않도록
 }
```

`Update`의 명중 처리:

```csharp
 ApplyHit();

 _visual?.OnHit(transform.position, _travelDirection);

+if (_impactSound is SoundId impactSound)
+{
+    SoundManager.Play(impactSound);
+}

 Release();
```

**결정 사항 3가지**

1. **`ProjectileVisual`이 아니라 `Projectile`이 재생한다.** `ProjectileVisual`은 "연출을 넣지 않은
   프리팹에는 붙이지 않는다"는 선택 컴포넌트다. 소리는 `TowerData`가 지정한 데이터이므로,
   선택 컴포넌트를 경유시키면 소리를 지정했는데 무음이 되는 경로가 생긴다.
2. **`Launch`의 기본 인자로 넣는다.** `MonsterAttack`의 호출부를 건드리지 않고, 몬스터는 지금처럼
   조용하다. 프리팹을 공유하게 되더라도 소리가 딸려가지 않는다(id가 데이터에서 오므로).
3. **타겟이 날아가는 도중 죽어도 파열음은 난다.** `ApplyHit`는 죽은 타겟에 조기 반환하지만
   `OnHit`은 무조건 불린다 — 지금의 임팩트 파티클과 **같은 규칙**이다. 소리만 다르게 두면
   "터졌는데 소리가 없는" 경우가 생기므로 일부러 맞춘다.

리터럴 상수·문자열이 코드에 새로 들어가지 않습니다(CLAUDE.md 3·4번). 볼륨·피치·간격은 전부
`SoundCatalog.asset`의 인스펙터 값입니다.

| `TowerImpactFlame` | `Magic_Spells/` | `fireball_impact_burn_01` / `fireball_impact_sizzle_burn1` |
| `TowerImpactFrost` | `Magic_Spells/` | `ice_spell_forming_shards_01` / `ice_spell_freeze_ground_01` |
| `TowerImpactBoulder` | `Impacts_Smashable/` | `rock_impact_heavy_slam_01` |

> 발사음과 명중음이 **같은 계열이되 다른 클립**이어야 합니다. 불 타워는 `blast`(쏘는 소리) →
> `impact_burn`(터지는 소리)로 자연스럽게 이어집니다.

⚠️ **위 후보는 전부 파일명만 보고 고른 것이고, 아직 한 번도 들어보지 않았습니다.**
[작업 노트 §3-1](./타워이펙트_작업노트.md)이 "자식 이름으로 후보를 거르지 말 것 ★"이라며 같은 실수를
두 번 기록해 뒀습니다 — `Impact_Fire_V1`의 `Derbis`가 실제로는 불덩이였고, 이름이 그럴듯한
`FX_Crack_Firewave`의 `flame`은 아무것도 그리지 않았습니다. **소리도 똑같습니다.**
`ice_spell_forming_shards_01`이 명중음으로 안 들릴 수 있습니다. 배선 후 첫 확인은 "소리가 나는가"가 아니라 **"그 소리로 들리는가"**를
보는 청취 패스여야 하고, 어긋나면 같은 폴더의 다른 번호로 바꿉니다(코드 변경 없음).

## 8. 믹싱 표 (`SoundCatalog.asset` 인스펙터)

`_minInterval`은 **같은 종류 타워 여러 개**가 겹쳐 커지는 것을 막는 장치입니다.
기본 공격 간격의 25~30%로 잡아, **타워 한 대의 소리는 절대 먹히지 않게** 합니다.

실제 발사 간격은 `Attack.Interval / staffingRatio / AttackSpeedMultiplier`라 데이터 값보다 짧아질 수
있어서, 가장 빠른 화살 타워로 하한을 계산했습니다.

- `PopulationAllocation.StaffingRatio`가 **`Mathf.Clamp01`**이라 인구로는 1배를 넘지 못한다
  (제산이지만 빨라지지 않는다).
- 공격속도 배수: 연구 `RE_TowerFireRateIncrease` +0.12 · 시간 타워 오라 ×1.2 ·
  용 스킬트리 +0.10~0.15짜리 몇 개. 전부 겹쳐도 **약 1.8~2.0배**.
- → 화살 타워의 실제 하한 ≈ **0.75 ÷ 2.0 = 0.38초**. `_minInterval` 0.20의 **두 배 여유**다.

이 전제(인구 Clamp01·배수 상한 2배)가 밸런싱으로 깨지면 `_minInterval`을 0.12~0.15로 내려야 합니다.

| SoundId | 공격 간격 | `_volume` | `_pitchRange` | `_minInterval` |
|---|---|---|---|---|
| `TowerFireArrow` | 0.75s | 0.35 | 0.92 ~ 1.08 | 0.20 |
| `TowerFireCrossBow` | 1.25s | 0.40 | 0.94 ~ 1.06 | 0.25 |
| `TowerFireMusket` | 2.0s | 0.45 | 0.96 ~ 1.04 | 0.30 |
| `TowerFireAntiAir` | 2.0s | 0.40 | 0.95 ~ 1.05 | 0.30 |
| `TowerFireFlame` | 1.0s | 0.40 | 0.94 ~ 1.06 | 0.20 |
| `TowerFireFrost` | 1.0s | 0.40 | 0.94 ~ 1.06 | 0.20 |
| `TowerFireBoulder` | 2.5s | 0.45 | 0.96 ~ 1.04 | 0.35 |
| `TowerImpactFlame` | (발사와 1:1) | 0.55 | 0.94 ~ 1.06 | 0.20 |
| `TowerImpactFrost` | (발사와 1:1) | 0.55 | 0.94 ~ 1.06 | 0.20 |
| `TowerImpactBoulder` | (발사와 1:1) | 0.70 | 0.96 ~ 1.04 | 0.35 |

**볼륨 기준**: UI 클릭음이 1.0이다. 발사음은 밤 내내 깔리는 배경이므로 0.35~0.45로 낮추고,
파열음은 그 위에 얹히는 강조라 0.55~0.70으로 올린다. 암석은 광역·저빈도라 가장 크게.

### 8-1. 파열음 길이는 임팩트 파티클 수명 안에 들어와야 한다

작업 노트 §3-5가 임팩트 파티클의 수명을 실측해 뒀습니다. 소리가 그림보다 오래 남으면
"이미 걷힌 자리에서 계속 나는 소리"가 되므로, **클립 길이를 이 값에 맞춰 고릅니다.**

| 타워 | `_impactLifetimeSeconds` | 파티클 실측 | 파열음 클립 목표 |
|---|---|---|---|
| 불 | 0.9 | (Risingfire를 물리고 이 안에서 꺼지게 맞춤) | ~0.8초 이하 |
| 얼음 | 1.5 | 1.2초에 643픽셀 잔존 | ~1.2초 이하 |
| 암석 | 1.4 | 0.6초에 0 | ~0.9초 이하 (암석이 가장 먼저 걷힌다) |

암석은 파티클이 0.6초에 이미 사라지므로 **가장 짧고 강한 클립**이 맞습니다
(`rock_impact_heavy_slam_*`이 그 성격입니다). 얼음은 잔향이 남아도 자연스럽습니다.

### 8-2. 소스 포화 — `_sePoolSize` 12 → 24

`SoundManager.TakeSeSource()`는 소스가 다 차면 **재생 중인 가장 오래된 소스를 덮어씁니다.**
소리가 중간에 뚝 끊기는 형태라 귀에 띕니다. 타워 7종 × 여러 대 + 명중음이 겹치면 12개는 모자랍니다.

`SoundManager`는 **프리팹이 아니라 씬 오브젝트**라 씬마다 따로 들어 있습니다(현재 7개 씬 전부 12).
스크립트 수정 없이 인스펙터 값만 바꾸면 되지만, **씬 하나를 고친다고 나머지가 따라오지 않습니다.**

| 씬 | 빌드 포함 | 전투 | 조치 |
|---|---|---|---|
| `SampleScene` | ○ | ○ | **필수** |
| `Tutorial` | ○ | ○ | **필수** |
| `Haneul_TowerEffectScene` | × | ○ (작업용) | 권장 |
| `StartScene` | ○ | × | 불필요 |
| `UIScene` · `Sangwook_SampleScene` · `Sangwook_Balancing` | × | △ | 담당자 판단 |

### 8-3. 배속과 쿨다운

`IsOnCooldown`은 `Time.unscaledTime` 기준입니다. 2배속에서는 발사 횟수가 두 배가 되지만 쿨다운은
실시간 그대로라 **억제가 더 세게 걸립니다.** 배속에서 소리가 덜 촘촘해지는 것은 의도된 동작입니다
(그대로 두면 2배속 밤이 소음이 됩니다).

## 9. 열린 문제 — 화면 밖 명중음

`SoundManager`의 SE 소스는 전부 `spatialBlend = 0`(2D)이고 매니저 오브젝트에 붙어 있습니다.
따라서 **지도 반대편에서 터진 파열음도 카메라 앞에서 터진 것과 똑같은 크기로 들립니다.**
포탈 4개가 열린 뒤 여러 전선이 동시에 돌아가면 이게 문제가 될 수 있습니다.

고치려면 `SoundManager`에 위치 기반 재생(`PlayAt(SoundId, Vector3)` + 카메라 거리 컷오프)이
필요한데, `SoundManager`는 게임 전체가 쓰는 공용 스크립트라 **팀 승인 후에 별도로 진행합니다.**

- **1단계(이번 작업)**: 2D 재생 + `_minInterval`로 밀도만 잡는다.
- **2단계(승인 후 판단)**: 밤 웨이브를 실제로 돌려 보고 거슬리면 `PlayAt`을 넣는다.

## 11. 플레이 확인 항목

1. 밤에 **화살 타워** 한 대만 두고 본다 → 0.75초마다 활 쏘는 소리가 끊김 없이 난다.
2. **화살 타워를 4~5대**로 늘린다 → 소리가 여러 겹으로 커지지 않고 촘촘해지기만 한다
   (`_minInterval` 0.2가 걸리는 지점).
3. **화살 타워 한 대를 최대로 강화**한다 — 인구를 꽉 채우고, 공격속도 연구를 완료하고, 가능하면
   시간 타워 오라 안에 세운다 → 발사가 빨라진 만큼 **소리도 매 발 빠짐없이 난다**
   (소리가 한 발 걸러 나면 §8의 `_minInterval` 여유 계산이 깨진 것 — 0.12~0.15로 내린다).
4. **석궁 · 머스킷 · 대공** 타워를 하나씩 세운다 → 세 소리가 서로 구분된다. 특히 화살과 석궁이
   같은 계열이므로 **다르게 들리는지**를 본다.
5. **불 타워** → 쏘는 소리(휙)와 명중 파열음(치익)이 **두 번** 들리고, 파열음이 임팩트 파티클이
   터지는 순간과 어긋나지 않는다.
6. **얼음 타워** → 5번과 같되 얼음 계열 소리다.
7. **암석 타워** → 명중음이 가장 묵직하고 크다. 2.5초 간격이라 소리가 겹치지 않는다.
8. 몬스터가 **날아오는 투사체 앞에서 죽는** 상황을 만든다 → 파티클과 파열음이 **함께** 난다
   (둘 중 하나만 나면 §5-5의 3번이 깨진 것).
9. **새끼용**을 배치해 공격시킨다 → 지금과 똑같이 **무음**이다(엉뚱한 UI 클릭음이 나면 §4-1 실패).
10. **시간 타워**를 세운다 → 공격을 안 하므로 아무 소리도 나지 않는다.
11. 타워 10대 이상으로 밤을 한 번 완주한다 → 소리가 중간에 **뚝 끊기지 않는다**(`_sePoolSize`).
12. 설정 창에서 **SE 볼륨을 0**으로 내린다 → 발사음·파열음이 모두 사라진다(BGM은 남는다).
13. **2배속**으로 밤을 돌린다 → 소음이 되지 않고, 발사 소리가 적당히 솎아진다(§8-3).
