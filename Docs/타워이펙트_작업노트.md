# 타워 이펙트 작업 노트

타워 발사체·명중 이펙트를 만들면서 알게 된 것을 적어 둔다.
새 세션에서 이 작업을 이어받는 사람(사람이든 에이전트든)이 같은 함정에 다시 빠지지 않도록.

최종 갱신: 2026-08-24 (근거리 트레이서 v2 — **머스킷 전용으로 축소**. 기본 꺼짐 — 5-6절)

---

## 0. 가장 먼저 알아야 할 것 — 프리팹이 결과물이다

**`Assets/Imported`는 버려지는 폴더가 아니라 팀이 공유하는 별도 private 저장소다.**

- 원격: `github.com/JoKangHyeon/TowerAndDragon_Imported`
- 서브모듈이 아니라 그 자리에 `Assets/Imported/.git`이 따로 있다
- 메인 저장소의 `.gitignore`에 `/[Aa]ssets/[Ii]mported`가 있어 **메인에서만** 빠져 있다
- 팀 규칙: 유료 외부 에셋을 여기에 넣고 팀원 전원이 이 저장소를 공유한다

그래서:

- 여기에 커밋한 프리팹은 **팀원 전원이 그대로 받아 쓴다.** 각자 생성기를 돌리지 않는다.
- 게임이 참조하는 것도 TowerData에 물린 **프리팹**이지 생성기가 아니다.
- 버전 상태를 볼 때는 `git -C Assets/Imported ...`로 물어본다.
  메인 저장소에서 `git status`를 돌리면 "추적 안 됨"으로 보여 **"되돌릴 수 없다"고 오판하기 쉽다.**
  실제로는 히스토리가 있고 `git -C Assets/Imported checkout <경로>`로 되돌릴 수 있다.

**`CoplayScripts/`의 생성기는 프리팹을 만들어 낸 발판이다. 타워 이펙트 작업이 끝나면 폴더째 삭제할 계획이다.**
생성기에 리팩터링·문서화를 투자하지 말 것 — 전부 버려질 코드다.
이펙트 변경 요청이 오면 "생성기에도 반영할까요?"를 기본 선택지로 내밀지 말고,
프리팹만 고치면 되는지 먼저 따진다. 생성기를 고쳐야 하는 경우는 앞으로도 그것을 계속 돌릴 때뿐이다.

작업이 끝나면 `Assets/Imported`에서 커밋해 팀에 공유한다.

## 2. 이 프로젝트에서 이펙트가 깨지는 이유 — 카메라

원본 팩은 **3D 지면을 내려다보는 카메라**를 전제로 만들어져 있다.
이 프로젝트는 카메라를 기울이지 않고(회전 0, z=-10 정사영) 타일 아트를 아이소메트릭으로 그린다.
여기서 두 가지가 어긋난다.

### 2-1. `HorizontalBillboard`는 아무것도 그리지 않는다

월드 XZ 평면에 고정된 렌더 모드라, 회전 0인 카메라에서는 **옆날로 서서 한 픽셀도 안 그린다.**
이 팩의 바닥 데칼은 대부분 이 모드다. 그대로 쓰면 지면 균열이 통째로 사라진다.

고치는 법: `Billboard` + `alignment = View`로 바꾸고, 세로만 절반으로 눌러 바닥에 누운 타원으로 만든다
(아이소메트릭 셀이 1 x 0.5이므로 바닥에 누운 원은 화면에서 2:1 타원이다).

`BuildStatusVfx`의 `LaysDecalsFlat` 옵션이 이 처리를 한다.
얼음·암석은 생성 후 `Apply*DecalTuning`으로 따로 걸었고, 화염은 생성기 안에서 한다.

### 2-2. 원본 기울기는 건드리지 말 것

처음에는 모든 자식의 X·Y 회전을 0으로 눕히는 게 맞다고 봤다(`FlattensToScreenPlane`).
실제로 놓고 보면 **원본 기울기가 그대로 맞다.** 57도쯤 뒤로 누운 메시가 화면에서 눌려 보이는 것이
곧 "셀 바닥에 놓인" 그림이 된다. 정면으로 세우면 오히려 바닥을 뚫고 선 것처럼 보인다.

지금 어느 정의도 이 옵션을 켜지 않는다.

## 3. 겪은 함정들

### 3-1. 자식 이름으로 후보를 거르지 말 것 ★

**이 팩들은 이름과 실제 그림이 자주 어긋난다. 반드시 렌더해서 픽셀로 확인한다.**

같은 작업에서 두 번 틀렸다.

- `Impact_Fire_V1`의 자식이 `Derbis`·`Sparks`·`BigSparks`·`GlowBlack`이라 "불기둥이 없다"고
  후보에서 뺐는데, 실제로는 **`Derbis`가 소용돌이치는 불덩이**였다. 최종 채택안이 됐다.
- 반대로 `FX_Crack_Firewave`의 `floorglow`·`flame`은 이름만 보면 바닥 불길인데
  실제로는 **아무것도 그려지지 않았다**(어두워서 임계값 미달).

측정 도구: `CoplayScripts/MeasureImpactChildren.cs` — 자식 하나만 렌더러를 켜고 구워
폭·높이·픽셀 수를 잰다.

### 3-2. 궤적이 흐릿하면 두께가 아니라 구조를 볼 것

석궁 궤적이 흐릿하다는 지적에 `TrailSizeMultiplier`가 없어서라고 진단했다가 틀렸다.
실제로 날려서 재 보니 배수 없이도 두께 0.06으로 화살(0.065)과 같은 대역이었다.
배수를 주니 0.49까지 부풀어 화면만 어지러워졌다.

진짜 원인은 **궤적을 만드는 자식이 다르다**는 것이었다.

- 화살 `01_nature_arrow`: `SubSparks`(작은 Stretch) + `Glow`(Billboard)가 겹쳐 **매끈한 한 줄**
- 석궁 `21_red_arrow`: `SubEnergy` 하나뿐인데 **넓은 삼각 조각이 흩날리는 그림**
  (렌더러 길이배율이 `-1.5` 음수라 진행 방향 반대로 늘어나기까지 한다)

발사체 원본을 바꿔야 해결된다. 배수로는 안 된다.

측정 도구: `CoplayScripts/RenderProjectileTrails.cs` — 한 프레임씩 Simulate하며 위치를 옮겨
실제로 날리면서 궤적을 굽는다. 제자리에서 Simulate만 하면 World 공간 파티클이 한 점에 겹쳐 쌓여
궤적을 볼 수 없다.

### 3-3. 색조(HueDegrees)는 `ColorOverLifetime`까지 돌려야 한다

`ApplyHue`가 `main.startColor`만 돌리고 `ColorOverLifetime`은 보지 않아,
어떤 색조를 줘도 궤적 선이 청록으로 남는 버그가 있었다(2026-08-23 수정).

원인: 선을 그리는 `SubSparks`는 `startColor`가 흰색이고 실제 색은
`ColorOverLifetime` 그라디언트에 박혀 있었다(`0.35,1,0` → `0,1,0.71`).
흰색을 아무리 돌려도 흰색이라 아무 일도 일어나지 않는다.

지금은 그라디언트 키를 하나씩 돌린다. 알파 키는 건드리지 않는다(페이드 타이밍이 같이 바뀐다).
채도 0인 키(흰색·검정)는 `ShiftHue`가 채도를 유지하므로 저절로 보존된다.

`HueDegrees`는 **절대값**이다 — 원본이 무슨 색이든 그 값으로 바뀐다(채도·명도·알파는 유지).
발사체뿐 아니라 머즐·임팩트에도 걸려 세트 전체가 같은 색이 된다.

⚠️ **단 근거리 트레이서는 따라오지 않는다** — 색이 `ProjectileVisual`에 손배선돼 있다.
여기를 돌렸으면 5-5의 색 표도 같이 고칠 것.

### 3-4. 광역 AOE는 정사영 2D에 못 얹는다

암석 타워에 `FX_Crack_RockAOE`를 얹어 광역 반경을 표시하려 했다가 뺐다.
이 팩의 AOE는 3D 지면을 내려다보는 카메라를 전제로 한 큰 바닥 판이라,
정사영 2D에 맞추려고 빌보드로 세우면 반경을 알려주기는커녕 **솟아오른 바위를 정면에서 덮어 버린다.**
어떤 크기·색 배수를 줘도 "가리거나, 안 보이거나" 둘 중 하나였다.

**대신 들어간 것은 없다. 광역 반경 표시는 지금 없는 상태다.**
남은 지면 균열(ring)은 2.88칸이라 반경 2(지름 4칸)에 못 미치니 반경 표시로 읽으면 안 된다.
사거리를 보여줘야 한다면 별도로 만들어야 한다.

### 3-5. 방출 방식이 명중 연출의 성패를 가른다

명중 이펙트는 **버스트 방출**이어야 한다. 연속 방출(rateOverTime)은 입자가 쌓이는 데 시간이 걸려
명중 순간이 빈다.

| 원본 | 버스트 | 연속 |
|---|---|---|
| `FX_GroundCrack_Blue` (얼음 바탕) | 9 | 2 |
| `FX_Crack_Rock` (암석 바탕) | 13 | 4 |
| `FX_Crack_Risingfire` | **1** | **10** |

Risingfire를 화염 바탕으로 썼다가 물렀다 — t=0.06에 82픽셀밖에 안 그려지고(얼음 6188, 암석 8291)
반대로 t=2.0에도 9646픽셀이 남아 스스로 꺼지지 않았다.

수명 참고값: 얼음은 1.2초에 643픽셀, 암석은 0.6초에 0. 화염도 그 안에서 꺼지게 맞췄다.

### 3-6. 렌더 시트끼리 숫자를 비교하려면 카메라 배율이 같아야 한다

`orthographicSize`가 다르면 임계값을 넘는 바깥 픽셀 수가 달라져 **잰 폭이 통째로 어긋난다.**
한 번 이것 때문에 배수를 반대 방향으로 잡았다(줄여야 한다고 판단했는데 실제로는 키워야 했다).

### 3-7. 병합한 자식은 배수를 다시 잡아야 한다

다른 원본에서 자식을 가져오면 authoring 기준이 달라 그대로는 안 맞는다.

- 얼음: `Crack_BlueShock`의 파열에 ×2.6, `Crack_Blue02`의 줄기에 ×25
- 화염: `Crack_Risingfire`의 `Flash`는 루트 0.11 기준이라 루트 0.84인 쪽에 얹으니
  유효 크기가 36까지 뛰었다 → ×0.13

### 3-8. `RotatesImpactToTravelDirection`은 지면 이펙트에서 꺼야 한다

기본값이 `true`다. 화살·총알처럼 튀는 방향이 있는 임팩트에는 켜야 하지만,
**지면에 깔리는 이펙트는 꺼야 한다** — 켜 두면 아래로 쏜 발사체가 맞았을 때
균열과 솟는 석영까지 뒤집혀 땅을 향한다.

Ice·StoneMeteor·Fire가 `false`다.

### 3-9. 지속 연출은 상태 지속시간 안에 완성돼야 한다 ★

명중 이펙트와 지속 연출은 요구가 정반대다.
명중은 "0.06초에 최대"가 목표지만(3-5), 지속 연출은 **상태가 끝나기 전에 완성 형태에 도달**해야 한다.

`FX_Status_FireBurn`을 화상(3초)에 붙였더니 이런 그림이 나왔다.

| 시점 | 그려진 픽셀(최대 대비) |
|---|---|
| 0.15초 (걸린 순간) | 22% |
| 1초 | 38% |
| 3초 (화상 종료) | 86% |
| 4초 (포화) | 100% |

**가장 알려야 할 첫 1초가 가장 흐리고, 다 타올랐을 때는 이미 끝나 있다.**
화면에서는 "몬스터가 뭔가에 걸렸다"가 아니라 "뭔가 점점 커지다 사라진다"로 읽힌다.

원인이 두 겹이라 한 값만 고치면 안 된다.

- **누적**: 연속 방출이라 입자가 쌓이는 데 시간이 걸린다 → **방출률**을 올려야 한다
- **알파 곡선**: `(0,0)(0.29,0.93)(1,0)` — 각 입자가 **자기 수명의 29%**가 지나야 최대 밝기다.
  수명 5초면 1.45초 뒤, 1.25초면 0.36초 뒤 → **수명**을 줄여야 한다

수명만 줄이면 변동폭은 잡히지만(66%p → 33%p) **초반 밝기는 거의 안 오른다**(34% → 31%).
초반 밝기를 정하는 것은 그 순간까지 쌓인 입자 수, 즉 방출률이기 때문이다.

채택값: **수명 ×0.25, 방출 ×4** (0.15초 52%, 포화 1.5초, 3초까지 변동 16%p)

### 3-10. `MinMaxCurve.constant`는 `constantMax`의 별칭이다 ★

배수를 걸 때 이렇게 쓰면 **제곱으로 걸린다.**

```csharp
rate.constant *= scale;      // constantMax에 쓴다
rate.constantMin *= scale;
rate.constantMax *= scale;   // 방금 곱한 값에 또 곱한다
```

방출률 13에 ×4를 걸었더니 52가 아니라 **208**(=13×16)이 나왔다.
같은 버그가 측정 스크립트에도 있어서 비교표의 `×3`·`×4`가 실제로는 9배·16배였다.

모드를 보고 해당하는 쪽만 건드린다.

```csharp
if (rate.mode == ParticleSystemCurveMode.TwoConstants)
{
    rate.constantMin *= scale;
    rate.constantMax *= scale;
}
else
{
    rate.constant *= scale;
}
```

### 3-11. 픽셀을 잴 때는 씬이 프레임에 섞이지 않게 한다

연출만 렌더한다고 생각했는데 배경 타일과 성이 함께 찍혀 **모든 프레임이 65536픽셀(=256×256) 포화**로
나왔다. 시간에 따른 변화가 전혀 안 보였다.

연출 인스턴스만 빈 레이어(31)로 옮기고 카메라 `cullingMask`를 그 레이어로 제한한다.
`Fire_A`처럼 `startSize`가 8인 자식이 있으면 `orthographicSize`도 넉넉히 잡아야 한다
(0.6은 프레임을 넘겨 역시 포화로 읽힌다).

## 4. 상태 지속 연출 (2026-08-24 추가)

명중 이펙트와 **보완 관계**다. 명중은 1회 사건이라 지속 구간을 못 그리고,
상태가 안 걸린 대상(속성 면역·군중제어 면역)에도 재생돼 거짓 신호가 된다.

### 데이터

프리팹 참조는 `StatusEffectSO`가 든다 — 몬스터가 아니라 **상태**가 자기 연출을 갖는다.
화상 불꽃은 탱크에 붙든 보스에 붙든 같은 불이고, `MonsterData`에 두면 34개 에셋을 채워야 한다.

```csharp
[WiringOptional] [SerializeField] private GameObject _activeVfxPrefab;
[SerializeField] private Vector2 _activeVfxOffset;
```

**비워 두는 것이 기본이다.** 어미용(`DS_*`)은 전역이거나 사거리가 넓어 화면의 모든 몬스터가
동시에 연출을 달게 되므로 채우지 않는다. `DS_FireBurn`·`DS_FireBurn_R2`는 지속시간 0(무한)이라
채우면 불 어미용 사거리 안 몬스터에 불이 상시 붙는다.

### 지금 배선된 것 (4/15)

| 상태 애셋 | 연출 | 지속 |
|---|---|---|
| `TS_FireBurn` | `FX_Status_FireBurn` | 3초 |
| `TS_IceSlow` | `FX_Status_IceSlow` | 2초 |
| `TS_BD_IceSlow` | `FX_Status_IceSlow` | 2초 |
| `TS_BD_IceFreeze` | `FX_Status_IceFreeze` | 3초 |

`FX_Status_IceSlow`는 `FX_Status_FireBurn`을 복사해 색만 바꾼 것이라 **3-9에서 맞춘 시간축을
그대로 물려받았다**(수명 1.25, 방출 40~80). 화상 쪽 타이밍을 다시 건드리면 둔화도 같이 맞춰야 한다.

`FX_Status_IceFreeze`는 별개 원본(rock 계열, 수명 1.3초·방출 200)인데 **0.15초에 이미 99%**로
지속 연출로는 이상적이다. 손댈 것이 없다.

새 상태를 추가할 때는 `_activeVfxPrefab`에 프리팹만 꽂으면 된다 — 코드 변경 0이다.
실제로 둔화·빙결 3개를 배선하는 동안 런타임 코드는 한 줄도 고치지 않았다.

### 런타임

| 파일 | 역할 |
|---|---|
| `MonsterStatusVfx` | 연출 인스턴스 관리. MonoBehaviour가 아니다 |
| `MonsterStatusReceiver` | 위를 소유. dirty 플래그로 변경 시점 수집 |
| `ProjectilePool.AcquirePersistent` / `ReleasePersistent` | 스스로 안 걷히는 연출용 |

설계 결정 세 가지와 이유:

- **몬스터의 자식으로 붙이지 않는다.** 풀 밑에 두고 `LateUpdate`에서 위치만 따라간다.
  루트 스케일이 0.1~1.5로 **15배** 갈려 있어 자식이면 맞춰 둔 크기가 몬스터마다 달라지고,
  사망이 `Destroy(gameObject)`라 자식 연출이 함께 파괴돼 풀 장부에서 인스턴스가 샌다.
- **키는 statusId가 아니라 프리팹이다.** statusId는 출처별로 갈리는데
  (`tower_fire_burn` / `baby_fire_burn` / `dragon_fire_burn`) 화면에 뜨는 불은 하나여야 한다.
- **MonoBehaviour로 만들지 않았다.** 몬스터 프리팹이 33종이고
  `[RequireComponent]`는 **이미 저장된 프리팹에 소급 적용되지 않는다.** 프리팹 배선이 0이다.

앵커는 몸통 중앙 고정이다. 발밑 얼음은 얼음 타워의 **명중** 이펙트가 이미 그린다.
위치는 `SpriteRenderer.bounds`(월드 AABB)로 푼다 — 크기 편차를 프리팹별 손배선 없이 흡수한다.
렌더러는 `Renderer`가 아니라 `SpriteRenderer`로 좁혀 찾는다(방어막·오버레이가 먼저 잡히면
손으로 확인하지 않은 몬스터에서만 연출이 엉뚱한 자리에 뜬다). 33종 전부 루트에서 잡히는 것을 확인했다.

**면역 검사를 연출 계층에 넣지 말 것.** 군중제어 면역은 `Apply`의 `IsImmuneTo`가,
속성 면역은 `BaseMonster.ApplyStatus`가 이미 거른다. 보관 중인 상태는 전부 통과한 것들이다.

### 검증된 것

부여·추종·재부여 중복 없음·만료 반납·사망 후 누수 없음. 몬스터 33종 앵커 정상.
`OnDisable`이 정리 지점이다 — 사망이 `Destroy`라 `Clear()`는 돌지 않는다
(`MonsterStatusReceiver.Clear()`는 지금 호출자가 0개다).

### 남은 것

- **몬스터 풀링을 도입하면** 재사용된 몬스터가 이전 개체의 상태를 물려받는다.
  대여/반납 시점에 `Clear()` 연결이 필요하다.
- `Projectile` 정렬 레이어는 `Building`보다 **나중에**(= 위에) 그려진다.
  TagManager 순서는 `Default → Building → Overlay → Projectile → Fog → Highlight`다.
  그래서 **뒤쪽 몬스터의 불이 앞쪽 몬스터를 덮는다** — 레이어 안에서 뎁스 정렬이 없기 때문이다.
  명중 이펙트도 같은 성질이지만 0.2~1.5초라 안 띄었고, 3초 루프에서 처음 문제가 된다.
  (예전 문장이 "Building보다 뒤에 그려져"로 돼 있어 가림 문제로 오독되기 쉬웠다. 가림이 아니다.)
- `TS_BD_IceFreeze`가 이름과 달리 `FreezeStatusSO`가 아니라 `MoveSpeedStatusSO`(배율 0)다.
  새끼용 3스택 결과가 `IsActionBlocked`를 안 켜서 **이동만 멈추고 공격은 계속한다.**
  `DragonSkillTreeAssetGenerator.cs:399-401`이 이 함정을 경고하고 있다. 별건으로 팀 확인 필요.
  (연출은 화면에서 멈추는 것이 사실이므로 빙결 프리팹을 붙였다 — 타입을 고치면 연출은 그대로 맞는다.)
- **`MP_Ground_ElementImmune_Stone`은 루트 스케일 0.1로 33종 중 유일한 극단값이다.**
  다른 몬스터의 1/10 크기라 어떤 상태 연출도 몬스터를 통째로 덮는다(폭 비율 1.00).
  연출을 줄일 문제가 아니라 그 프리팹의 스케일을 봐야 한다.
- **빙결 결정이 몸통 중앙이 아니라 아래쪽에 몰린다.** 프리팹 내부 오프셋 때문이며,
  `TS_BD_IceFreeze._activeVfxOffset`의 y를 올리면 코드 없이 맞출 수 있다.

## 5. 근거리 트레이서 — v1 진단과 v2 방향 (2026-08-24)

공격 투사체 타워 7종에 근거리 보조 트레이서(v1)를 넣었지만 **수직(상방) 사격의 시인성 문제가 남았다.**
플레이 테스트 지적을 받아 코드·프리팹·씬 설정을 원본에서 다시 읽고 수치로 원인을 특정했다.
아래 5-1은 **파일에서 계산한 확정 수치**, 5-2는 그로부터 정한 **v2 방향**, 5-3은 **측정으로 정할 값**이다.

기준값(이하 전부 공통): `TA_Arrow._range = 4` · `IsometricMath.RADIUS_Y_RATIO = 0.5` ·
FirePoint 로컬 y `3.418 × 루트 스케일 0.12 = 0.41` 월드 ·
`orthographicSize` 5 · 1080p → **108px / 월드유닛**.

### 5-1. v1이 부족했던 이유 (전부 파일에서 확인)

#### ① 상방이 짧아지는 원인은 하나가 아니라 둘이다 ★

| 방향 | FirePoint→표적 거리(월드) | 화면 길이 | 횡 대비 |
|---|---|---|---|
| 횡 (최대) | √(4.0² + 0.41²) ≈ 4.02 | 434px | 1.00 |
| 하 (최대) | 0.41 + 2.0 = 2.41 | 260px | 0.60 |
| **상 (최대)** | **2.0 − 0.41 = 1.59** | **172px** | **0.40** |

타원 사거리(`RADIUS_Y_RATIO = 0.5`)만 보면 1:2다. 실제로는 **1:2.5**다 —
**FirePoint가 상방 반지름 2.0 안쪽으로 0.41을 이미 먹고 들어가기 때문**이다.

근본 원인은 **사거리 판정 원점과 발사 원점이 다르다**는 것이다.
`TowerAttack.IsWithinAttackRange`는 `transform.position` 기준, 발사는 `_firePoint.position` 기준이다.

그래서 타워 원점 위 0 ~ 0.41 월드 구간에 **데드밴드**가 생긴다. 이 구간의 몬스터는
FirePoint보다 **아래**에 있어 사격이 아주 살짝 아래를 향하고, `|dy| ≈ 0`이라 v1의 수직 판정도
통과하지 못해 **보정을 하나도 못 받는다.**

> 사거리 판정을 FirePoint 기준으로 바꾸면 이 불일치는 사라지지만 **밸런스가 바뀐다.**
> 연출 문제를 밸런스로 풀지 않는다 — v2는 연출 계층에서만 흡수한다(5-2 ③).

#### ② Impact Placement가 상방 길이를 한 번 더 깎는다 ★

몬스터 스프라이트 피벗을 확인했다. `EvilDog_64_32`: 64×32px, PPU 32, **pivot y = 0.25**.
→ `bounds.min.y = pos.y − 0.25`, `bounds.center.y = pos.y + 0.25` (월드).

몬스터가 타워 2행 위(+0.5 월드)에 있을 때:

| Placement | 종점 y | FirePoint(0.41) 기준 | 결과 |
|---|---|---|---|
| `Body` (Arrow·CrossBow·Musket·AntiAir) | 0.75 | **+0.34** = 37px | 아주 짧은 선 |
| `Ground` (Fire·Ice·StoneMeteor) | 0.25 | **−0.16** = 17px | **아래를 향한다** |

`Ground` 정책은 상방 근거리에서 **트레이서 부호가 반전된다.**
머즐 섬광은 `_travelDirection`으로 위를 보는데 트레이서는 아래로 그려진다.
최대 사거리에서도 `Ground`는 상방 1.59 중 0.25(16%)를 깎아 145px, 횡 대비 **1:3**이 된다.

Placement는 종점의 **y만** 움직인다. 그래서 4.0 월드짜리 횡 사격에는 각도만 살짝 바꾸지만,
1.59 월드짜리 상방 사격에는 길이를 통째로 깎는다. **두 기능이 서로를 모른 채 간섭하고 있었다.**

#### ③ 48px 게이트가 문제 구간을 거의 덮지 못한다

`_nearTracerMaxScreenDistancePixels = 48` → ortho 5에서 **0.444 월드**.

- 상방 유효 사거리 1.59 월드 중 **약 28%만 커버.** 나머지 72%의 상방 사격은 트레이서가 안 나온다.
- 옆 칸 몬스터(dx 0.5)도 선 길이 0.525 월드 = **57px > 48px → 횡 근거리도 안 나온다.**
- 결국 이 게이트가 실제로 잡는 건 **②의 퇴화 케이스(10~40px)뿐**이다.

#### ④ 줌에 따라 게이트와 선 두께가 정반대로 움직인다 ★

게이트는 **스크린 스페이스**(48px), 선 폭은 **월드 스페이스**(0.08)다.
`CameraController`의 줌 폭은 `_minZoom 3` ~ `_maxZoom 18`으로 **6배**다.

| orthoSize | px/월드 | 게이트 48px = ? 월드 | 글로우 폭 0.08월드 = ? px |
|---|---|---|---|
| 3 (최대 확대) | 180 | 0.27 (거의 발동 안 함) | 14.4px (잘 보임) |
| 5 (기본) | 108 | 0.44 | 8.6px |
| 18 (최대 축소) | 30 | 1.60 (자주 발동) | **2.4px** (끝은 1.35px) |

**잘 보일 두께일 때는 발동하지 않고, 발동할 때는 안 보이는 두께다.**
단위를 섞으면 이렇게 된다 — 한쪽으로 통일해야 한다.

#### ⑤ 보정의 축이 손실의 축과 다르다

수직에서 실제로 잃는 것: **길이 ×0.4 · 비행시간 ×0.4 · 궤적 입자 수 ×0.4**.
v1이 적용한 보정: **폭 ×1.25 · 밝기 ×1.25.**

발광 면적으로 보면 `0.4 × 1.25 = 0.5` — **여전히 절반이다.**
25% 폭 증가로 2.5배 길이 손실을 되돌릴 수 없다.

#### ⑥ 밝기 배율은 사실상 무효다 ★

`ProjectileTracerVisual.SetRendererColor`는 **RGB만** 곱하는데 코어 색이 이미 `(1, 0.95, 0.75)`다.
그리고 `Mat_Tracer_Tower_Near`는 프로퍼티 구성(`_AlphaTex` · `_EnableExternalAlpha` · `PixelSnap` ·
`_Flip` · `_RendererColor`)으로 보아 **Sprites/Default = 프리멀티플라이드 알파, 가산이 아니다.**

→ 1.25배는 클램프돼 색만 흰쪽으로 밀린다. **가산 블렌딩이었다면 진짜 25%가 됐을 값이다.**

덤으로 `_MainTex`가 비어 있다. Sprites/Default는 그 경우 흰 텍스처를 쓰므로
**"글로우"는 글로우가 아니라 하드 엣지 사다리꼴**이다. 알파 블렌드라 밝은 몬스터 스프라이트 위에서
빛나지 못하고 덮기만 한다.

#### ⑦ 트레이서가 하필 몬스터 쪽에서 사라진다 ★

`SetRendererColor`가 `endColor` 알파를 **하드코딩 `0f`**로 두고, 프리팹 폭 커브도
글로우 0.08→0.045 / 코어 0.035→0.012로 좁아진다.
→ **타워 쪽이 가장 밝고 몬스터 쪽이 완전히 투명하다.**

플레이어 시선은 몬스터에 있다. 172px 선에서는 티가 덜 나지만 37px 상방 선에서는
**머즐 섬광 옆의 혹**으로만 남는다.

#### ⑧ 수직 판정이 너무 좁고 계단이다

`|dx| ≤ |dy| × 0.25` → 수직에서 **atan(0.25) = 14°** 원뿔.
"타워 위로 접근"의 대부분(20~45°)은 보정을 **0** 받는다.
그리고 14.1°→14.0°를 넘는 순간 폭·밝기가 25% 튄다 — 램프가 아니라 계단이다.

#### ⑨ 배속을 고려하지 않았다

`GameSpeedManager._fastScales = {2, 3}`이고 `ProjectileTracerVisual.Update`는 `Time.deltaTime`을 쓴다.
3배속에서 0.1초 트레이서는 실시간 **0.033초 ≈ 2프레임**, 상방 근거리 비행은 **0.5프레임**이 된다.

`Update`의 페이드와 `ProjectilePool.ReleaseEffectAfterAsync`의 반납 타이머는 **서로 독립된 시계**다.
지금은 같은 값(`_nearTracerLifetimeSeconds`)을 받아서 우연히 일치할 뿐이다.
한쪽만 unscaled로 바꾸면 어긋난다 — **둘 다 바꾸거나 둘 다 두거나 해야 한다.**

#### ⑩ 문서와 실제가 어긋난 것

- 예전 §5가 적어 둔 "`rateOverDistance`를 3에서 12로 올린다"는
  **7종 중 1종(`Projectile_Tower_Musket_Orange`)에만** 적용돼 있었다.
  실측: Musket 3 · Ice 2·5 · Arrow_Nature 40·3 · Fire 20·5 · **AntiAir 0 · StoneMeteor 0**.
  AntiAir는 공중 몬스터를 쏴 상방 사격 비율이 가장 높은 타워인데 거리 기반 잔상이 아예 없다.
- 애초에 **`rateOverDistance`는 보정 수단으로 부적합하다.** 월드 거리당 방출이라
  상방에서 그대로 절반이 된다 — ⑤의 손실 축과 같은 축이다. 올려도 비율은 안 바뀐다.
- `Projectile_Tower_Arrow.prefab` · `Projectile_Tower_CrossBow.prefab`은 트레이서 미배선인데
  **TowerData가 참조하지 않는 고아 프리팹**이다(실제 배선은 Arrow_Nature / Musket).

#### 가림(occlusion)은 원인이 아니다 — 확인함

TagManager 정렬 레이어 순서는 `Default → Building → Overlay → Projectile → Fog → Highlight`이고,
트레이서는 Projectile 레이어 order 10·11, 타워·몬스터 스프라이트는 Building(`-1328854079`)이다.
**트레이서는 항상 위에 그려진다.** 다음 사람이 이 가설을 다시 쫓지 않도록 적어 둔다.

남는 건 **대비(contrast)** 문제다 — 상방 경로는 타워 자기 스프라이트(0.61월드)와 몬스터 위를 지나고,
횡 경로는 빈 지면을 지난다. 이건 정성적 관찰이고 아직 측정하지 않았다(5-3).

### 5-2. v2 방향 — 방향 판정을 버리고 화면 길이로 간다 ★

**핵심 통찰: "수직"은 원인이 아니라 증상이다.** 수직이 안 보였던 건 방향 때문이 아니라
그 방향에서 **선이 짧아지기** 때문이다. 화면 길이를 직접 재면 수직 케이스가 자동으로 포함되고,
⑧의 14° 원뿔·계단·필드 3개가 통째로 사라지며, ③의 "횡 근거리 57px이 아무것도 못 받는" 구멍도 같이 막힌다.

#### A. 단위를 스크린 스페이스로 통일한다 (④ 해소)

선 폭을 px로 저작하고, 매 `Play`마다 카메라에서 월드 폭을 역산한다.

```csharp
float worldPerPixel = 2f * worldCamera.orthographicSize / worldCamera.pixelHeight;
```

`Screen.height`가 아니라 **`worldCamera.pixelHeight`**를 쓴다 — `WorldToScreenPoint`가 돌려주는 것과
같은 픽셀 공간이어야 레터박스·렌더 텍스처에서 게이트와 폭이 어긋나지 않는다.
`worldLength / screenLength`로 유도하고 싶지만 **하필 고치려는 퇴화 케이스에서 0으로 나눈다.** 쓰지 않는다.

#### B. 계단 게이트를 "길이 부족분" 연속 램프로 바꾼다 (③⑧ 해소)

```
t = 1 − clamp01(screenLength / REFERENCE_LENGTH_PIXELS)
```

`t`가 트레이서의 강도(폭·알파)를 정한다. 기준 220px 가정 시:

| 케이스 | 화면 길이 | t |
|---|---|---|
| 횡 최대 | 434px | 0.00 (안 나옴 — v1과 같음) |
| 상방 최대 | 172px | 0.22 (약하게) |
| 횡 근거리(옆 칸) | 57px | 0.74 |
| 상방 근거리 `Body` | 37px | 0.83 |
| 상방 근거리 `Ground` | 17px | 0.92 |

`_verticalScreenRatio` · `_verticalWidthMultiplier` · `_verticalBrightnessMultiplier` **3개 필드를 제거한다.**

> ⚠️ **의도적인 동작 변경**: 긴 상방 사격(172px)은 지금까지 트레이서가 아예 없었는데
> v2에서는 약한 트레이서가 붙는다. 원치 않으면 `REFERENCE_LENGTH_PIXELS`를 낮춰 되돌릴 수 있다.

#### C. 최소 화면 길이를 보장한다 (①② 해소) — **E에 의존한다**

길이가 `MIN_TRACER_SCREEN_LENGTH_PIXELS` 미만이면 **끝점(몬스터)을 고정하고 시작점을 뒤로 늘린다.**
시선이 있는 쪽을 건드리지 않기 위해서다.

방향은 종점−시작점이 아니라 **항상 `_travelDirection`을 따른다.**
그래야 ②의 `Ground` 부호 반전(길이가 음수가 되는 경우)이 함께 풀린다.
①의 데드밴드도 여기서 흡수된다 — 길이 ≈ 0이면 최소 길이까지 연장된다. **사거리 판정은 건드리지 않는다.**

**C는 E 없이는 오히려 나빠진다.** 시작점을 FirePoint 뒤로 늘리면 선이 타워 스프라이트 안쪽에서
시작하는데, 거기엔 머즐 섬광이 없다. 현재 테이퍼(⑦)에서는 그쪽이 **밝은 끝**이라 고장 난 것처럼 보인다.
E를 먼저 적용해야 그쪽이 **흐린 꼬리**가 되어 "화면 밖에서 들어온 섬광"으로 읽힌다.

#### D. 줌 아웃 가드 (A+B의 부작용 차단) ★

A로 폭이 줌 독립이 되고 B의 게이트도 스크린 px이면, **최대 축소에서 모든 사격이 트레이서를 받는다.**
ortho 18에서는 횡 최대 사격도 4.02월드 = **121px**이라 기준 220px 대비 `t = 0.45`가 된다.
C의 최소 길이 64px도 그 줌에서는 **2.13월드** — 타워보다 긴 줄이 된다.

그래서 두 겹으로 막는다.

1. `worldCamera.orthographicSize > NEAR_TRACER_MAX_ORTHO_SIZE`면 **아예 건너뛴다.**
   (그 줌에서는 투사체 하나하나를 볼 상황이 아니다)
2. C의 연장 길이에 **월드 상한**을 건다. 단 허용 줌 범위(ortho ≤ 10) 안에서는 물리지 않는
   **예비 가드**다 — ortho 10에서 최소 길이가 1.185월드이고 상한이 1.2다.
   실제로 동작하는 가드는 1·3이다.
3. `t < MIN_EFFECTIVE_T`면 건너뛴다 — 램프로 바꾸면 거의 모든 사격이 `t > 0`이 되므로,
   3배속 × 다수 타워에서 `_effectPool.Acquire` 호출이 폭증하는 것을 막는다.

**"드물게"가 조용히 "항상"이 되지 않게 하는 장치다. v1의 반대 방향 함정을 새로 만들면 안 된다.**

#### E. 알파·폭 테이퍼 방향을 뒤집는다 (⑦ 해소)

몬스터 쪽을 불투명·굵게, 타워 쪽을 투명·가늘게. 총알이 지나간 뒤 남는 꼬리 형태다.
`endColor` 알파 `0f` 하드코딩을 없애고, 폭 커브는 프리팹에서 뒤집는다
(글로우 0.045→0.08 / 코어 0.012→0.035). **코드는 프리팹 값을 그대로 쓴다.**

#### F. 가산 블렌딩 (⑥ 해소) — **보류됨. 5-5 참고**

`Mat_Tracer_Tower_Near`의 셰이더를 Sprites/Default → **가산**으로 바꾼다.
그래야 밝기 배율이 실제로 동작하고, 밝은 몬스터 스프라이트 위에서 덮는 대신 빛난다.

소프트 엣지용 그라디언트 텍스처(`_MainTex`)는 **생성하지 않고 팀에 요청한다**(CLAUDE.md 도구 규칙).
없는 동안은 `numCapVertices`로 끝만 둥글린다.

#### G. 배속 (⑨) — **unscaled로 확정. 5-5 참고**

`Update`를 `Time.unscaledDeltaTime`으로 바꾼다면 `ReleaseEffectAfterAsync`의
`UniTask.WaitForSeconds`에도 `ignoreTimeScale: true`를 함께 줘야 한다. **둘 다거나 둘 다 아니거나.**

트레이드오프: unscaled면 3배속에서 트레이서가 게임 시간으로 3배 오래 남아 사격끼리 겹칠 수 있다.
어느 쪽이 나은지는 눈으로 봐야 한다 → 5-3.

#### H. 튜닝값을 SO 하나로 모은다

지금 `48 / 0.1 / 0.25 / 1.25 / 1.25`가 **7개 프리팹에 그대로 복제**돼 있다.
"공용 트레이서"라지만 공유되는 건 프리팹뿐이고 튜닝은 아니다 — 한 값을 고치려면 7곳을 고쳐야 한다.

`NearTracerTuningSO` 하나에 기준 길이·최소 길이·폭(px)·수명·줌 상한을 넣고,
프리팹은 **그 SO 참조 + 글로우 색만** 갖는다. CLAUDE.md의 데이터 주도 원칙과도 맞다.

> ⚠️ **구현 순서**: 수직 관련 3개 필드는 **SO가 생기고 7개 프리팹이 이관된 뒤에** 지운다.
> 먼저 지우면 유니티가 직렬화 값을 조용히 버린다.
> `ProjectileImpactPlacement`의 "새 값은 항상 끝에만 추가한다" 주석과 같은 규율이다.

#### I. 손대지 않기로 한 것

- **사거리 판정** — ①의 원점 불일치는 연출(C)로 흡수한다. 밸런스를 건드리지 않는다.
- **피해 시점·투사체 속도·경로** — v1과 같이 그대로 둔다.
- **`rateOverDistance`** — ⑩대로 손실과 같은 축이라 올려도 비율이 안 바뀐다.
  예전 §5의 "3→12"는 **6/7이 미적용이었을 뿐 아니라 애초에 방향이 틀렸다.** 측정 후 최종 판단(5-3).

### 5-3. 측정으로 결정할 것 — 각 수치가 답할 결정

파일에서 계산한 5-1의 산술은 렌더 없이 확정이다.
하지만 **길이 손실 · 알파 테이퍼 · 대비 중 무엇이 지배적인지 순위는 파일로 못 정한다.**
§3-2가 정확히 이 함정이다 — "두께가 문제"라는 그럴듯한 진단이 렌더 측정으로 뒤집혔던 건.

| 측정 | 답할 결정 |
|---|---|
| 4케이스(횡 최대 / 상방 최대 / 상방 근거리 `Body` / 상방 근거리 `Ground`) 픽셀 | 길이 vs 테이퍼 vs 대비 **순위** |
| 기준 길이 후보 시트 | `REFERENCE_LENGTH_PIXELS` |
| 최소 길이 후보 시트 | `MIN_TRACER_SCREEN_LENGTH_PIXELS` |
| ortho 3 / 5 / 12 / 18 시트 | `NEAR_TRACER_MAX_ORTHO_SIZE`, `MIN_EFFECTIVE_T` |
| 알파 블렌드 vs 가산 비교 | F를 적용할지 |
| 1× / 3배속 연속 사격 | G의 scaled vs unscaled |
| 잔상 유/무 비교 | `rateOverDistance`를 손댈 가치가 있는지 |

**측정 방법 — 페이드를 돌릴 필요가 없다.**
페이드는 선형이라 해석적으로 안다. 4케이스가 다른 건 **기하(화면 길이 × 폭)**뿐이다.
그래서 플레이 모드 없이, `tracer.Play(start, end, ...)`에 5-1에서 유도한 좌표
(FirePoint +0.41 / 몬스터 +0.5·+2.0 / `bounds.center` +0.25 · `bounds.min` −0.25)를 넣고 **한 프레임만 굽는다.**

시트는 **둘로 나눈다.**

- **격리 시트** — 레이어 31 + `cullingMask` 제한(§3-11). 트레이서 픽셀 수를 재는 용도.
  이걸 안 하면 모든 프레임이 65536으로 포화해 아무것도 안 보인다. **이미 한 번 당한 함정이다.**
- **합성 시트** — 타워·몬스터를 같이 넣는다. **대비 질문에만** 필요하다.

한 시트 안에서는 `orthographicSize`를 반드시 통일한다(§3-6 — 배수를 반대로 잡게 만든 함정).
그리고 §3-1대로 **자식 이름이 아니라 픽셀로 판정한다.**

가장 중요한 실측이다. 5-1 ③의 "72% 미커버"가 예측이 아니라 사실이었다.

| 케이스 | 정책 | 화면 길이 | v1 게이트 | v1 총픽셀 |

| 횡 최대 | Body | 432px | 차단 | **0** |
| 횡 근거리 | Body | 57px | 차단 | **0** |
| **상방 최대** | Body | 199px | **차단** | **0** |

**플레이 테스트에서 지적된 "타워 위로 접근하는 적"은 v1의 트레이서가 한 픽셀도 그리지 않는 구간이었다.**

#### ② 최소 화면 길이 보장은 방향 차이를 실제로 없앤다

끝점 고정 + 시작점을 `travelDirection` 반대로 연장:

| 케이스 | 원래 | 보정 후 | 총픽셀 | 방향 |
|---|---|---|---|---|
| 횡 근거리 | 57px | 64px | 427 | 정방향 |
| 상방 근거리 Body | 37px | 64px | 430 | 정방향 |
| 상방 근거리 Ground | 17px | 64px | 430 | **정방향** (v1은 역방향) |
| 상방 데드밴드 | 4px | 64px | 428 | 정방향 |

**네 케이스가 427~430픽셀로 수렴한다.** "방향과 무관하게 같은 양"이 목표였고 그것이 달성된다.
`Ground` 정책의 부호 반전(5-1 ②)도 함께 풀린다 — `travelDirection`을 따르게 했기 때문이다.

96px 후보는 데드밴드에서 v1 대비 8.3배가 되고 ortho 18에서 2.13월드(타워 0.61월드의 3.5배)가 되어
과하다. → **`MIN_TRACER_SCREEN_LENGTH_PIXELS = 64`.**

#### ③ ⚠️ 초안이 틀렸다 — `t`를 폭에 걸면 긴 선이 사라진다 ★★

v2 초안은 "`t`가 폭과 알파를 함께 스케일한다"였다. **측정에서 뒤집혔다.**

기준 220px에서:

| 케이스 | 화면 길이 | t | 폭=t | **폭=고정** | 폭=0.6~1.0 |
|---|---|---|---|---|---|
| 횡 최대 | 432px | 0.00 | 0 | 0 | 0 |
| **상방 최대 Body** | 199px | 0.10 | **0** | **324** | 194 |
| 상방 최대 Ground | 145px | 0.34 | 188 | **772** | 590 |
| 횡 근거리 | 64px | 0.71 | 287 | 412 | 361 |
| 상방 근거리 Ground | 64px | 0.71 | 294 | 414 | 372 |

낮은 `t`에서 폭까지 줄이면 선이 **서브픽셀이 되어 통째로 사라진다**
(t=0.10 → 폭 0.008월드 = 0.86px). 알파를 낮추는 것과 폭을 좁히는 것이 곱으로 걸린다.

→ **`t`는 알파만 스케일한다. 폭은 px 저작값 고정이다.** 설계 문서 9-2 규칙 3을 이 내용으로 고쳤다.

같은 함정을 3-10에서 이미 한 번 겪었다 — **배수를 어디에 거는지가 결과를 가른다.**

#### ④ 기준 길이는 280px

| 기준 | 횡 최대 432px | 상방 최대 B 199px | 상방 최대 G 145px | 판정 |
|---|---|---|---|---|
| 160px | t=0 (안 나옴) | **t=0 (안 나옴)** | t=0.10 → 234px | ✗ 문제 구간이 여전히 빈다 |
| 220px | t=0 (안 나옴) | t=0.10 → 324px | t=0.34 → 772px | △ 상방 최대가 너무 약하다 |
| **280px** | **t=0 (안 나옴)** | **t=0.29 → 984px** | t=0.48 → 844px | ✓ |

280px면 **횡 최대는 계속 배제**하면서(레이저처럼 남지 않는다) 상방 최대를 확실히 잡는다.
→ **`REFERENCE_LENGTH_PIXELS = 280`.**

> 흉내낸 것이고, "몬스터 쪽 절반"은 원래 기준선으로 센다. 그래서 밝고 굵은 쪽이 반대 끝으로
> 옮겨가면 그 절반의 개수가 **구조적으로** 올라간다. 총픽셀이 2722 → 2724로 거의 같고
> 다섯 케이스가 모두 +24~28%p로 대칭인 것이 그 증거다.
>
> 즉 이 표는 **질량 재배치를 확인한 것이고, 시인성 이득을 독립적으로 측정한 것이 아니다.**
> "플레이어 시선이 몬스터에 있다"는 전제에서 이득을 **추론**한 것이다 —
> 합리적이지만 측정된 사실은 아니다.

**반면 다음은 대칭 아티팩트가 아니다 — 절대 임계값을 넘고 못 넘는 문제라 더 강한 근거다.**

③ 표의 "고정 몬스터쪽" 열을 보면 기준 220px · 상방 최대 Body는 총 324픽셀인데
**몬스터 쪽 절반은 0**이다. 낮은 `t`에서 현재 테이퍼가 몬스터 쪽을 임계 알파 아래로 깎기 때문이다.
반전하면 같은 픽셀 예산에서 그 0이 채워진다.

→ **램프(B)는 테이퍼 반전(E) 없이는 동작하지 않는다.** 5-2는 C(최소 길이)만 E에 의존한다고
적었지만 B도 의존한다. 초안에 없던 발견이다.

#### 배속: unscaled로 확정 (5-2 G 결정)

`ProjectileTracerVisual.Update`는 `Time.unscaledDeltaTime`, `ProjectilePool`의 반납은
`UniTask.WaitForSeconds(..., ignoreTimeScale: true)`다. **둘 다 바꿨다** — 한쪽만 바꾸면 어긋난다.

`ignoreTimeScale`은 **트레이서에만** 준다. 명중 이펙트는 게임 시간에 묶여 있어야 배속에서
전투 속도와 함께 빨라진다.

겹침 우려는 크지 않다: 최단 타워 공격 간격이 0.75초(`TA_Arrow`)이므로 3배속에서도 실시간
0.25초 간격이고 트레이서는 0.1초다. 공격속도 배율을 겹겹이 쌓으면 이 여유가 줄 수 있지만,
같은 시작·끝을 공유하는 두 트레이서는 화면에서 거의 구분되지 않고 각자 별도 풀 인스턴스라
장부도 어긋나지 않는다. **경계를 촘촘히 잡을 필요가 없는 종류의 위험이다.**

#### 가산 블렌딩(F)은 보류했다 — 미룬 것이 아니라 근거가 사라졌다 ★

> 굳이 없어도. musket 타워가 그 부분의 문제가 도드라져서 내가 트레이서를 만든 건데,
> musket 타워에만 일단 붙이고 나머지 타워는 내가 필요성을 느껴서 해달라고 하면 그 때 추가하는
> 게 나을 것 같아."

**트레이서는 원래 머스킷의 시인성 문제를 풀려고 만든 장치다.** 그런데 구현할 때 "공격 투사체
타워 7종"으로 범위를 넓혔고, 그 전제를 아무도 검증하지 않았다. 실제로는 나머지 타워가
트레이서 없이도 근거리에서 잘 보인다 — **없어도 되는 곳에 붙어 있었다.**

그래서 정책을 뒤집는다.

| | 이전 | **지금** |
|---|---|---|
| 기본값 | 켜짐 (7종 전부) | **꺼짐** |
| 목록의 뜻 | 제외 목록 | **포함 목록** (`TRACER_ENABLED`) |
| 켜져 있는 타워 | 7종 (암석 제외 후 6종) | **머스킷 1종** |

켜는 방법은 `WireNearTracerTuning.TRACER_ENABLED`에 한 줄 추가하고 스크립트를 다시 돌리는 것뿐이다.
**코드 변경도 프리팹 손배선도 없다.** 튜닝 참조(`_nearTracerTuning`)는 꺼진 타워에도 남겨 두어
"의도된 꺼짐"과 "배선 누락"이 구분되고, 나중에 켤 때 바로 켜진다.

이 설계가 값싼 이유는 `PlayNearTracer`가 `_nearTracerPrefab`이 널이면 그냥 빠져나오기 때문이다.
분기도, 플래그도, 타워별 코드도 없다.

#### 배운 것 — "일반화"가 항상 이득은 아니다

5-1~5-5의 진단·측정·구현은 전부 맞았다. **틀린 것은 적용 범위였다.**
한 타워의 문제를 고치면서 "같은 성질의 타워 전부"로 넓히는 것은 자연스러워 보이지만,
그 타워들에 실제로 문제가 있는지는 **재지 않았다.** 측정은 "트레이서가 얼마나 그려지나"를 쟀지
"트레이서가 없으면 안 보이나"를 잰 적이 없다.

필요하지 않은 곳의 연출은 이득 없이 대여 비용(사거리 안 사격의 약 50%)과 화면 노이즈만 늘린다.

#### 암석은 그 전에 이미 빠졌다 — 다른 이유로

정책 전환 직전에 암석이 먼저 제외됐고, 근거가 달라서 남겨 둔다.
**측정으로는 잡을 수 없는 종류의 문제였다.**

> "암석 타워는 발사체가 둥근 메테오 같은 발사체라, 근거리에서 라인 렌더러로 나가면
> 발사체는 없이 갑자기 라인으로만 나가게 되거든."

#### 이것은 5-5의 위치 문제와 다른 문제다

| | 5-5가 지적한 것 | 여기서 지적된 것 |
|---|---|---|
| 종류 | **위치** — 트레이서가 머즐 섬광보다 아래 | **시각 어휘** — 둥근 발사체에 선 |
| 숫자로 잡히나 | 좌표로 보인다 | **전혀 안 잡힌다** (픽셀·방향 다 정상) |

5-3-1과 5-5는 "얼마나 그려지나 / 어느 방향인가"만 쟀다.
**"그 선이 이 타워의 발사체처럼 보이나"는 잰 적이 없다.** 픽셀로 답이 나오는 질문이 아니다.

#### 왜 암석에서 가장 심한가 — 세 가지가 겹친다

1. **발사체 원본이 `Projectile_V1_19_circle_bomb`** — 이름 그대로 둥근 폭탄이다.
   선은 화살·총알의 어휘이고 낙하하는 바위의 어휘가 아니다.
2. **`rateOverDistance`가 4개 전부 0** — 7종 중 유일하게 거리 기반 잔상이 없다(5-1 ⑩ 실측).
   다른 타워는 짧게나마 입자가 깔리는데 암석은 그것도 없다.
3. **근거리 상방 비행이 0.09월드 / `_projectileSpeed 5`** = **0.018초 ≈ 1프레임.**
   (속도 5는 7종 중 유일하게 절반이다. 그래도 거리가 짧아 상쇄되지 않는다.)

화면에서는 `머즐 → (한 프레임) → 선 → 지면 균열`이 되고 가운데 "바위가 날아간다"가 통째로 빠진다.
선이 그 자리를 메우려다 **다른 무기가 발사된 것처럼** 읽힌다.

Fire(둥근 화염구)도 정도가 덜할 뿐 같은 성질이고, Ice(`blue_crystal`, 파편형)는 선이 그나마 맞는 어휘다.
**지금은 암석만 뺀다** — 불·얼음은 플레이에서 문제로 지적되지 않았다.

#### 제외의 근거 — 임팩트가 이미 말하고 있다

암석은 `_impactLifetimeSeconds`가 **1.4초**로 7종 중 가장 길고 지면 균열이 크다.
트레이서가 필요했던 것은 **명중 연출이 짧고 작은 타워들**이다.
암석은 "명중했다"를 임팩트가 충분히 전달하므로 비행 구간을 선으로 메울 이유가 약하다.

#### ⚠️ 석궁은 이 작업의 관리 밖으로 나갔다

병렬 세션이 `TD_CrossBow._projectilePrefab`을 이 작업 중에 **두 번** 바꿨다.

```

이후    Projectile_V2_25_yellow          (현재)
```

배선 도구는 TowerData를 따라가므로 **현재 발사체(`Projectile_V2_25_yellow`)에는 튜닝이 없다.**
그리고 `Projectile_Tower_CrossBow_AP`에는 **트레이서가 켜진 채로 남아 있다** —
21:21 실행 때 붙은 것인데, 지금은 어느 TowerData도 참조하지 않아 도구가 끄지 못한다.
석궁 작업이 정리되면 `WireNearTracerTuning`을 한 번 더 돌릴 것.

#### 검증 (`CoplayScripts/VerifyStoneTracerExclusion.cs`)

암석 제외 시점에 실제 코드 경로(`OnHit`)로 확인했다. **대조군을 같이 돌렸다** —
"암석에 안 나온다"만 보면 제외가 먹은 것인지 측정이 잘못된 것인지 구분되지 않는다.
(이후 정책이 바뀌어 얼음도 꺼졌으므로, 지금 이 스크립트를 다시 돌리면 둘 다 "없음"이 나온다.)

| 몬스터 위치 | 암석 | 얼음(대조군) |
|---|---|---|
| (0, 0.5) 상방 근거리 | 없음 ✓ | 재생 ✓ |
| (0, 2.0) 상방 최대 | 없음 ✓ | 재생 ✓ |
| (0.5, 0) 횡 근거리 | 없음 ✓ | 재생 ✓ |

배선 상태도 함께 찍었다: 암석 `트레이서=<비어 있음> 튜닝=NearTracerTuning`,
얼음 `트레이서=Tracer_Tower_Near 튜닝=NearTracerTuning`.

#### 남긴 선택지 (지금은 하지 않는다)

머리를 굵고 둥글게 만들어 "도착한 덩어리 + 짧은 꼬리"로 읽히게 하는 방법도 있다.
다만 **폭은 공용 SO 한 곳에서 나오고 타워별로 다른 것은 색뿐**이라 구조 변경이 따라온다.
암석 하나 때문에 그 구조를 깨지 않는다. 불·얼음까지 같은 문제로 지적되면 그때 재검토한다.

## 6. 도구

전부 `CoplayScripts/` 아래에 있고 Coplay MCP `execute_script`로 실행한다.
`Assets/` 밖이라 유니티가 컴파일하지 않고 `MenuItem`도 없어서 **에디터에서 직접 호출할 수 없다.**

| 스크립트 | 하는 일 |
|---|---|
| `BuildStatusVfx` | Eric 팩에서 `FX_Impact_*` 조합. `Build`(있으면 건너뜀) / `Rebuild`(덮어씀+백업) |
| `AssignTowerProjectiles` | 타워별 클론 생성 + TowerData 배선. `BuildAssignAndValidate` / `RebuildAll` |
| `Apply*DecalTuning` | 생성 후 손튜닝(얼음·암석). 생성기를 다시 돌리면 다시 걸어야 한다 |
| `MeasureImpactChildren` | 자식 하나씩 렌더해 크기·픽셀 측정 |
| `RenderProjectileTrails` | 발사체를 실제로 날리며 궤적 측정 |
| `MeasureNearTracerCases` | 근거리 트레이서 8케이스 기하 측정. v1 게이트 차단 여부 + 최소길이 후보 |
| `MeasureNearTracerRamp` | 길이 램프·테이퍼 방향·줌 상한. 폭 정책 3개를 나란히 비교 |
| `WireNearTracerTuning` | `NearTracerTuning` 애셋 생성 + 7종 배선. TowerData를 따라간다 |
| `VerifyNearTracerV2` | **실제 코드 경로**(`OnHit`)로 v2 검증. 편집 모드용 풀 초기화 포함 |
| `RenderImpactAlign` | 여러 임팩트를 같은 시트에 굽고 스폰 높이 기준 정렬 확인 |
| `VerifyTowerDataRefs` | ScriptableObject 참조가 살아있는지 검사 |
| `MeasureStatusVfxRamp` | 지속 연출의 시간대별 입자 수 (개수는 참고용, 판정은 픽셀로) |
| `MeasureStatusVfxPixels` | 지속 연출의 시간대별 픽셀·높이. 전용 레이어로 배경 배제 |
| `TuneStatusVfxLifetime` | 수명·방출 배수 후보를 한 시트에 굽고 초반 밝기·변동폭 비교 |
| `ApplyStatusVfxTiming` | 고른 배수를 프리팹에 적용 |
| `RenderStatusVfxOnMonster` | 연출을 실제 몬스터 위에 얹어 굽고 몬스터 대비 폭 비율 측정 |

렌더 결과는 `output/vfx_check/`에 쌓아 둔다. **대부분 커밋되지 않은 상태다** —
`git ls-files output`이 2개만 돌려준다. 재현이 필요하면 위 스크립트를 다시 돌리는 것이 전제다.

**덮어쓰기 전에 반드시 백업한다.** 기본 진입점은 이미 있는 산출물을 건너뛰고,
`Rebuild`/`RebuildAll`은 프로젝트 루트 `VfxBackup/<시각>/`에 사본을 남긴다(`.meta`까지 — GUID가 거기 있다).

## 7. 남은 것 (타워 이펙트)

- **근거리 트레이서 v2 플레이 확인** — 구현·정지프레임 검증은 끝났다(5-5). 남은 4항목은 5-5 맨 끝. 마일스톤 M9
- 광역 반경 표시 (3-4) — 암석 타워가 유일한 광역인데 지금 표시가 없다
- 화염 임팩트가 얼음·암석보다 무게중심이 높다(0.22~0.29 대 0.03~0.19).
  폭발이라 어느 정도는 자연스럽지만 셋을 나란히 보면 눈에 띈다
- Arrow와 CrossBow가 같은 발사체 원본이라 **색만으로 구분된다**
  — 손대면 트레이서 색도 함께 고쳐야 한다(5-5의 색 표). 자동으로 따라오지 않는다
- `CoplayScripts/` 삭제 (작업 완료 후)
