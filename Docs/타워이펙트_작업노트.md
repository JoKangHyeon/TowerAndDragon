# 타워 이펙트 작업 노트

타워 발사체·명중 이펙트를 만들면서 알게 된 것을 적어 둔다.
새 세션에서 이 작업을 이어받는 사람(사람이든 에이전트든)이 같은 함정에 다시 빠지지 않도록.

최종 갱신: 2026-08-25 (근거리 트레이서 **제거**. 원인을 발사체 교체로 해결 — 5절)

---

## 0. 가장 먼저 알아야 할 것 — 프리팹이 결과물이다

**`Assets/Imported`는 버려지는 폴더가 아니라 팀이 공유하는 별도 private 저장소다.**

- 원격: `github.com/JoKangHyeon/TowerAndDragon_Imported`
- 서브모듈이 아니라 그 자리에 `Assets/Imported/.git`이 따로 있다
- 메인 저장소의 `.gitignore`에 `/[Aa]ssets/[Ii]mported`가 있어 **메인에서만** 빠져 있다
- 팀 규칙: 유료 외부 에셋을 여기에 넣고 팀원 전원이 이 저장소를 공유한다

그래서:

- 여기에 커밋한 프리팹은 **팀원 전원이 그대로 받아 쓴다.** 각자 생성기를 돌리지 않는다.
- 게임이 참조하는 것도 TowerData에 물린 **프리팹**이지 생성기가 아니다.
- 버전 상태를 볼 때는 `git -C Assets/Imported ...`로 물어본다.
  메인 저장소에서 `git status`를 돌리면 "추적 안 됨"으로 보여 **"되돌릴 수 없다"고 오판하기 쉽다.**
  실제로는 히스토리가 있고 `git -C Assets/Imported checkout <경로>`로 되돌릴 수 있다.

**`CoplayScripts/`의 생성기는 프리팹을 만들어 낸 발판이다. 타워 이펙트 작업이 끝나면 폴더째 삭제할 계획이다.**
생성기에 리팩터링·문서화를 투자하지 말 것 — 전부 버려질 코드다.
이펙트 변경 요청이 오면 "생성기에도 반영할까요?"를 기본 선택지로 내밀지 말고,
프리팹만 고치면 되는지 먼저 따진다. 생성기를 고쳐야 하는 경우는 앞으로도 그것을 계속 돌릴 때뿐이다.

작업이 끝나면 `Assets/Imported`에서 커밋해 팀에 공유한다.

## 2. 이 프로젝트에서 이펙트가 깨지는 이유 — 카메라

원본 팩은 **3D 지면을 내려다보는 카메라**를 전제로 만들어져 있다.
이 프로젝트는 카메라를 기울이지 않고(회전 0, z=-10 정사영) 타일 아트를 아이소메트릭으로 그린다.
여기서 두 가지가 어긋난다.

### 2-1. `HorizontalBillboard`는 아무것도 그리지 않는다

월드 XZ 평면에 고정된 렌더 모드라, 회전 0인 카메라에서는 **옆날로 서서 한 픽셀도 안 그린다.**
이 팩의 바닥 데칼은 대부분 이 모드다. 그대로 쓰면 지면 균열이 통째로 사라진다.

고치는 법: `Billboard` + `alignment = View`로 바꾸고, 세로만 절반으로 눌러 바닥에 누운 타원으로 만든다
(아이소메트릭 셀이 1 x 0.5이므로 바닥에 누운 원은 화면에서 2:1 타원이다).

`BuildStatusVfx`의 `LaysDecalsFlat` 옵션이 이 처리를 한다.
얼음·암석은 생성 후 `Apply*DecalTuning`으로 따로 걸었고, 화염은 생성기 안에서 한다.

### 2-2. 원본 기울기는 건드리지 말 것

처음에는 모든 자식의 X·Y 회전을 0으로 눕히는 게 맞다고 봤다(`FlattensToScreenPlane`).
실제로 놓고 보면 **원본 기울기가 그대로 맞다.** 57도쯤 뒤로 누운 메시가 화면에서 눌려 보이는 것이
곧 "셀 바닥에 놓인" 그림이 된다. 정면으로 세우면 오히려 바닥을 뚫고 선 것처럼 보인다.

지금 어느 정의도 이 옵션을 켜지 않는다.

## 3. 겪은 함정들

### 3-1. 자식 이름으로 후보를 거르지 말 것 ★

**이 팩들은 이름과 실제 그림이 자주 어긋난다. 반드시 렌더해서 픽셀로 확인한다.**

같은 작업에서 두 번 틀렸다.

- `Impact_Fire_V1`의 자식이 `Derbis`·`Sparks`·`BigSparks`·`GlowBlack`이라 "불기둥이 없다"고
  후보에서 뺐는데, 실제로는 **`Derbis`가 소용돌이치는 불덩이**였다. 최종 채택안이 됐다.
- 반대로 `FX_Crack_Firewave`의 `floorglow`·`flame`은 이름만 보면 바닥 불길인데
  실제로는 **아무것도 그려지지 않았다**(어두워서 임계값 미달).

측정 도구: `CoplayScripts/MeasureImpactChildren.cs` — 자식 하나만 렌더러를 켜고 구워
폭·높이·픽셀 수를 잰다.

### 3-2. 궤적이 흐릿하면 두께가 아니라 구조를 볼 것

석궁 궤적이 흐릿하다는 지적에 `TrailSizeMultiplier`가 없어서라고 진단했다가 틀렸다.
실제로 날려서 재 보니 배수 없이도 두께 0.06으로 화살(0.065)과 같은 대역이었다.
배수를 주니 0.49까지 부풀어 화면만 어지러워졌다.

진짜 원인은 **궤적을 만드는 자식이 다르다**는 것이었다.

- 화살 `01_nature_arrow`: `SubSparks`(작은 Stretch) + `Glow`(Billboard)가 겹쳐 **매끈한 한 줄**
- 석궁 `21_red_arrow`: `SubEnergy` 하나뿐인데 **넓은 삼각 조각이 흩날리는 그림**
  (렌더러 길이배율이 `-1.5` 음수라 진행 방향 반대로 늘어나기까지 한다)

발사체 원본을 바꿔야 해결된다. 배수로는 안 된다.

측정 도구: `CoplayScripts/RenderProjectileTrails.cs` — 한 프레임씩 Simulate하며 위치를 옮겨
실제로 날리면서 궤적을 굽는다. 제자리에서 Simulate만 하면 World 공간 파티클이 한 점에 겹쳐 쌓여
궤적을 볼 수 없다.

### 3-3. 색조(HueDegrees)는 `ColorOverLifetime`까지 돌려야 한다

`ApplyHue`가 `main.startColor`만 돌리고 `ColorOverLifetime`은 보지 않아,
어떤 색조를 줘도 궤적 선이 청록으로 남는 버그가 있었다(2026-08-23 수정).

원인: 선을 그리는 `SubSparks`는 `startColor`가 흰색이고 실제 색은
`ColorOverLifetime` 그라디언트에 박혀 있었다(`0.35,1,0` → `0,1,0.71`).
흰색을 아무리 돌려도 흰색이라 아무 일도 일어나지 않는다.

지금은 그라디언트 키를 하나씩 돌린다. 알파 키는 건드리지 않는다(페이드 타이밍이 같이 바뀐다).
채도 0인 키(흰색·검정)는 `ShiftHue`가 채도를 유지하므로 저절로 보존된다.

`HueDegrees`는 **절대값**이다 — 원본이 무슨 색이든 그 값으로 바뀐다(채도·명도·알파는 유지).
발사체뿐 아니라 머즐·임팩트에도 걸려 세트 전체가 같은 색이 된다.


### 3-4. 광역 AOE는 정사영 2D에 못 얹는다

암석 타워에 `FX_Crack_RockAOE`를 얹어 광역 반경을 표시하려 했다가 뺐다.
이 팩의 AOE는 3D 지면을 내려다보는 카메라를 전제로 한 큰 바닥 판이라,
정사영 2D에 맞추려고 빌보드로 세우면 반경을 알려주기는커녕 **솟아오른 바위를 정면에서 덮어 버린다.**
어떤 크기·색 배수를 줘도 "가리거나, 안 보이거나" 둘 중 하나였다.

**대신 들어간 것은 없다. 광역 반경 표시는 지금 없는 상태다.**
남은 지면 균열(ring)은 2.88칸이라 반경 2(지름 4칸)에 못 미치니 반경 표시로 읽으면 안 된다.
사거리를 보여줘야 한다면 별도로 만들어야 한다.

### 3-5. 방출 방식이 명중 연출의 성패를 가른다

명중 이펙트는 **버스트 방출**이어야 한다. 연속 방출(rateOverTime)은 입자가 쌓이는 데 시간이 걸려
명중 순간이 빈다.

| 원본 | 버스트 | 연속 |
|---|---|---|
| `FX_GroundCrack_Blue` (얼음 바탕) | 9 | 2 |
| `FX_Crack_Rock` (암석 바탕) | 13 | 4 |
| `FX_Crack_Risingfire` | **1** | **10** |

Risingfire를 화염 바탕으로 썼다가 물렀다 — t=0.06에 82픽셀밖에 안 그려지고(얼음 6188, 암석 8291)
반대로 t=2.0에도 9646픽셀이 남아 스스로 꺼지지 않았다.

수명 참고값: 얼음은 1.2초에 643픽셀, 암석은 0.6초에 0. 화염도 그 안에서 꺼지게 맞췄다.

### 3-6. 렌더 시트끼리 숫자를 비교하려면 카메라 배율이 같아야 한다

`orthographicSize`가 다르면 임계값을 넘는 바깥 픽셀 수가 달라져 **잰 폭이 통째로 어긋난다.**
한 번 이것 때문에 배수를 반대 방향으로 잡았다(줄여야 한다고 판단했는데 실제로는 키워야 했다).

### 3-7. 병합한 자식은 배수를 다시 잡아야 한다

다른 원본에서 자식을 가져오면 authoring 기준이 달라 그대로는 안 맞는다.

- 얼음: `Crack_BlueShock`의 파열에 ×2.6, `Crack_Blue02`의 줄기에 ×25
- 화염: `Crack_Risingfire`의 `Flash`는 루트 0.11 기준이라 루트 0.84인 쪽에 얹으니
  유효 크기가 36까지 뛰었다 → ×0.13

### 3-8. `RotatesImpactToTravelDirection`은 지면 이펙트에서 꺼야 한다

기본값이 `true`다. 화살·총알처럼 튀는 방향이 있는 임팩트에는 켜야 하지만,
**지면에 깔리는 이펙트는 꺼야 한다** — 켜 두면 아래로 쏜 발사체가 맞았을 때
균열과 솟는 석영까지 뒤집혀 땅을 향한다.

Ice·StoneMeteor·Fire가 `false`다.

### 3-9. 지속 연출은 상태 지속시간 안에 완성돼야 한다 ★

명중 이펙트와 지속 연출은 요구가 정반대다.
명중은 "0.06초에 최대"가 목표지만(3-5), 지속 연출은 **상태가 끝나기 전에 완성 형태에 도달**해야 한다.

`FX_Status_FireBurn`을 화상(3초)에 붙였더니 이런 그림이 나왔다.

| 시점 | 그려진 픽셀(최대 대비) |
|---|---|
| 0.15초 (걸린 순간) | 22% |
| 1초 | 38% |
| 3초 (화상 종료) | 86% |
| 4초 (포화) | 100% |

**가장 알려야 할 첫 1초가 가장 흐리고, 다 타올랐을 때는 이미 끝나 있다.**
화면에서는 "몬스터가 뭔가에 걸렸다"가 아니라 "뭔가 점점 커지다 사라진다"로 읽힌다.

원인이 두 겹이라 한 값만 고치면 안 된다.

- **누적**: 연속 방출이라 입자가 쌓이는 데 시간이 걸린다 → **방출률**을 올려야 한다
- **알파 곡선**: `(0,0)(0.29,0.93)(1,0)` — 각 입자가 **자기 수명의 29%**가 지나야 최대 밝기다.
  수명 5초면 1.45초 뒤, 1.25초면 0.36초 뒤 → **수명**을 줄여야 한다

수명만 줄이면 변동폭은 잡히지만(66%p → 33%p) **초반 밝기는 거의 안 오른다**(34% → 31%).
초반 밝기를 정하는 것은 그 순간까지 쌓인 입자 수, 즉 방출률이기 때문이다.

채택값: **수명 ×0.25, 방출 ×4** (0.15초 52%, 포화 1.5초, 3초까지 변동 16%p)

### 3-10. `MinMaxCurve.constant`는 `constantMax`의 별칭이다 ★

배수를 걸 때 이렇게 쓰면 **제곱으로 걸린다.**

```csharp
rate.constant *= scale;      // constantMax에 쓴다
rate.constantMin *= scale;
rate.constantMax *= scale;   // 방금 곱한 값에 또 곱한다
```

방출률 13에 ×4를 걸었더니 52가 아니라 **208**(=13×16)이 나왔다.
같은 버그가 측정 스크립트에도 있어서 비교표의 `×3`·`×4`가 실제로는 9배·16배였다.

모드를 보고 해당하는 쪽만 건드린다.

```csharp
if (rate.mode == ParticleSystemCurveMode.TwoConstants)
{
    rate.constantMin *= scale;
    rate.constantMax *= scale;
}
else
{
    rate.constant *= scale;
}
```

### 3-11. 픽셀을 잴 때는 씬이 프레임에 섞이지 않게 한다

연출만 렌더한다고 생각했는데 배경 타일과 성이 함께 찍혀 **모든 프레임이 65536픽셀(=256×256) 포화**로
나왔다. 시간에 따른 변화가 전혀 안 보였다.

연출 인스턴스만 빈 레이어(31)로 옮기고 카메라 `cullingMask`를 그 레이어로 제한한다.
`Fire_A`처럼 `startSize`가 8인 자식이 있으면 `orthographicSize`도 넉넉히 잡아야 한다
(0.6은 프레임을 넘겨 역시 포화로 읽힌다).

## 4. 상태 지속 연출 (2026-08-24 추가)

명중 이펙트와 **보완 관계**다. 명중은 1회 사건이라 지속 구간을 못 그리고,
상태가 안 걸린 대상(속성 면역·군중제어 면역)에도 재생돼 거짓 신호가 된다.

### 데이터

프리팹 참조는 `StatusEffectSO`가 든다 — 몬스터가 아니라 **상태**가 자기 연출을 갖는다.
화상 불꽃은 탱크에 붙든 보스에 붙든 같은 불이고, `MonsterData`에 두면 34개 에셋을 채워야 한다.

```csharp
[WiringOptional] [SerializeField] private GameObject _activeVfxPrefab;
[SerializeField] private Vector2 _activeVfxOffset;
```

**비워 두는 것이 기본이다.** 어미용(`DS_*`)은 전역이거나 사거리가 넓어 화면의 모든 몬스터가
동시에 연출을 달게 되므로 채우지 않는다. `DS_FireBurn`·`DS_FireBurn_R2`는 지속시간 0(무한)이라
채우면 불 어미용 사거리 안 몬스터에 불이 상시 붙는다.

### 지금 배선된 것 (4/15)

| 상태 애셋 | 연출 | 지속 |
|---|---|---|
| `TS_FireBurn` | `FX_Status_FireBurn` | 3초 |
| `TS_IceSlow` | `FX_Status_IceSlow` | 2초 |
| `TS_BD_IceSlow` | `FX_Status_IceSlow` | 2초 |
| `TS_BD_IceFreeze` | `FX_Status_IceFreeze` | 3초 |

`FX_Status_IceSlow`는 `FX_Status_FireBurn`을 복사해 색만 바꾼 것이라 **3-9에서 맞춘 시간축을
그대로 물려받았다**(수명 1.25, 방출 40~80). 화상 쪽 타이밍을 다시 건드리면 둔화도 같이 맞춰야 한다.

`FX_Status_IceFreeze`는 별개 원본(rock 계열, 수명 1.3초·방출 200)인데 **0.15초에 이미 99%**로
지속 연출로는 이상적이다. 손댈 것이 없다.

새 상태를 추가할 때는 `_activeVfxPrefab`에 프리팹만 꽂으면 된다 — 코드 변경 0이다.
실제로 둔화·빙결 3개를 배선하는 동안 런타임 코드는 한 줄도 고치지 않았다.

### 런타임

| 파일 | 역할 |
|---|---|
| `MonsterStatusVfx` | 연출 인스턴스 관리. MonoBehaviour가 아니다 |
| `MonsterStatusReceiver` | 위를 소유. dirty 플래그로 변경 시점 수집 |
| `ProjectilePool.AcquirePersistent` / `ReleasePersistent` | 스스로 안 걷히는 연출용 |

설계 결정 세 가지와 이유:

- **몬스터의 자식으로 붙이지 않는다.** 풀 밑에 두고 `LateUpdate`에서 위치만 따라간다.
  루트 스케일이 0.1~1.5로 **15배** 갈려 있어 자식이면 맞춰 둔 크기가 몬스터마다 달라지고,
  사망이 `Destroy(gameObject)`라 자식 연출이 함께 파괴돼 풀 장부에서 인스턴스가 샌다.
- **키는 statusId가 아니라 프리팹이다.** statusId는 출처별로 갈리는데
  (`tower_fire_burn` / `baby_fire_burn` / `dragon_fire_burn`) 화면에 뜨는 불은 하나여야 한다.
- **MonoBehaviour로 만들지 않았다.** 몬스터 프리팹이 33종이고
  `[RequireComponent]`는 **이미 저장된 프리팹에 소급 적용되지 않는다.** 프리팹 배선이 0이다.

앵커는 몸통 중앙 고정이다. 발밑 얼음은 얼음 타워의 **명중** 이펙트가 이미 그린다.
위치는 `SpriteRenderer.bounds`(월드 AABB)로 푼다 — 크기 편차를 프리팹별 손배선 없이 흡수한다.
렌더러는 `Renderer`가 아니라 `SpriteRenderer`로 좁혀 찾는다(방어막·오버레이가 먼저 잡히면
손으로 확인하지 않은 몬스터에서만 연출이 엉뚱한 자리에 뜬다). 33종 전부 루트에서 잡히는 것을 확인했다.

**면역 검사를 연출 계층에 넣지 말 것.** 군중제어 면역은 `Apply`의 `IsImmuneTo`가,
속성 면역은 `BaseMonster.ApplyStatus`가 이미 거른다. 보관 중인 상태는 전부 통과한 것들이다.

### 검증된 것

부여·추종·재부여 중복 없음·만료 반납·사망 후 누수 없음. 몬스터 33종 앵커 정상.
`OnDisable`이 정리 지점이다 — 사망이 `Destroy`라 `Clear()`는 돌지 않는다
(`MonsterStatusReceiver.Clear()`는 지금 호출자가 0개다).

### 남은 것

- **몬스터 풀링을 도입하면** 재사용된 몬스터가 이전 개체의 상태를 물려받는다.
  대여/반납 시점에 `Clear()` 연결이 필요하다.
- `Projectile` 정렬 레이어는 `Building`보다 **나중에**(= 위에) 그려진다.
  TagManager 순서는 `Default → Building → Overlay → Projectile → Fog → Highlight`다.
  그래서 **뒤쪽 몬스터의 불이 앞쪽 몬스터를 덮는다** — 레이어 안에서 뎁스 정렬이 없기 때문이다.
  명중 이펙트도 같은 성질이지만 0.2~1.5초라 안 띄었고, 3초 루프에서 처음 문제가 된다.
  (예전 문장이 "Building보다 뒤에 그려져"로 돼 있어 가림 문제로 오독되기 쉬웠다. 가림이 아니다.)
- `TS_BD_IceFreeze`가 이름과 달리 `FreezeStatusSO`가 아니라 `MoveSpeedStatusSO`(배율 0)다.
  새끼용 3스택 결과가 `IsActionBlocked`를 안 켜서 **이동만 멈추고 공격은 계속한다.**
  `DragonSkillTreeAssetGenerator.cs:399-401`이 이 함정을 경고하고 있다. 별건으로 팀 확인 필요.
  (연출은 화면에서 멈추는 것이 사실이므로 빙결 프리팹을 붙였다 — 타입을 고치면 연출은 그대로 맞는다.)
- **`MP_Ground_ElementImmune_Stone`은 루트 스케일 0.1로 33종 중 유일한 극단값이다.**
  다른 몬스터의 1/10 크기라 어떤 상태 연출도 몬스터를 통째로 덮는다(폭 비율 1.00).
  연출을 줄일 문제가 아니라 그 프리팹의 스케일을 봐야 한다.
- **빙결 결정이 몸통 중앙이 아니라 아래쪽에 몰린다.** 프리팹 내부 오프셋 때문이며,
  `TS_BD_IceFreeze._activeVfxOffset`의 y를 올리면 코드 없이 맞출 수 있다.

## 5. 근거리 트레이서 — 만들었다가 제거함 (2026-08-24 ~ 08-25) ★

**결론: 시스템은 제거됐다.** 코드·SO·프리팹·머티리얼 전부 없다.
되살리려면 커밋 `925247a2`(메인) / Imported 이력에서 꺼내면 된다.

### 무엇이었나

머스킷 타워가 근거리에서 투사체가 안 보인다는 지적으로 시작했다.
명중 직후 0.1초간 `LineRenderer` 두 겹(코어+글로우)으로 발사점→명중점을 그어
"방금 뭔가 지나갔다"를 읽히게 하는 보조 연출이었다.

### 왜 제거했나 — 원인을 다른 방식으로 없앴다

트레이서는 **증상을 덮는 처방**이었다. 진짜 원인은 머스킷 발사체가
`ShellQuad2`(회전하는 사각 쿼드) + `Noise34cg`(어두운 노이즈)라 **형태도 밝기도 없었던** 것이다.

| | t=0.15초 그려진 픽셀 |
|---|---|
| 옛 머스킷(`Musket_Orange`) | 7,711 |
| 화살(`Conus` + `Flare3cg`) | 37,724 ← **5배** |

발사체를 `Cannonball_Core` + `Trail_Smoke`(현재 `Projectile_Tower_Musket_Heavy`)로 바꿔
**원인 자체를 없애자 트레이서가 필요 없어졌다.**

플레이 확인에서 "다른 타워는 트레이서 없이도 잘 보인다"가 확인돼 7종 → 머스킷 전용 →
전면 제거로 좁혀졌다. 남겨 두면 발사체 프리팹마다 인스펙터에 필드 4개가 뜨고
읽을 이유 없는 코드 250줄이 남는다.

### 남길 만한 교훈 ★

**① 적용 범위를 재지 않았다.** 진단·측정·구현은 맞았지만 "공격 투사체 타워 7종"으로
넓힌 근거가 없었다. 측정은 "트레이서가 얼마나 그려지나"를 쟀지
**"없으면 안 보이나"를 잰 적이 없다.** 한 타워의 문제를 고칠 때 같은 성질의 타워로
일반화하기 전에, 그 타워들에 정말 문제가 있는지 먼저 재야 한다.

**② 배수를 어디에 거는지가 결과를 가른다.** 강도를 폭에도 걸었더니 낮은 강도에서
선이 서브픽셀이 되어 **통째로 사라졌다**(강도 0.10 → 0픽셀). 알파에만 걸어야 했다.
3-10과 같은 함정이다.

**③ 아이소메트릭에서 상방 사격은 횡의 1/2.5로 짧다.** 원인이 둘이다 —
사거리 타원(`RADIUS_Y_RATIO 0.5`)에 **FirePoint 높이 0.41 월드가 겹친다.**
사거리 판정은 `transform.position` 기준인데 발사는 `_firePoint.position` 기준이라
상방 0~0.41 구간에 데드밴드도 생긴다. **연출을 상방 기준으로 맞출 일이 또 생기면 이 수치를 볼 것.**

**④ `ProjectileImpactPlacement.Ground`는 종점 y를 발밑으로 내린다.**
상방 근거리에서는 종점이 발사점보다 아래로 와 **선의 부호가 뒤집힌다.**
지면형 임팩트를 쓰는 타워(Fire·Ice·StoneMeteor)에서 방향을 쓰는 연출을 할 때 주의.

**⑤ 정렬 레이어 순서**: `Default → Building → Overlay → Projectile → Fog → Highlight`.
Projectile은 Building **위에** 그려진다. 투사체 연출이 안 보이면 가림은 원인이 아니다.

### 측정 도구는 삭제했다

`MeasureNearTracerCases` · `MeasureNearTracerRamp` · `VerifyNearTracerV2` ·
`VerifyStoneTracerExclusion` · `WireNearTracerTuning` 등 트레이서 전용 도구는 함께 지웠다.
렌더 산출물은 `output/vfx_check/near_tracer_*`에 남아 있다.

## 6. 도구

전부 `CoplayScripts/` 아래에 있고 Coplay MCP `execute_script`로 실행한다.
`Assets/` 밖이라 유니티가 컴파일하지 않고 `MenuItem`도 없어서 **에디터에서 직접 호출할 수 없다.**

| `MeasureImpactChildren` | 자식 하나씩 렌더해 크기·픽셀 측정 |
| `RenderProjectileTrails` | 발사체를 실제로 날리며 궤적 측정 |
| `RenderImpactAlign` | 여러 임팩트를 같은 시트에 굽고 스폰 높이 기준 정렬 확인 |

| `MeasureStatusVfxRamp` | 지속 연출의 시간대별 입자 수 (개수는 참고용, 판정은 픽셀로) |

| `ApplyStatusVfxTiming` | 고른 배수를 프리팹에 적용 |
| `RenderStatusVfxOnMonster` | 연출을 실제 몬스터 위에 얹어 굽고 몬스터 대비 폭 비율 측정 |

렌더 결과는 `output/vfx_check/`에 쌓아 둔다. **대부분 커밋되지 않은 상태다** —
`git ls-files output`이 2개만 돌려준다. 재현이 필요하면 위 스크립트를 다시 돌리는 것이 전제다.

**덮어쓰기 전에 반드시 백업한다.** 기본 진입점은 이미 있는 산출물을 건너뛰고,
`Rebuild`/`RebuildAll`은 프로젝트 루트 `VfxBackup/<시각>/`에 사본을 남긴다(`.meta`까지 — GUID가 거기 있다).
