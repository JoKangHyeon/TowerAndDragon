# 타워 투사체 연출 마일스톤 (2026-08-20 ~)

> 설계 근거: [타워 투사체 연출 설계](./타워_투사체_연출_설계.md) — 왜 이렇게 하는지는 그쪽을 본다.
> 이 문서는 **구현 진행표**다. 설계가 바뀌면 설계 문서를 먼저 고치고 여기에 반영한다.

## 이 문서를 처음 여는 에이전트에게

작업이 중간에 끊겨도 이어받을 수 있게 쓴 문서다. 순서대로 한다.

1. **[진행 현황](#진행-현황) 표에서 상태가 `⬜ 대기`인 첫 마일스톤**을 찾는다
2. 그 마일스톤의 **선행 조건**을 [현재 상태 확인 명령](#현재-상태-확인-명령)으로 직접 검증한다
   — 표의 상태를 믿지 말고 명령 결과를 믿는다. 이전 작업자가 표를 갱신 못 하고 끊겼을 수 있다
3. **완료 판정** 항목을 전부 만족시키고, 표의 상태와 해당 절의 작업 로그를 갱신한다
4. 다음 마일스톤으로 넘어간다

## 왜 쪼갰나

한 번에 갈아엎으면 중간에 플레이가 안 되는 구간이 길어진다.
**마일스톤 하나 = 컴파일 에러 0 + 플레이 모드 진입 가능 + 밤 전투 정상**으로 끊는다.

특히 M2(풀 도입)와 M3(호출자 이관)은 **한 세트로 끝내야 한다.** 사이에서 멈추면 몬스터 투사체가 반납 대상을 못 찾아 밤 웨이브가 깨진다. 자세한 건 M3의 경고 참조.

## 작업 원칙

- **커밋은 하지 않는다.** 변경분을 정리해 보고하고 커밋은 담당자가 직접 한다
- `Assets/Imported/Hovl Studio/` 아래 임포트 원본은 수정하지 않는다. 외부 VFX를 가공한 타워용 복제본은
  `Assets/Imported/Prefabs/Projectile/Tower/`에 따로 만든다
- 씬·프리팹은 Coplay MCP로 다루고, **플레이 모드가 켜진 상태에서 코드를 고치지 않는다**
- 리터럴 상수 금지 · 지연은 `UniTask` (CLAUDE.md 커밋 규칙 4·비동기 규칙)
- Coplay의 생성형 기능(3D·텍스처·이미지·음악·SFX 생성)은 사용 금지

## 환경

- Unity `6000.3.15f1` · URP `17.3.0` · UniTask 설치됨
- `ObjectPool<T>`는 `UnityEngine.Pool` 네임스페이스 (Unity 표준, 별도 패키지 불필요)

## M2 — 풀 진입점 (✅ 완료)

**목표**: 투사체·명중 이펙트를 프리팹별로 재사용하는 풀을 붙인다.

### ⚠️ 계획과 달라진 점 — 새 통을 만들지 않았다

원래 계획은 `Assets/Scripts/Util/PrefabPool.cs`를 **신설**하는 것이었다.
그런데 **이미 있었다.** `PrefabPool<T>`는 프리팹별 획득/반납 풀에 `Prewarm`·`Forget`까지 갖춘
완성된 클래스이고, `VillagerDispatchSystem`이 `PrefabPool<Villager>` + `PrefabPool<Transform>`으로
주민과 이펙트를 이미 이렇게 풀링하고 있다.

그래서 통은 그대로 쓰고 **정적 진입점만** 새로 만들었다.

| 파일 | 역할 |
|---|---|
| `Assets/Scripts/Util/PrefabPool.cs` | **기존.** 손대지 않았다 |
| `Assets/Scripts/Combat/ProjectilePool.cs` | **신규.** `PrefabPool<T>` 두 개를 들고 정적으로 열어 준다 |
| `Assets/Scripts/Util/ParticleRewind.cs` | **신규.** 파티클 되감기·정리. 아래 참조 |

`ComponentPool<T>`(인덱스형)은 쓰지 않는다 — 매 갱신마다 앞쪽 N개만 쓰고 뒤를 끄는 방식이라
개체마다 수명이 다른 투사체에는 맞지 않는다. `PrefabPool`의 주석이 이 구분을 이미 설명한다.

### 씬에 놓지 않는다 — 첫 사용 시 자동 생성

`SoundManager`처럼 정적 접근점을 두지만, **씬 오브젝트를 요구하지 않는다.**
SoundManager는 카탈로그·믹서 그룹을 인스펙터에서 받아야 하지만 이 풀은 받을 것이 없다.

배선을 요구하지 않으면 배선을 빠뜨릴 수도 없고(튜토리얼 씬 배선 누락 이력),
**"풀이 없는 씬"이라는 두 번째 경로가 사라져** 어느 씬에서든 같은 코드가 돈다.
그래서 `Destroy`도 fail-open 분기도 없다.

활성 씬에 만들므로 씬 언로드와 함께 사라진다(`DontDestroyOnLoad`를 쓰지 않는다) —
남겨 두면 이전 씬의 투사체가 파괴된 타겟을 문 채로 다음 씬까지 따라온다.

### `ParticleRewind` — 되감기 지식을 한 곳에

풀에서 꺼낸 파티클은 **꺼낼 때 되감고 넣을 때 지워야** 한다. 한쪽만 하면 잔상이 남는다.

`VillagerDispatchSystem`이 이미 이 처리를 하고 있었고 그 주석이
*"남아 있던 파티클을 지우지 않으면 다음에 꺼내 쓸 때 이전 자리의 잔상이 한 프레임 비친다"* 라고
적어 두었다 — 설계 문서 §9에서 Clear를 강조한 이유가 **이미 겪은 문제**라는 뜻이다.

같은 것을 투사체에도 써야 해서 `ParticleRewind.PlayFromStart` / `StopAndClear`로 뽑고,
`VillagerDispatchSystem`의 두 메서드도 그것을 부르도록 바꿨다(동작 동일, 복사본 제거).

### 프리워밍

`ProjectilePool.Prewarm(prefab, count)` 정적 메서드로 열어 뒀다. **아직 부르는 곳은 없다** — M8에서
필요한 씬에만 붙인다. 부르지 않아도 동작은 같고, 첫 발사에서 Instantiate 비용이 몰릴 뿐이다.

### 완료 판정

- [x] 컴파일 에러 0 (`Assembly-CSharp.dll` 재빌드 확인)
- [x] 플레이 진입 + 밤 전투 정상 (2026-08-20 확인: 로그 없음, ProjectilePool 자동 생성 확인)

### 작업 로그

- 2026-08-20: `PrefabPool<T>`가 이미 있어 신설하지 않고 재사용. 진입점 `ProjectilePool`만 추가
- 씬 배선 요구를 없애기 위해 자동 생성 방식 채택 → fail-open 분기와 `Destroy` 전부 제거
- `ParticleRewind` 신설, `VillagerDispatchSystem`의 중복 로직 제거

## M3 — Projectile 이관 (M2와 한 세트)

**목표**: `Projectile`을 풀 기반으로 바꾸고, 호출자를 **동시에** 전부 옮긴다.

### 선행 조건

- M2 완료 (`Assets/Scripts/Util/PrefabPool.cs` 존재)

### ⚠️ 반쪽으로 끝내면 안 된다

`Projectile`이 풀로 반납하기 시작하는 순간, 아직 `Instantiate`로 만들어진 몬스터 투사체는 반납 대상을 못 찾는다.
**밤 웨이브에서 원거리 몬스터가 쏘는 순간 터진다.**

이 마일스톤은 아래 3개 파일을 **한 번에** 고치고 한 번에 검증한다.

| 파일 | 할 일 |
|---|---|
| `Assets/Scripts/Combat/Projectile.cs` | 반납 경로 + `ResetState` + 훅 2개 + **진행 방향 회전** |
| `Assets/Scripts/Buildings/Tower/TowerAttack.cs` | `LaunchProjectile` → `PrefabPool.Spawn` |
| `Assets/Scripts/Monster/MonsterAttack.cs` (`:251`) | 같은 변경 |

새끼용은 `TowerAttack`을 공유하므로 자동 반영된다.

### 작업

**`Projectile.cs`**

- 스폰/반납을 `PrefabPool` 경유로 통일. 반납은 스폰 시 주입받은 경로로만
  — 자기 풀이 아닌 곳에 반납하는 사고를 구조적으로 막는다
- `ResetState()` 추가: `_isLaunched` · `_target` · `_targetObject` · `_targetTransform` · `_lastTargetPosition` 초기화
  > 현재 `_isLaunched`는 한 번 true가 되면 false로 안 돌아간다. 이대로 재사용하면 두 번째 발사가 깨진다
- `Launch`의 실패 조기 반환 3곳(target null / attack null / speed ≤ 0, 타겟 오브젝트 null)을
  `Destroy` → **반납**으로 바꾼다
- 훅 2개 추가. 대상 컴포넌트(`ProjectileVisual`)는 M4에서 만들므로 **여기서는 호출 지점만 비워 둔다**
  (또는 M4를 먼저 하고 와도 된다 — 두 마일스톤은 순서를 바꿔도 무방)
  - `OnLaunched()` — `Launch` 성공 직후
  - `OnHit(Vector3 hitPosition, Vector3 direction)` — `ApplyHit` 직후, 반납 직전.
    `direction`은 명중 시점의 진행 방향

### ⚠️ 진행 방향 회전 (필수 요구사항)

**투사체와 이펙트가 적이 있는 방향을 향해야 한다.** 설계 문서 §5 참조.
지금 `Projectile`은 회전을 전혀 하지 않으므로 여기서 넣는다.

```csharp
// Z축 단일 회전. 우리 게임은 2D 아이소메트릭이다
float angle = Mathf.Atan2(direction.y, direction.x) * Mathf.Rad2Deg;
transform.rotation = Quaternion.Euler(0f, 0f, angle);
```

- `Launch` 시점에 한 번 잡는다. **추적 투사체이므로 이동 중에도 갱신할지는 M5 파일럿에서 눈으로 보고 정한다**
  (타겟이 움직이면 `_lastTargetPosition`이 바뀌어 실제 진행 방향이 달라진다)
- **아이소메트릭 타원 보정은 넣지 않는다.** `MoveTowards`가 월드 좌표에서 직선으로 가므로
  화면에서도 직선이고, 그 각도가 곧 보이는 각도다. `RADIUS_Y_RATIO` 보정을 넣으면 궤적과 어긋난다
### 회전 대상은 "날아가는 투사체"뿐이다

`Projectile.cs`에 넣는 회전이므로 **투사체 오브젝트만** 돈다.
타워·새끼용 **본체는 건드리지 않는다.** 본체 방향은 이미 다른 메커니즘이 담당한다:

| 대상 | 방향 처리 | 담당 | 이번 작업 영향 |
|---|---|---|---|
| 타워·새끼용 본체 스프라이트 | `flipX` (좌/우 2단계) | `TowerAttack.Update` (`_aimingSprite`) | 없음 |
| 새끼용 `AimLight` | Z축 회전 (`Atan2`) | `TowerLightAimer` | 없음 |
| **투사체** | 없음 → 여기서 추가 | `Projectile` | **있음** |

- **다만 옛 프리팹을 쓰는 투사체(새끼용·몬스터)도 같이 회전한다.**
  연출은 범위 밖이라 프리팹은 `Projectile_Fire` 등 그대로인데, 그 스프라이트가 회전에 안 맞게
  그려져 있으면(원형이 아니라 특정 방향으로 그려진 경우) 이상해질 수 있다.
  어색하면 회전 적용 여부를 프리팹 단위로 끌 수 있게 한다 (`ProjectileVisual` 유무로 가르는 방법도 가능)

**`TowerAttack.cs` / `MonsterAttack.cs`**

- `Instantiate(...)` + `GetComponent<Projectile>()` + 에러 로그 블록을 `PrefabPool.Spawn`으로 교체
- 프리팹 검증(`Projectile` 유무)은 풀 생성 시 1회로 옮긴다 — 발사마다 `GetComponent`를 타지 않는다

### ⚠️ 필드 타입을 바꾸지 않는다

`TowerData._projectilePrefab` · `MonsterData._projectilePrefab`은 **`GameObject`로 유지한다.**
`Projectile`로 바꾸면 YAML의 fileID가 안 맞아 **참조 18개가 조용히 null이 된다.**
에러도 안 나고 그냥 투사체가 안 나간다.

### 작업

`Assets/Scripts/Combat/ProjectileVisual.cs`

```csharp
[SerializeField] private ParticleSystem[] _trailParticles;
[WiringOptional]
[SerializeField] private GameObject _impactPrefab;
[SerializeField] private float _impactLifetimeSeconds = DEFAULT_IMPACT_LIFETIME_SECONDS;
```

- **`OnLaunched()`**: `Clear(withChildren: true)` **후** `Play(true)`
  > Clear를 빼면 world-space 파티클이 재사용 시 직전 명중 지점에서 새 발사 지점까지 줄을 긋는다.

- **`OnHit(hitPosition, direction)`**: `Stop(true, ParticleSystemStopBehavior.StopEmittingAndClear)`
  → 명중 이펙트를 **진행 방향 각도로** 스폰
  > `Hit *` 프리팹도 방향성이 있는 것이 섞여 있다 (폭발형은 무관, 튀는 형태는 유관).

- `_impactPrefab`이 `[WiringOptional]`이라 비어 있어도 조용히 생략된다

### ⚠️ 궤적 자식을 detach하지 않는다

에셋의 `HS_ProjectileMover2D`는 명중 시 자식을 unparent해서 파티클을 마저 재생시킨다.
**그러면 풀이 자식 하나가 사라진 오브젝트를 돌려받는다.**
"명중 후에도 남는 연출"은 궤적 잔상이 아니라 **별도 명중 이펙트**가 담당한다 —
`VillagerDispatchSystem`의 `_conquestCompletionEffectPrefab` + `_conquestCompletionEffectLifetimeSeconds`와 같은 구조다.

## M5 — 파일럿 (Fire) · **Vol1 vs Vol2 비교 선택**

**목표**: Fire 하나를 **Vol1판·Vol2판 둘 다** 만들어 아이소 씬에서 나란히 보고 고른다.
여기서 고른 팩과 확정한 절차를 M6에서 반복한다.

Fire를 고른 이유: 이미 전용 프리팹(`Projectile_Fire`)을 쓰고 있어 공용 프리팹 분리 문제가 섞이지 않는다.

### 선행 조건

- M1(에셋) · M4(`ProjectileVisual`) 완료

### 왜 비교하나

문서로는 결론이 안 난다. 남은 쟁점이 **"3D Mesh 파티클이 아이소 직교 카메라에서 어떻게 보이는가"** 하나인데,
이건 화면으로만 판단된다. 확인된 사실은 이렇다.

| | Vol1 `2D Projectile 16 fire` | Vol2 `Projectile 4 fire` |
|---|---|---|
| ParticleSystem 수 | 3 | 5 (+ Flash·Hit 중첩 프리팹) |
| **Mesh 파티클** | **0** | **2** (`Conus.fbx` 등 참조) |
| 물리 컴포넌트 | `Rigidbody2D` · `CircleCollider2D` | `Rigidbody` · `SphereCollider` (3D) |
| 조명 | 없음 | `Light` (3D) |
| 무버 스크립트 | `HS_ProjectileMover2D` | `HS_ProjectileMover` |
| 구조 | 투사체만 | **발사·투사체·명중 번들** |

> **파티클은 양쪽 다 정상으로 보인다.** 머티리얼이 `HS_Blend_CG.shadergraph`(URP Shader Graph)라
> `Renderer2D`에서도 렌더된다. 프리팹 미리보기에서 보이는 것이 맞다.
>
> 3D `Light`만 `Renderer2D`에서 무시되는데, **파티클이 아니라 부가 조명**이라 없어도 그림은 그대로다.
> `Rigidbody`/`SphereCollider`는 무버 스크립트를 떼면 아무 일도 안 하므로 그냥 제거하면 된다.
>
> 카메라 확인: `SampleScene`은 `orthographic: 1`, 렌더러는 `Assets/Settings/Renderer2D.asset`.

**Vol2의 번들 구조는 이점이 되지 못한다.** `hit`/`flash`/`Detached` 배선이 전부
`HS_ProjectileMover`의 필드에만 있는데, 그 스크립트는 `OnCollisionEnter`(3D 물리) 명중 판정 +
`rb.linearVelocity` 직진 이동이라 우리 `Projectile`과 못 쓴다.
**스크립트를 떼는 순간 배선도 같이 날아가고**, `ProjectileVisual`에 다시 잡아야 한다 — Vol1과 같은 작업량이다.
그래서 이 비교의 기준은 **작업량이 아니라 "아이소 화면에서 어느 쪽이 나은가"** 하나다.

### 작업

1. `Assets/Prefabs/Projectile/` 폴더 신설

2. **Vol1판** 만들기 — `Projectile_Fire_V1` (임시 이름)
   - 원본: `Assets/Imported/Hovl Studio/AAA Projectiles Vol 1/Prefabs/Projectiles 2D/2D Projectile 16 fire.prefab`

   - `_trailParticles` 배선 (본체 + `SubSmoke` + `SubSparks` 3개)

### ⚠️ 발사 방향 — 여기서 축을 맞춘다

M3에서 `Projectile`이 Z축 회전을 하도록 만들었지만, **프리팹 쪽 축이 3D 전제라 그대로는 안 맞는다.**

Vol1 `2D Projectile 16 fire`를 뜯어본 결과:

- 자식에 **Y축 90° 회전이 구워져 있다** (`m_LocalRotation: {y: 0.7071, w: 0.7071}`)
- 메인 파티클이 **Cone 이미터**(`type: 5`, `angle: 25`)라 **로컬 +Z 방향**으로 뿜는다
- 에셋 readme 명시: *"Projectile should face forward in the Z direction for correct movement."*

우리는 Z축 회전(`Atan2` 기준 **0° = +X**)을 쓰므로, 프리팹에서 **파티클 방출이 로컬 +X를 향하도록** 맞춰야 한다.
**Vol2도 같은 3D 전제라 같은 보정이 필요하다.**

**작업**:
1. 자식에 구워진 Y축 90° 회전을 걷어낸다
2. Cone 이미터 방향을 +X로 맞춘다
3. `ParticleSystemRenderer`의 Stretched Billboard 정렬을 확인한다
4. **타워 기준 동서남북 네 방향**에 몬스터가 왔을 때 각각 눈으로 확인한다.
   한 방향만 보면 축이 뒤집혀 있어도 모른다

**여기서 확정한 축 보정 절차를 아래 로그에 적고, M6에서 그대로 반복한다.**

### 정렬(Sorting) — 여기서 반드시 잡는다

**M5에서 정한 Sorting Layer/Order 값을 아래 로그에 적어두고, M6에서 그대로 쓴다.**

**2-1. ⚠️ `Flash *` · `Hit *` 복제본에서도 Hovl 스크립트를 걷어낸다 — 풀을 깨뜨린다**

`Flash *` 프리팹에는 **`HS_CallBackParent`가 붙어 있고, 파티클의 `Stop Action`이 `Callback`으로**
설정돼 있다. 그 스크립트는 파티클이 끝나면 이렇게 한다:

```csharp
protected virtual void OnParticleSystemStopped()
{
    if (parentObject != null) { /* 원래 부모로 복귀 */ }
    else
        Destroy(gameObject);   // ← parentObject가 비어 있으면 자기를 파괴한다
}
```

`parentObject`가 비어 있으므로 **재생이 끝나는 순간 풀이 재사용해야 할 인스턴스를 파괴한다.**
증상이 조용하다 — 에러도 안 나고, 몇 발 뒤부터 발사 이펙트만 안 나온다.

- `HS_CallBackParent` 컴포넌트 **제거**
- 그 파티클의 `Stop Action`을 `Callback` → **`None`으로** (콜백을 받을 스크립트가 없어졌다)
- `Hit *` 쪽에는 없었지만 복제할 때마다 확인한다

한 번에 확인하는 방법:

```bash
grep -c '15f64663d9bea784b8060d7fbcdc2b23' <프리팹>   # HS_CallBackParent (0이어야 함)
grep -c 'stopAction: 3' <프리팹>                      # Callback (0이어야 함)
```

**5. ⚠️ Sorting Layer를 `Projectile`로 — 빠뜨리기 쉽다**

임포트한 프리팹의 렌더러는 전부 `Default`(0)로 되어 있다. 그대로 두면 아이소 뎁스에서
**파티클이 타일·건물 뒤로 숨는다.**

- 복제본 3개(투사체·명중·발사) **모두**, **자식 렌더러 하나하나** 다 바꿔야 한다
- 인스펙터: 각 `ParticleSystem`의 `Renderer` 섹션을 펼쳐 `Sorting Layer` → `Projectile`
- 개수가 만만치 않다 — M5 기준: 투사체 3~5개, 명중 5~8개, 발사 3~6개. **한 타워당 11~19개**

YAML로 한 번에 바꿀 수도 있다(M5에서 이렇게 했다):

```bash
sed -i 's/^  m_SortingLayerID: 0$/  m_SortingLayerID: 1811136797/' <프리팹>
sed -i 's/^  m_SortingLayer: 0$/  m_SortingLayer: 3/' <프리팹>
```

`1811136797`은 `Projectile` 레이어의 uniqueID, `3`은 그 목록에서의 인덱스다
(`ProjectSettings/TagManager.asset` 기준: Default 0 · Building 1 · Overlay 2 · **Projectile 3** ·
Fog 4 · Highlight 5). 두 값은 **반드시 짝으로** 바꾼다 — `Villager_05.prefab`이 같은 쌍을 쓴다.

- **화살 3종(Arrow·CrossBow·Musket)이 서로 구분되는지** — 색만 다르면 밤에는 구분이 안 된다.
  크기·궤적 길이로도 차이를 준다. Musket은 "둔탁한 총알"이라 화살 계열을 피하는 편이 낫다
- **Stone은 속도가 5**(다른 타워의 절반)다. Hovl readme 4.1:
  *"속도를 줄이면 파티클의 Trail 탭에서 trail lifetime을 늘려야 하고, 모든 파티클 컴포넌트의
  Duration과 Lifetime도 늘려야 한다."* 안 하면 느리게 나는 동안 궤적이 끊긴다
- **Anti_Air는 `TargetMovementFilter`가 대공 전용**이다. 공중 몬스터가 나오는 웨이브에서 확인해야 한다
- **Vol1 궤적은 `Rate over Time`이 0이고 `Rate over Distance`만 있다** — 즉 **움직여야 파티클이 나온다.**
  씬에 세워두고 보면 아무것도 안 나오는 게 정상이다. 반드시 발사시켜서 확인한다
- **Hit 프리팹은 `ParticleSystem`이 5개짜리도 있다.** 아이소 타일 위에서 과하면 자식을 덜어낸다

## M7 — TimeTower 마법진 (신규, 2026-08-20 추가)

**목표**: 버프 타워인 TimeTower에 **마법진** 연출을 붙인다.

### 선행 조건

- M6 완료

### ⚠️ 이건 투사체가 아니다

TimeTower는 **공격을 하지 않는다.** `TD_TimeTower.asset`을 확인한 결과:

```yaml
_attack: {fileID: 0}          # 공격 데이터 없음 → CanAttack == false
_projectilePrefab: {fileID: 0}
_projectileSpeed: 0
_towerAura: TAD_TimeTowerAura  # 반경 2, 공속 ×1.2, 부활속도 ×1.2
```

즉 `TowerAttack`이 아예 돌지 않으므로 **`Projectile`·`ProjectileVisual`·`PrefabPool`과 무관하다.**
M2~M6에서 만든 것 중 어느 것도 여기 쓰이지 않는다.

**필요한 것은 "타워 발밑에 상시 떠 있는 오라 표시"다.**

### 확인된 현재 상태

- `TowerAuraDataSO`는 **수치만** 들고 있다 (`_radius` · `_attackSpeedMultiplier` 등). 시각 필드 없음
- `TowerAuraSystem`도 `_gridMap` 참조뿐이고 렌더링을 하지 않는다
- 즉 **오라를 그리는 코드가 프로젝트에 전혀 없다.** 지금은 눈에 보이지 않는 버프다
- `TP_TimeTower.prefab`에는 `SpriteRenderer` 1개 + `BaseLight` · `AimLight` · `FirePoint`가 있다
  (`AimLight`·`FirePoint`는 공격 타워에서 복사된 흔적. TimeTower는 안 쓴다)

### 설계 판단이 필요하다

이건 M2~M6과 성격이 다른 작업이라 **접근을 먼저 정해야 한다.** 두 갈래다.

**A. 프리팹에 자식으로 붙인다 (간단)**
- `TP_TimeTower.prefab`에 마법진 파티클/스프라이트를 자식으로 추가
- 코드 변경 0. 인스펙터만으로 끝난다
- 단점: 반경이 `TAD_TimeTowerAura._radius`(2)와 **따로 논다.** 데이터에서 반경을 바꿔도 그림은 그대로다.
  `_scaleRadiusWithStaffing: 1`이라 **배치 인원에 따라 반경이 변하는데** 그것도 반영 안 된다

**B. 오라 시각화 컴포넌트를 만든다 (정합)**
- `TowerAuraDataSO`에 시각 필드 추가 (`_auraVisualPrefab` 등)
- `TowerAuraSystem` 또는 신규 컴포넌트가 반경에 맞춰 스케일을 맞춘다
- 장점: 반경과 그림이 항상 일치. 충원율에 따라 커지고 작아지는 것도 표현됨
- 단점: 코드 신설. **`ITowerAuraDataProvider`를 구현하는 다른 것들(새끼용 `BabyDragonData`)에도 영향**

> **권장: A로 시작한다.** 이번 작업의 목적은 "마법진이 보이게 하는 것"이고,
> 반경 정합은 별도 과제다. B가 필요해지면 그때 올린다.
> 단, A를 고르면 **반경이 데이터와 어긋난다는 사실을 이 문서에 남긴다.**

### 에셋 후보

마법진 = 바닥에 깔리는 원형. 투사체 팩에서는 **`Hit` 계열 중 원형으로 퍼지는 것**이 가깝다.

| 후보 | 출처 |
|---|---|
| `Hit 17 nova violet` / `Hit 18 nova orange` | Vol1 `Flash and hits/` — 원형 확산 |
| `Hit 19 circle bomb` | Vol1 — 이름 그대로 원형 |
| `Projectile 17 heal` | Vol2 — 힐 계열이라 버프 톤에 맞을 수 있다 |
| `Fx_Glow_01~03` / `Particle_Shines_Glow` | `Imported/Layer Lab/.../Prefabs_DemoScene_Particle/` |

> 마법진은 **상시 재생(loop)** 이라 투사체용 원샷 이펙트와 재생 설정이 다르다.
> `ParticleSystem.main.loop`을 켜고 `Duration`을 조정해야 한다.
> 명중 이펙트를 그대로 쓰면 한 번 터지고 사라진다.

### 정렬 — 바닥에 깔려야 한다

투사체와 반대 문제다. 마법진은 **타워와 유닛보다 뒤에** 그려져야 바닥에 깔린 것처럼 보인다.
M5에서 정한 투사체 Sorting Order보다 **낮은 값**을 쓴다.
아이소 타일 위에서 원이 눌려 보이도록 `IsometricMath.RADIUS_Y_RATIO`(0.5)만큼
**Y 스케일을 압축**하는 것을 검토한다 — 정원(正圓)이면 아이소 그리드에서 떠 보인다.

### 완료 판정

- [ ] 컴파일 에러 0
- [ ] TimeTower를 건설하면 발밑에 마법진이 상시 떠 있다
- [ ] 마법진이 타워·유닛보다 뒤에 그려진다 (바닥에 깔린 느낌)
- [ ] 아이소 그리드 위에서 원이 떠 보이지 않는다 (Y 압축 확인)
- [ ] 타워가 파괴/비활성화되면 마법진도 사라진다
- [ ] **A안을 골랐다면** 반경 불일치를 아래 로그에 명시했다
