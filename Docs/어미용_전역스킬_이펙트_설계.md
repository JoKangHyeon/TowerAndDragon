# 어미용 전역 스킬 이펙트 설계

어미용 스킬트리 액티브 4종(빙결·화염·타워수리·메테오)에 발동 연출을 붙이는 설계.
**지금은 4종 다 VFX가 0이거나(빙결만 절반) 게임플레이 로직뿐이다.**

선행 문서:
- `Docs/타워이펙트_작업노트.md` — 카메라 제약·색조·버스트 방출·발밑 앵커 등 이 프로젝트의 이펙트 함정 전부
- `Docs/버프타워_이펙트_설계.md` — 같은 팩·같은 기법을 쓰는 선행 사례, 문서 형식의 전례

작성: 2026-08-28

## 0. 범위와 결론 요약

`Skill.cs`의 5개 액티브 중 이 문서는 4개를 다룬다. **성 회복(HEAL_CASTLE)은 제외** — 단일 대상(성 1개)이라
"전역" 연출 문제(다수 동시 발동)가 없고, 기획 자체가 방벽의 임시 대체(§타워이펙트_작업노트 확인 대기)라
기획 확정 전까지 손대지 않는다.

| 스킬 | 대상 | A. 시전 연출 | B. 대상별 연출 |
|---|---|---|---|
| 빙결 (FREEZE_ALL) | 필드의 모든 몬스터 | 없음 → **신규** | **이미 있음** (`FX_Status_IceFreeze`, §2-1) |
| 화염 (GLOBAL_CURRENT_HEALTH_DAMAGE) | 필드의 모든 몬스터 | 없음 → **신규** | 없음 → **신규** (기존 상태 VFX 경로 못 씀, §2-2) |
| 타워수리 (REPAIR_TOWERS) | 파괴된 모든 타워 | 없음 → **신규** | 없음 → **신규** |
| 메테오 (METEOR_BARRICADE) | 지정 지점 광역 | 없음 → **신규** | 없음 → **신규** (§2-4, 대상이 몬스터+방벽 둘) |

빙결의 대상별 연출이 이미 있다는 걸 처음엔 놓쳤다 — `DS_IceFreeze`/`_R1`/`_R2` 세 상태이상 에셋
전부 `_activeVfxPrefab`이 `FX_Status_IceFreeze`로 채워져 있고, `FreezeAllSkill.ApplyEffect`가 부르는
`monster.ApplyStatus`는 타워가 건 상태이상과 완전히 같은 파이프라인(`MonsterStatusReceiver`)을 타므로
코드 0줄로 이미 동작한다. 남은 건 §4의 **N-동시발동 검증**뿐이다.

## 1. 두 계층 구조

버프 타워 설계와 같은 전제 — **"발동 순간에 항상 뜨는 것"과 "대상별로 뜨는 것"을 분리한다.**

- **A. 시전 연출**: 대상 수·성공 실패와 무관하게, 스킬이 실제로 효과를 낸 순간 **1회만** 뜬다.
  화면 어디를 보고 있어도 "어미용 스킬이 지금 발동했다"가 읽혀야 하는 몫.
- **B. 대상별 연출**: 스킬마다 실제로 영향을 받은 개체(몬스터/타워/방벽 설치 지점)에 뜬다.
  "무엇이 얼마나 영향을 받았는지"를 보여주는 몫.

두 계층 다 `ProjectilePool.PlayForSeconds(prefab, position, rotation, seconds)`로 스폰한다 — 이미 있는
1회성 버스트 경로라 새 풀링 코드가 필요 없다.

## 2. 스킬별 설계

### 2-1. 빙결 (FREEZE_ALL)

**B(대상별)는 이미 완료.** `FX_Status_IceFreeze`가 §타워이펙트_작업노트 4장에서 "0.15초에 이미
99% — 지속 연출로는 이상적, 손댈 것이 없다"고 검증까지 끝난 자산이다. `AppliedStatus`가
`FreezeStatusSO`라 지속시간이 유한하고(`ICE_FREEZE_DURATION`/`_R1`/`_R2`), 이 스킬에만 배선돼 있어
다른 경로에서 뜰 일이 없다.

**A(시전)만 신규.** 지금은 발동 순간 화면에 아무 신호가 없고, 몬스터들이 각자 얼어붙는 것만 보인다.
얼음 속성의 시전 연출은 §7에서 다른 3종과 함께 설계한다.

### 2-2. 화염 (GLOBAL_CURRENT_HEALTH_DAMAGE)

**B를 기존 상태 VFX 경로로 못 만든다 — 확인된 제약.** `AppliedStatus`가 가리키는 `DS_FireBurn`은
불 속성 각성 패시브(`DragonSpawnStatusEffectSO` — 몬스터가 스폰될 때 사거리 안이면 상시 화상을 건다)와
**같은 SO 하나를 공유한다.** 지속시간도 무한(`FIRE_BURN_DURATION_INFINITE`)이다.
`_activeVfxPrefab`을 채우면 스킬을 쓰지 않아도 몬스터가 스폰될 때마다 화면에 불이 상시로 뜬다
(§타워이펙트_작업노트 4장이 이미 이 이유로 비워두라고 못 박아 뒀다).

**대안**: `GlobalCurrentHealthDamageSkill.ApplyEffect`가 데미지를 준 몬스터 각각에 대해 **스킬 쪽에서
직접** 1회성 임팩트를 스폰한다(상태이상 시스템을 거치지 않음 — "화상이 걸려 있다"가 아니라 "지금 막
타격했다"는 신호이므로 오히려 명중 이펙트 성질에 더 맞다). 기존 `FX_Impact_FireCrack`을 축소·경량화한
버전을 새로 만든다(§4의 N-동시발동 때문에 원본 그대로는 못 씀).

### 2-3. 타워수리 (REPAIR_TOWERS)

상태이상 경로 자체가 없는 스킬이라 A·B 둘 다 신규다.

**B(대상별)**: `RepairTowersSkill.ApplyEffect`가 복구에 성공한 타워마다 "복구되며 빛이 차오르는" 연출을
직접 스폰한다. **`Building` 레이어는 뎁스 정렬이 있으므로**(`Overlay`와 다름 — §타워이펙트_작업노트 4장),
`tower.DepthSortOrder + 1`을 그대로 상속해야 한다(`TowerBuffOrbDisplay:199`와 같은 관용구).
`Overlay`로 올리면 오히려 정렬을 잃는다.

가용 자산 후보: 8-1절에서 이미 도입한 `VfxFlashLight` + `Light2D` 조합을 재사용해 "복구된 타워가
잠깐 밝게 빛난다"로 표현하면 새 파티클 자산 없이도 될 수 있다 — 프로토타입 단계에서 먼저 시도해 볼 것.

### 2-4. 메테오 (METEOR_BARRICADE)

`SK_Dragon_Meteor`: 고정 피해 40 · 광역 반경 1.5 · 하루 2회(유일하게 무제한이 아닌 액티브).
GroundPoint 타겟팅이라 이미 `RangeIndicator`로 조준 미리보기는 있다 — 이 문서가 다루는 건 **명중 순간**부터다.

지금 `ApplyEffect`는 데미지 적용 → `StoneBarricade` 인스턴스화를 **연출 없이** 순서대로 처리한다.
방벽이 화면에 아무 전조 없이 "짠" 하고 나타나는 상태.

**대상이 둘로 갈린다 — 몬스터(피해)와 방벽 설치 지점(구조물).**

- **A(시전)**: 낙하 궤적 + 착지 폭발. 이미 있는 `StoneMeteor` 타워의 자산(`FX_Impact_StoneCrack`,
  색조 280 보라 — §적_이펙트_연출_설계에서 이미 암석 속성 시그니처 색으로 굳어져 있다)을 그대로
  베이스로 삼아 **범위에 맞게 확대한 버전**을 만든다. 새 자산을 처음부터 만들 필요가 없다.
- **B-몬스터**: 광역 반경 1.5는 몬스터 수가 많아 봐야 한 자리 수라 §4의 N-cap 대상이 아니다.
  타격받은 몬스터 각각에 화염 계열이 아닌 **암석 계열** 경량 임팩트(§2-2와 같은 이유로 상태이상
  경로가 아니라 스킬에서 직접 스폰).
- **B-방벽**: 방벽이 완성되기 **직전**에 "땅이 솟아오르는" 짧은 마무리 플래시가 있어야
  구조물이 갑자기 나타나는 게 아니라 "떨어진 돌이 뭉쳐 방벽이 됐다"로 읽힌다. 착지 폭발(A)이
  가라앉는 타이밍과 겹치지 않게 살짝 늦게(약 0.1~0.2초) 넣는 걸 권장 — 정확한 값은 프로토타입에서
  픽셀 측정으로 잡는다(§타워이펙트_작업노트 3-9와 같은 종류의 타이밍 조정).

## 3. 시전 연출(A)의 공통 앵커 — 성(Castle)

어미용은 필드에 실체가 없다. `MotherDragonTypeOverlay`가 메인 성 위에 속성 아이콘으로만
표시되고, 별도의 월드 트랜스폼이 없다. 따라서 A계층의 자연스러운 앵커는 **성 위치**다 —
화면 어디를 보고 있어도 성은 항상 UI/카메라 기준에 가깝게 놓이므로 신호가 묻히지 않는다.

메테오만 예외 — 그 자체가 "지정 지점에 낙하"하는 스킬이라 A가 캐스트 지점(=대상 지점)과 같다.
나머지 3종(빙결·화염·타워수리)은 대상이 화면 전체/여러 곳에 흩어져 있으므로 성에서 터지는 게 맞다.

## 4. N-동시발동 문제

노트에 쌓인 모든 대상별 이펙트 교훈은 N=1(명중) 또는 N=소수(상태 트리클)에서 나왔다.
전역 스킬은 **한 프레임에 몬스터 20~30마리를 동시에** 건드릴 수 있다. `Projectile` 레이어는
뎁스 정렬이 없다는 게 이미 알려진 제약(§타워이펙트_작업노트 4장 — 3초 지속 연출에서도 문제였다)이라,
30개 동시 버스트면 그게 지배적인 시각 잡음이 된다.

**기본 방향: A(시전 연출)가 이미 "뭔가 크게 일어났다"를 전달하므로, B(대상별)는 가볍게 만들고
과도하면 자른다.**

- 빙결·화염 B는 원본 임팩트 세트를 그대로 쓰지 않고 파티클 수를 줄인 경량 버전으로 새로 만든다
- 화면에 동시 대상이 일정 수(예: 15마리, 정확한 값은 [미정] — 실측 필요)를 넘으면 초과분은 생략
- 타워수리도 같은 프레임에 여러 타워가 복구될 수 있어 같은 캡이 필요할 수 있다(밤 웨이브가 길게
  이어지면 파괴된 타워가 여러 개 쌓여 있을 수 있음 — 실측 필요)
- 지연 스폰(프레임 분산)은 1순위로 채택하지 않는다 — 빙결·화염 둘 다 "즉시 동시에 걸렸다"는 신호가
  스킬의 정체성이라, 늦게 뜨는 연출은 오히려 의미를 흐린다

**빙결은 B가 이미 구현돼 있어 이 문제를 가장 먼저, 가장 싸게 검증할 수 있다** — 새 자산 없이
플레이에서 몬스터 20마리 이상 있을 때 빙결을 눌러 보면 된다. §9 마일스톤의 0번째 항목으로 둔다.

## 5. 배선 지점 — `Skill.Activate`가 성공 여부를 못 돌려준다

```csharp
public void Activate(in SkillCastContext context)
{
    if (!CanUse) return;
    if (ApplyEffect(in context)) { SpendResources(); }
}
```

`RepairTowersSkill`은 고칠 타워가 없으면 `false`, `MeteorBarricadeSkill`도 설치 실패 시 `false`를
돌려주는데 지금은 호출부(`SkillTargetingController.ActivateSkill`)가 이 값을 모른다. 그대로 A를
붙이면 **아무 일도 안 일어난 시전에도 화려한 이펙트가 뜨는** 버그가 된다.

**필요한 변경**: `Activate`를 `bool` 반환으로 바꾸고, `SkillTargetingController.ActivateSkill`에서
`true`일 때만 A를 스폰한다. 호출부는 그 한 곳뿐이라 영향 범위는 작지만, `Skill.cs`는 모든 액티브가
공유하는 기반 코드다 — 이 파일을 직접 고치는 건 구현 단계에서 다시 확인받는다.

```csharp
private void ActivateSkill(Skill skill, SkillCastContext context)
{
    bool didActivate = skill.Activate(context);
    if (didActivate)
    {
        // A계층 스폰 지점
    }
    SkillUsed.Invoke(skill);
}
```

## 6. 앵커·레이어 규칙 (재확인 — 이미 검증된 것만 재사용)

- 몬스터 발밑: `MonsterMovement.GroundPlanePosition`. `SpriteRenderer.bounds`로 잡지 않는다
  (보스에서 −0.8 월드 단위까지 어긋난 전례가 있다)
- 타워: `tower.DepthSortOrder + 1` 상속, `Overlay`로 올리지 않는다
- 새 씬 컴포넌트가 필요하면 `Find` 금지, `OnEnable`에서 정적 필드로 자가등록
  (§타워이펙트_작업노트 3-13 ★★ — 배선 누락이 PR 직전까지 안 보였던 전례가 있다)
- 색조: 얼음/화염/암석 모두 기존 타워 색조 규칙(파랑·오렌지·보라 280)을 그대로 물려받아
  속성 색 규칙을 어미용 스킬에서도 깨지 않는다

## 7. 에셋 소스 계획

CLAUDE.md 규칙상 Coplay의 생성형 기능(3D·텍스처·SFX 생성 등)은 쓰지 않는다. 지금까지와 같은 방식대로
`CoplayScripts/`에 1회성 조합 스크립트를 짜서 Eric/Hovl 팩에서 기존 파츠를 조합하고, 완성된 프리팹은
`Assets/Imported`(팀 공유 저장소)에 커밋한다.

| 스킬 | A 베이스 후보 | B 베이스 후보 |
|---|---|---|
| 빙결 | 신규 조합(파랑, 성 중심 확산) | 이미 있음 |
| 화염 | 신규 조합(오렌지, 성 중심 확산) | `FX_Impact_FireCrack` 경량화 |
| 타워수리 | 신규 조합 또는 §2-3의 `VfxFlashLight` 재사용 | 위와 동일 |
| 메테오 | `FX_Impact_StoneCrack` 확대판 | 암석 계열 경량 임팩트 + 방벽 마무리 플래시 |

## 8. 열린 질문 (팀 확인 필요)

- 타워수리 A/B를 새 파티클로 만들지, `VfxFlashLight` 재사용으로 끝낼지
- 화염 B의 "경량화" 기준(파티클 수 배수) — §타워이펙트_작업노트 3-10의 `MinMaxCurve.constant` 함정을
  피해 실측으로 잡는다
- 성 회복(HEAL_CASTLE)을 이 작업 범위에 넣을지 — 지금은 제외로 가정(§0)

## 9. 마일스톤 제안

1. **빙결 N-동시발동 실측** (신규 자산 0개, 플레이 확인만) — §4
2. **A계층 공통 프로토타입** — 빙결에 먼저 붙여 "성에서 터지는 시전 연출" 자체를 검증(재사용 가능한
   패턴인지 확인하는 게 목적, 얼음 색조로 시작)
3. **`Skill.Activate` bool 반환 전환 + `SkillTargetingController` 배선** (§5)
