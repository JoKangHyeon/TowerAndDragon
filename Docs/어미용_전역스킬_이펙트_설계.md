# 어미용 스킬 이펙트 설계

어미용 스킬트리 **액티브 5종**(전역 4 + 단일 대상 1)에 발동 연출을 붙이는 설계.
**지금은 5종 다 VFX가 0이거나(빙결만 절반) 게임플레이 로직뿐이다.**

선행 문서:
- `Docs/타워이펙트_작업노트.md` — 카메라 제약·색조·버스트 방출·발밑 앵커 등 이 프로젝트의 이펙트 함정 전부
- `Docs/버프타워_이펙트_설계.md` — 같은 팩·같은 기법을 쓰는 선행 사례, 문서 형식의 전례

**순서·완료 조건·진행 상태는 이 문서가 갖지 않는다** → `Docs/어미용_전역스킬_이펙트_마일스톤.md`
이 문서는 **무엇을 만드는가**(수치·자산 경로·표)의 단일 출처다.

## 0. 범위와 결론 요약

`Skill.cs`의 어미용 액티브 **5종 전부**를 다룬다.

| 스킬 (속성) | 대상 | A. 시전 연출 (화면 오버레이) | B. 대상별 연출 |
|---|---|---|---|
| 전역 빙결 (FREEZE_ALL, 얼음) | 필드의 모든 몬스터 | 없음 → **신규** | **이미 있음** (`FX_Status_IceFreeze`, §2-1) |
| 전역 화염 (GLOBAL_CURRENT_HEALTH_DAMAGE, 불) | 필드의 모든 몬스터 | 없음 → **신규** | 없음 → **신규** (기존 상태 VFX 경로 못 씀, §2-2) |
| 즉시 재활성화 (REPAIR_TOWERS, 시간) | 비활성 상태인 모든 타워 | 없음 → **신규** | 없음 → **신규** (§2-3) |
| 메테오 방벽 (METEOR_BARRICADE, 암석) | 지정 지점 광역 + 방벽 | 없음 → **신규** | 없음 → **신규** (대상이 몬스터+방벽 둘, §2-4) |
| 성벽 재생 (HEAL_CASTLE, 생명) | 메인 성 1개 | 없음 → **신규** | 없음 → **신규** (§2-5) |

**성 회복이 "전역"이 아닌데도 범위에 드는 이유**: 5속성 중 생명만 연출 0으로 남는 것을 막기 위해서다.
파일명 `어미용_전역스킬_이펙트_설계.md`는 교차 참조와 git 이력 때문에 유지한다.

빙결의 대상별 연출이 이미 있다는 걸 처음엔 놓쳤다 — `DS_IceFreeze`/`_R1`/`_R2` 세 상태이상 에셋
전부 `_activeVfxPrefab`이 `FX_Status_IceFreeze`로 채워져 있고(각각 3/4/5초), `FreezeAllSkill.ApplyEffect`가
부르는 `ApplyStatus`는 타워가 건 상태이상과 완전히 같은 파이프라인을 타므로 코드 0줄로 이미 동작한다.
남은 건 §4의 **N-동시발동 검증**뿐이다.

### 1차 개정에서 뒤집힌 것 (2026-09-01)

무엇을 만들지가 바뀐 3건이다. 이전 판의 문장을 보고 되돌리지 말 것.

| 항목 | 초판이 적었던 것 | 확정 |
|---|---|---|

## 1. 두 계층 구조

버프 타워 설계와 같은 전제 — **"발동 순간에 항상 뜨는 것"과 "대상별로 뜨는 것"을 분리한다.**

- **A. 시전 연출 (화면 오버레이)**: 스킬이 실제로 효과를 낸 순간 **1회만** 뜬다.
  카메라가 어디를 보고 있든 "어미용 스킬이 지금 발동했다"가 읽혀야 하는 몫. 월드가 아니라 **화면**에 뜬다.
- **B. 대상별 연출**: 실제로 영향을 받은 개체(몬스터/타워/성/방벽 지점)에 뜬다.
  "무엇이 얼마나 영향을 받았는지"를 보여주는 몫.

### 1-1. 스폰 방법은 계층마다 다르다

초판은 "두 계층 다 `ProjectilePool.PlayForSeconds`로 스폰"이라고 적었으나 **성립하지 않는다.**
`ProjectilePool.PlayForSeconds`(`Assets/Scripts/Combat/ProjectilePool.cs:65`)는 시그니처는
`(prefab, position, rotation, seconds)`가 맞지만 **반환값이 `void`이고 오버로드가 없다.**
정렬 순서를 지정할 수도, 뜬 이펙트를 나중에 조작할 수도 없다.
정렬을 건드리는 기존 두 경로는 전부 핸들을 받는다
(`MonsterStatusVfx.cs:118`의 `ProjectilePool.AcquirePersistent` → `Transform` 반환 /
`TowerBuffOrbDisplay.cs:199`의 보관된 Transform).

**핵심: 정렬·지연이 필요한 계층에만 호스트가 필요하고, 그 계층엔 이미 호스트가 있다.**

| 계층 | 정렬 필요 | 지연·페이드 필요 | 스폰 방법 / 호스트 |
|---|---|---|---|
| A 오버레이 (5종) | 화면 최상단 고정 | ○ (루프 페이드, §3-2) | 카메라 자식 + **신규 호스트 컴포넌트** (§3-3). `ProjectilePool` 미사용 |
| B 빙결 | × | × | **이미 완료** — `DS_IceFreeze`/`_R1`/`_R2` → `FX_Status_IceFreeze` |
| B 화염 (몬스터) | × | × | `PlayForSeconds` 그대로. `TakeDamage` 직후 |
| B 메테오-몬스터 | × | × | `PlayForSeconds` 그대로 |
| B 즉시 재활성화 (타워) | **○** — `Building`은 뎁스 정렬이 있다 | ○ | **`Tower`가 호스트.** 이미 UniTask를 쓴다(`ReviveAfterDelayAsync`) |
| B 성 회복 | ○ | × | `HealCastleSkill.ApplyEffect`에서 직접 (§2-5) |
| B 방벽 (생성) | ○ | ○ (0.1~0.2초 늦은 플래시) | **`StoneBarricade`가 호스트** (MonoBehaviour). ~~소멸~~은 범위 제외 (2026-09-02) |

`Projectile` 레이어는 뎁스 정렬이 없으므로(작업노트 4장) 몬스터에 붙는 버스트는 지금 API로 충분하다.
**따라서 `ProjectilePool`에 오버로드를 추가하지 않아도 5종을 전부 만들 수 있다.**
오버로드 추가는 "있으면 편한 것"으로만 남긴다 — `ProjectilePool`은 공용 기반 코드다.

> **`Skill`은 호스트가 될 수 없다.** `Skill.cs:80`의 `public abstract class Skill`은 MonoBehaviour가
> 아니라 코루틴/UniTask 호스트가 없다. 초판 §2-4가 지연 연출을 `MeteorBarricadeSkill` 안에 두려 한 것은
> 불가능하다.

## 2. 스킬별 설계

### 2-1. 전역 빙결 (FREEZE_ALL, 얼음)

`SK_Dragon_FreezeAll.asset` — Type 3. 스트링테이블 `dragon_skill_freeze_all_name` = "전역 빙결".

**B(대상별)는 이미 완료.** `FX_Status_IceFreeze`가 작업노트 4장에서 "0.15초에 이미 99% — 지속 연출로는
이상적, 손댈 것이 없다"고 검증까지 끝난 자산이다. `AppliedStatus`가 `FreezeStatusSO`라 지속시간이
유한하고(`DS_IceFreeze` 3초 / `_R1` 4초 / `_R2` 5초), 이 스킬에만 배선돼 있어 다른 경로에서 뜰 일이 없다.

**A(시전)만 신규.** 지금은 발동 순간 화면에 아무 신호가 없고, 몬스터들이 각자 얼어붙는 것만 보인다.

> **각주 — 선행 문서와의 불일치 1건.** `타워이펙트_작업노트.md` 4장은 "어미용(`DS_*`)은 채우지 않는다"고
> 포괄적으로 적었으나 `DS_IceFreeze`/`_R1`/`_R2` 3개는 실제로 채워져 있다(`f314c212`, 2026-08-25 —
> 4장 작성 다음 날). 노트의 **근거**(무한 지속 → 상시 표시)는 3/4/5초 유한인 이 3개엔 해당하지 않아
> 문구가 근거보다 넓게 쓰인 것이다. 노트 자체는 고치지 않는다.

### 2-2. 전역 화염 (GLOBAL_CURRENT_HEALTH_DAMAGE, 불)

`SK_Dragon_GlobalDamage.asset` — Type 4. 현재 체력의 30% 피해 + 화상 재적용.

**B를 기존 상태 VFX 경로로 못 만든다 — 확인된 제약.** `AppliedStatus`가 가리키는
`Assets/Data/Dragon/Status/DS_FireBurn.asset`은 `DamageOverTimeStatusSO`이고 지속시간이 무한
(`_durationSeconds: 0`)이며, 불 속성 각성 패시브의 `DE_Fire_Unlock_R1_Passive.asset`
(`DragonSpawnStatusEffectSO` — 몬스터가 스폰될 때 사거리 안이면 상시 화상을 건다)이 **이 SO를 참조한다.**
`_activeVfxPrefab`(현재 `{fileID: 0}` = 비어 있음)을 채우면 스킬을 쓰지 않아도 몬스터가 스폰될 때마다
화면에 불이 상시로 뜬다. 작업노트 4장이 이미 이 이유로 비워두라고 못 박아 뒀다.

**대안**: `GlobalCurrentHealthDamageSkill.ApplyEffect`(`Skill.cs:417`)가 데미지를 준 몬스터 각각에 대해
**스킬 쪽에서 직접** 1회성 임팩트를 스폰한다. 상태이상 시스템을 거치지 않는다 — "화상이 걸려 있다"가
아니라 "지금 막 타격했다"는 신호이므로 오히려 명중 이펙트 성질에 더 맞다.
자산은 §7의 `Impact_BD_Fire`를 1순위로 본다(신규 경량화 제작보다 싸다).

### 2-3. 즉시 재활성화 (REPAIR_TOWERS, 시간)

`SK_Dragon_RepairTowers.asset` — Type 5. 스트링테이블 `dragon_skill_repair_towers_name` = **"즉시 재활성화"**,
`_desc` = "비활성화된 모든 타워를 대기시간 없이 즉시 복구합니다".

> **초판의 "타워수리 / 파괴된 모든 타워 / 복구되며 빛이 차오르는"은 폐기한다.** CLAUDE.md의
> **"타워는 파괴 대신 비활성화"** 규칙과 어긋나는 프레이밍이었다. `Tower.cs:372` 주석도 이 스킬을
> "시간 어미용 액티브 스킬의 즉시 수리"로 못 박고 있다.

**연출의 의미**: "복구되며 빛이 차오른다"가 아니라 **"기다림을 건너뛴다"**다. 합성해야 할 기존 시각 상태 2개:

- `Tower.IsBrokenPose`(`Tower.cs:133`) → `RefreshBrokenAnimation()`(`:136`)이 `_animator`의 BROKEN
  플래그를 내린다. **부서진 포즈 → 정상 포즈 애니메이션 전환이 이미 있다.** 새로 만들 필요 없다
- 부활 게이지(`Tower.ReviveProgress` `:117`, `IReviveProgress`) — 체력바 UI가 그리고 있고, 스킬은 그
  게이지를 **중간에 끊는다**(`CancelRevive()` → `RestoreAndReactivate`)

**스폰 지점**: 모든 재활성화가 지나는 단일 관문 `Tower.RestoreAndReactivate(cause)`(`Tower.cs:496`).
원인 구분 enum `ReactivationCause`(`:483`)에 **값이 3개** 있다:

| 값 | 경로 | 이 연출 |
|---|---|---|
| `NightRevive` | 부활 게이지 완주 (`:416`) | **뜨면 안 된다** |
| `SkillRepair` | 이 스킬 (`TryRestoreDuringCombat` `:366` → `:374`) | **여기서만 뜬다** |
| `MorningRestore` | 아침 일괄 복구 (`:273`) | **뜨면 안 된다** |

`RepairTowersSkill.ApplyEffect`(`Skill.cs:449`)에서 직접 스폰하는 안은 **채택하지 않는다** —
`Skill`은 정렬 상속과 반납을 처리할 수 없다(§1-1).

**전제 조건 주의**: `CanUseCombatRepair`(`Tower.cs:441`)는 연구 해금 질의다. 미해금 상태에서는
`TryRestoreDuringCombat`이 전부 false를 돌려주어 **아무 타워도 안 고쳐진다.**

### 2-4. 메테오 방벽 (METEOR_BARRICADE, 암석)

`SK_Dragon_Meteor.asset` — Type 7. 고정 피해 40 · 광역 반경 1.5 · 하루 2회(유일하게 무제한이 아닌 액티브).
GroundPoint 타겟팅이라 이미 `RangeIndicator`로 조준 미리보기는 있다 — 이 절이 다루는 건 **명중 순간**부터다.

**대상이 둘로 갈린다 — 몬스터(피해)와 방벽(구조물).**

- **A(시전)**: 다른 4종과 같은 화면 오버레이(§3). 암석 색조
- **B-몬스터**: 광역 반경 1.5는 몬스터 수가 많아 봐야 한 자리 수라 §4의 N-cap 대상이 아니다.
  타격받은 몬스터 각각에 **암석 계열** 경량 임팩트(§2-2와 같은 이유로 상태이상 경로가 아니라 직접 스폰)
- **B-방벽**: 아래 생애주기 표를 따른다

#### 방벽 생애주기 — 사건이 3개다

`Assets/Scripts/Buildings/StoneBarricade.cs`(`Building`, `IMonsterTarget`)에는 **VFX 훅이 전혀 없다.**
초판 §2-4는 이 중 생성 하나만 다뤘다 — 예고 없이 나타나는 것을 문제 삼으면서 예고 없이 사라지는 것은 빠뜨렸다.

| 사건 | 코드 | 연출 | 우선순위 |
|---|---|---|---|
| **생성** | `Initialize(healthMultiplier)` `:47` (안 부르면 `MaxHealth == 0`) | "땅이 솟아오르는" 짧은 마무리 플래시. 착지 폭발이 가라앉는 타이밍과 겹치지 않게 **약 0.1~0.2초 늦게** — 정확한 값은 픽셀 측정으로(작업노트 3-9와 같은 종류) | 높음 |
| ~~**피격·파괴**~~ | `TakeDamage` `:52` / `HandleDie` `:68` | ❌ **범위 제외 (2026-09-02)** — 연출을 넣지 않는다 | — |
| ~~**밤 종료 소멸**~~ | `RegisterAutoDestroy(CycleManager)` `:89` → `HandleNightEnd` `:100` → `HandleDie` | ❌ **범위 제외 (2026-09-02, 팀 결정)** — 예고 없이 사라져도 무방하다고 판단했다 | — |

**초판의 우려 하나는 해소된다**: `MeteorBarricadeSkill.ApplyEffect`(`Skill.cs:585`)는 설치 가능 여부를
**데미지보다 먼저** 검증하고 실패 시 `return false`로 데미지도 넣지 않는다. "몬스터는 맞았는데 방벽만
실패"하는 경로가 없어 B-몬스터 연출은 항상 A와 동반된다. 불필요한 예외 처리를 하지 않는다.

### 2-5. 성벽 재생 (HEAL_CASTLE, 생명) — 1차 개정에서 신설

`SK_Dragon_CastleHeal.asset` — Type 6, Heal 50, Cooltime 60, UsePerDay −1.
스트링테이블 `dragon_skill_castle_heal_name` = "성벽 재생". 기획종합_v2 §10의 생명 속성 액티브.
초판의 제외 근거("기획 미확정")는 사실이 아니었다 — 기획·스트링테이블·에셋·코드 모두 확정이다.

### 3-1. 초판의 "성 앵커"를 폐기한 이유

## 4. N-동시발동 문제

노트에 쌓인 모든 대상별 이펙트 교훈은 N=1(명중) 또는 N=소수(상태 트리클)에서 나왔다.
전역 스킬은 **한 프레임에 몬스터 20~30마리를 동시에** 건드릴 수 있다. `Projectile` 레이어는 뎁스
정렬이 없다는 게 이미 알려진 제약(작업노트 4장)이라, 30개 동시 버스트면 그게 지배적인 시각 잡음이 된다.

**기본 방향: A(화면 오버레이)가 이미 "뭔가 크게 일어났다"를 전달하므로, B는 가볍게 만들고 과도하면 자른다.**

- 화염 B는 원본 임팩트 세트를 그대로 쓰지 않고 경량 버전을 쓴다(§7의 `Impact_BD_*` 1순위)
- ~~화면에 동시 대상이 일정 수를 넘으면 초과분은 생략. 임계값은 `[미정]`~~
  → **N-cap은 두지 않는다. 2026-09-01 실측으로 확정** (근거는 아래 §4-1)
- 즉시 재활성화도 같은 프레임에 여러 타워가 켜질 수 있다. 타워는 파괴되지 않고 비활성 상태로 부활
  게이지를 돌리며, 스킬은 그 순간 **비활성인 타워 전부**를 동시에 켠다. 동시 대상 수는 실측 대상이다
- 지연 스폰(프레임 분산)은 1순위로 채택하지 않는다 — 빙결·화염 둘 다 "즉시 동시에 걸렸다"는 신호가
  스킬의 정체성이라, 늦게 뜨는 연출은 오히려 의미를 흐린다

**빙결은 B가 이미 구현돼 있어 이 문제를 가장 먼저, 가장 싸게 검증할 수 있다** — 마일스톤 M1이 이 실측이고,
아래가 그 결과다.

### 4-1. 실측 결과 (2026-09-01, M1) — N-cap 불필요

`CodexWave_13`(38마리)을 실제로 돌리고 전원을 빙결시킨 뒤, 화면 안 마릿수가 임계

## 5. 배선 지점 — `Skill.Activate`가 성공 여부를 못 돌려준다

```csharp
// Skill.cs:256
public void Activate(in SkillCastContext context)
{
    if (!CanUse) return;
    if (ApplyEffect(in context)) { SpendResources(); }
}
```

`RepairTowersSkill`은 고칠 타워가 없으면 `false`, `MeteorBarricadeSkill`도 설치 실패 시 `false`,
`HealCastleSkill`도 성이 없으면 `false`를 돌려주는데 지금은 유일한 호출부
(`SkillTargetingController.ActivateSkill` `:244`)가 이 값을 버린다. 그대로 A를 붙이면
**아무 일도 안 일어난 시전에도 화면 전체에 오버레이가 뜨는** 버그가 된다.

**필요한 변경**: `Activate`를 `bool` 반환으로 바꾸고, `ActivateSkill`에서 `true`일 때만 A를 띄운다.
A가 화면 오버레이가 되면서 호스트가 컨트롤러 쪽으로 확정됐으므로, 이 변경은 회피 가능한 선택이 아니라
**필요한 변경**이 됐다. 다만 `Skill.cs`는 모든 액티브가 공유하는 기반 코드다 —
이 파일을 직접 고치는 건 구현 단계에서 다시 확인받는다.

### 5-1. bool 전환만으로는 막히지 않는 구멍 2개

**① 대상 0마리여도 `true`를 돌려주는 스킬이 둘 있다.**
`FreezeAllSkill.ApplyEffect`(`Skill.cs:391`)와 `GlobalCurrentHealthDamageSkill.ApplyEffect`(`:417`)는
`AllMonsters`가 null이 아니기만 하면 몬스터가 0마리여도 `true`다. bool 전환만 하면 필드에 몬스터가
없는데 오버레이가 뜨는 버그가 이 둘에 남는다.
→ **영향받은 대상 수를 세어 0이면 A를 생략**한다.

**② `SkillUsed`를 조건 안으로 옮기면 튜토리얼이 깨진다.**
`SkillUsed`는 지금 무조건 발화하고 `GuideQuestController.cs:152`·`:220`·`:358`이 이를
`TutorialConditionType.SkillUsed` 판정에 쓴다(6개 씬 배선). 아래 예시가 `SkillUsed.Invoke`를
**조건 밖**에 둔 것은 옳다. 코드에 그 이유를 주석으로 남긴다.

```csharp
private void ActivateSkill(Skill skill, SkillCastContext context)
{
    bool didActivate = skill.Activate(context);
    if (didActivate)
    {
        // A계층(화면 오버레이) 스폰 지점
    }

    // 조건 밖이어야 한다 - 가이드 퀘스트의 "밤에 용 스킬을 써 봤는가" 판정이 이 신호를 쓴다.
    SkillUsed.Invoke(skill);
}
```

`FogTintReceiver`(`Assets/Scripts/Grid/FogTintReceiver.cs:17`)는 **Awake에서

그런데 상태 연출 인스턴스는 **몬스터의 자식이 아니라 풀 밑에 있고 위치만 따라간다**
(`MonsterStatusVfx` 클래스 주석 — 몬스터 스케일이 0.1~1.5로 갈리고 사망이 `Destroy`라 그렇게 만들었다).
그래서 **미탐색 구역의 몬스터는 어두워지는데 그 위의 연출만 원래 밝기로 남는다.**
빙결 실측에서 몬스터가 안개에 묻혀 "x6" 뱃지로만 보이는 자리에 얼음 큐브가 선명하게 떠 있었다.

이건 빙결만의 문제가 아니라 **몬스터에 붙는 모든 B계층이 그대로 물려받는다** — M5(전역 화염 B),
M7(메테오 B-몬스터)도 같다. M1 범위가 아니라 고치지 않았고, 손대려면 연출 인스턴스에도 같은
틴트를 먹이는 경로가 필요하다. **B계층 작업 전에 이 항목을 읽을 것.**

⚠️ **`FX_Status_IceFreeze`의 `IceShell`은 뎁스 정렬에 참여하지 않는다.** `Building` 소팅 레이어의
`m_SortingOrder: 0` 고정이라, `IsometricDepthSorter`가 몬스터에 매기는 순서(−36~+21 관측)와 무관하게
같은 자리에 그려진다. 실측 화면에서 성 뒤쪽 몬스터의 큐브가 성탑 위로 올라왔다.

  **밝기·지속을 코드로 바꿀 수 없다**
