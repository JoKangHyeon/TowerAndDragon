# 버프 타워 이펙트 마일스톤 (2026-08-25 ~)

> 설계 근거: [버프타워 이펙트 설계](./버프타워_이펙트_설계.md) — 왜 이렇게 하는지는 그쪽을 본다.
> 이 문서는 **구현 진행표**다. 설계가 바뀌면 설계 문서를 먼저 고치고 여기에 반영한다.
>
> 이 문서는 [타워 투사체 연출 마일스톤](./타워_투사체_연출_마일스톤.md)의 **M7(TimeTower 마법진)을 대체한다.**
>
> **⚠️ 2026-08-25 3차 전환**: 상시 표시 방식(M3~M5)을 **폐기**하고
> **클릭한 타워의 범위 + 수혜자 표시**로 바꿨다. 현행 작업은 **N0부터**다.
> M0~M8은 이력으로 남긴다 — 거기서 얻은 측정·교훈이 N에서도 그대로 쓰인다.
>
> **⚠️ 2026-08-25 3차-b 정정 (중요)**: 수혜자 표시를 **2차에서 만든 구체 `FX_BuffOrb_*` 4색**으로
> 확정했다. 방향(선택 기반)은 3차 그대로다. **폐기된 것은 "상시 표시"였고 "구체"가 아니었다.**
> → `FX_BuffOrb_*` · `M_BuffOrb.mat`을 **지우지 않는다.** 감싸기 파티클 작업(N1·N2)은 **폐기.**
> 필드 개명(`_recipientHighlightPrefab`)도 **취소**다. 설계 §0·§5·§10을 먼저 읽을 것.
>
> **별도 세션에서 새끼용 범위 인디케이터를 같은 기법으로 만들고 있다.** 설계 §7을 먼저 읽을 것.

## 이 문서를 처음 여는 에이전트에게

1. **[현행 진행 현황](#현행-진행-현황-3차)의 `⬜ 대기`인 첫 마일스톤**을 찾는다 (N 번호)
2. 선행 조건을 [확인 명령](#확인-명령)으로 직접 검증한다 — 표가 아니라 명령 결과를 믿는다
3. **완료 판정**을 전부 만족시키고 표와 작업 로그를 갱신한다

**N 번호가 현행이고 M 번호는 이력이다.** 거기서 작업을 시작하지 말 것.
다만 **M3 산출물(`FX_BuffOrb_*` 4색)은 현행 자산이다** — 이력표를 "전부 끝난 것"으로 읽고
지우지 않도록 주의한다 (N0의 ⛔ 목록).

## 작업 원칙

- **커밋은 하지 않는다.** 변경분을 정리해 보고하고 커밋은 담당자가 직접 한다
- `Assets/Imported` 아래 임포트 원본은 수정하지 않는다. 가공본은 복제해서 따로 만든다
  (`Assets/Imported`는 팀 공유 별도 저장소다 — 작업노트 §0)
- 씬·프리팹은 Coplay MCP로 다루고, 플레이 모드가 켜진 상태에서 코드를 고치지 않는다
- 리터럴 상수 금지 · 지연은 `UniTask` (CLAUDE.md)
- Coplay의 생성형 기능(3D·텍스처·이미지·음악·SFX 생성)은 사용 금지
- 마일스톤 하나 = **컴파일 에러 0 + 플레이 모드 진입 가능 + 밤 전투 정상**
- **새끼용 세션과 기법이 갈라지지 않게 한다** (설계 §7-1 표가 기준)

## 가공본 위치

- 범위 마커 · 수혜자 구체: `Assets/Imported/Prefabs/Aura/` (**둘 다 이미 만들어져 있다**)
- 생명 타워 투사체: `Assets/Imported/Prefabs/Projectile/Tower/`
- (새끼용 세션은 `Assets/Imported/Prefabs/BabyDragon/Range/` — 건드리지 않는다)

## N0 — 상시 표시 걷기 (프리팹은 남긴다) ★

**목표**: 늘 떠 있던 구체를 걷어낸다. **이 단계가 끝나면 선택과 무관하게 뜨는 구체가 사라진다.**
**프리팹·머티리얼은 지우지 않는다** — N5가 같은 것을 쓴다.

### 지울 것 (코드만)

| 대상 | 경로 | 이유 |
|---|---|---|
| `TowerAuraOrbStrength` 파일 + `TowerBuffOrbDisplay.Layout`의 세기 계산 호출 | `Assets/Scripts/Buildings/ElementalTower/` | 세기 연동 폐기. 크기는 `BASE_DIAMETER` 고정 (설계 §10) |
| `TowerBuffOrbCoordinator`의 `GridMap` 전수 등록 · `LateUpdate` 순회 | 같은 폴더 | **상시 표시가 여기서 나온다.** 걷으면 화면이 조용해진다 |

### ⚠️ `TowerBuffOrbDisplay`의 딕셔너리·호선 배치는 N0에서 건드리지 않는다 ★

오라별 딕셔너리(`_activeByAura`)와 호선 배치를 N0에서 먼저 걷으면
`Tick`·`Reconcile`이 없어진 필드를 참조한 채로 남아 **컴파일이 깨진다** —
"마일스톤 하나 = 컴파일 에러 0" 규칙을 스스로 어기게 된다.

- N0에서는 **호출자만 없앤다.** 클래스는 그대로 남지만 아무도 부르지 않아 화면에 안 뜬다
- **N5가 이 파일을 수혜자 타워별로 통째로 고쳐 쓴다** — 그때 딕셔너리 키와 배치가 함께 바뀐다
- 세기 계산만 N0에서 떼는 것은 안전하다 (`TowerAuraOrbStrength` 호출 한 줄 → 고정 크기)

**클래스 두 개(`TowerBuffOrbDisplay`·`TowerBuffOrbCoordinator`)는 파일을 지우지 않는다.**
이름을 유지하는 이유는 씬에 붙은 컴포넌트와 연결된 참조를 살리기 위해서다 (설계 §8-2).

**N5로 넘길 조각**: `ResolveAnchor`(발밑 앵커) · `ApplySortingOrder`(Building 레이어 +
`DepthSortOrder + 1`) · `Orb` 렌더러 캐시 · 풀 대여/반납 · 상수 `BASE_HEIGHT 1.4` ·
`BASE_DIAMETER 0.31` · `SORTING_ORDER_OFFSET 1`.

## N4 — 런타임: 범위 마커

**목표**: 오라 타워를 클릭하면 발밑에 `FX_Aura_*`가 유효 반경으로 뜬다.

### 구현된 모습 (as-built)

```csharp
// TowerBuffOrbCoordinator.LateUpdate (요약)
if (!TryResolveRangeMarker(out Tower source, out GameObject prefab, out float radius))
{ ReleaseRangeMarker(); return; }
_rangeMarker ??= ProjectilePool.AcquirePersistent(prefab);   // 프리팹이 바뀌면 반납 후 재대여
_rangeMarker.position   = source.transform.position;
_rangeMarker.rotation   = Quaternion.identity;
_rangeMarker.localScale = Vector3.one * radius;              // 루트 스케일 1 = 반경 1
```

`TryResolveRangeMarker`가 거르는 것: 선택이 `Tower`가 아님 · **`BabyDragonTower`** ·
`TryGetActiveAura` 실패(감전·비활성·인구 0) · `RangeMarkerPrefab` 미배선 · 반경 0.

### 지킨 것 ★

- **`TryGetActiveAura`의 유효 반경**을 쓴다. `TryGetPreviewRadius`(항상 2)를 쓰면
  인구 절반인 타워에서 "원 안인데 구체가 안 뜨는 타워"가 생긴다 (설계 §4-2)
- 마커 프리팹은 `_rangeMarkerPrefab`에서 읽는다 — 경로를 코드에 박지 않는다
- 선형 인디케이터는 `ShowBuffRangeIndicatorFor`에서 **`aura.HasRangeMarker`일 때만** 숨긴다.
  마커를 안 꽂은 오라는 기존 선을 그대로 쓴다
- **새끼용 제외** — `BabyDragonTower`도 `Tower`를 물려받고 버프 모드에서 `TryGetActiveAura`가
  통과한다. 그쪽 범위는 `BabyDragonRangeVfxDisplay`가 그리므로 겹쳐 그리지 않는다

### 씬 재배선이 없다 ★

`BuildingPlacementController`는 `BuildingPlacementManager` 프리팹 안에 있어 씬마다 프리팹
인스턴스 내부를 배선해야 한다. `BabyDragonRangeVfxDisplay`와 같이 `FindFirstObjectByType`로
런타임에 한 번 찾는다. `_towerAuraSystem`은 이미 배선돼 있으므로 손댈 것이 없다.

### 자산 재생성이 함께 들어갔다 (계획 밖) ★

M2 마커가 실제 씬에서 너무 흐려 **새끼용 버프 범위와 같은 소스·처리로 다시 구웠다**
(`CoplayScripts/RebuildAuraMarkers.cs`, 설계 §4-0). 다시 손댈 때 지켜야 하는 것:

- **같은 경로에 저장한다** — GUID·루트 fileID가 유지돼 오라 4장 배선이 살아 있다(실측 확인)
- **맥동 주기를 박지 않는다** — `FX_BD_BuffRange_<속성>`의 `Circle`에서 읽는다
  (시간·은신·강화 0.8초 / 영혼 1.0초. 새끼용 쪽이 바뀌면 스크립트를 다시 돌린다)
- 색은 `DragonAttributePalette` — 시간=Time · 은신=Stone · 영혼=Ice · 강화=Fire

### 완료 판정

- 오라 타워를 클릭하면 마커가 뜨고, 선택을 풀면 사라진다 ✅
- **인구를 옮기면 원이 그 자리에서 커지고 작아진다** ✅
- 감전·비활성·인구 0이면 사라진다 ✅ (**인구 0에서 안 뜨는 것은 기존 선형 인디케이터와 같은 동작**)
- 선형 인디케이터와 겹쳐 보이지 않는다 ✅
- 마커 선명도가 새끼용 범위 표시와 같다 ✅
- **맥동 속도가 새끼용과 같다 ✅** — 프리팹 YAML 정적 대조로 확인(속성별 `Circle` 지속시간 일치).
  화면 육안 확인은 남아 있다
- 일반 공격 타워의 사거리 표시는 그대로다 / 철거·씬 이동 시 반납된다 — 미확인

## N5 — 런타임: 수혜자 구체 ★ 이 작업의 본체

**목표**: 클릭한 오라 타워의 범위 안 수혜 타워 **머리 위에 구체 하나씩** 띄운다.

### 구현된 모습 (as-built) ★

```csharp
// TowerBuffOrbCoordinator.LateUpdate (요약)
if (!TryResolveActiveSource(out Tower source, out TowerAuraDataSO aura, out float radius))
{ ReleaseAll(); return; }                    // 마커·구체를 한 번에 반납한다
UpdateRangeMarker(source, aura, radius);     // aura.RangeMarkerPrefab이 없으면 마커만 쉰다
UpdateRecipientOrbs(source, aura, radius);   // aura.HasRecipientOrb가 아니면 구체만 쉰다

// TowerAuraSystem (신설)
public void CollectAuraRecipients(Tower source, TowerAuraDataSO aura,
                                  float effectiveRadius, List<Tower> recipients)
```

**선택 판정을 한 번만 푼다.** 마커와 구체가 각각 `SelectedBuilding`을 해석하면 조건이 한 글자만
갈려도 한쪽만 뜨는 프레임이 생긴다. 프리팹 유무 분기는 그 **다음** 단계로 내렸다 —
N4 코드는 `RangeMarkerPrefab == null`에서 false를 돌려줬는데, 그대로 두면 마커를 안 꽂은
오라에서 **구체까지 죽는다.**

**반경을 두 번 계산하지 않는다.** `CollectAuraRecipients`는 `TryGetActiveAura`를 다시 부르지 않고
마커가 쓴 유효 반경을 **인자로 받는다** — 같은 값을 나눠 써서 "원 안인데 구체가 안 뜨는 타워"를
구조적으로 없앤다 (설계 §4-2).

### ⚠️ `CollectAuraRecipients`에 재진입 가드를 넣지 마라 ★★

설계 §8-3("재진입 가드는 그대로 필요하다")을 읽고 "빠졌다"며 넣기 쉬운 자리다. **넣으면 버그다.**

- 가드가 필요한 경로는 `TryGetActiveAura(source)` → `CanOperate` → `ResolveModifiers`이고,
  그것은 **호출자가 이미 지나온 곳**이다. 그쪽 재귀는 `ResolveModifiers` 자신의 가드가 끊는다
- 수집 루프가 타는 `IsEffectiveOn` → `HasSoulEffect`는 `SoulPopulation`이 아니라
  **`RealAssignedPopulation`만** 읽어 `ResolveModifiers`로 되돌아가지 않는다
- 여기서 `source`를 가드에 넣으면 호출자의 `TryGetActiveAura`가 `Neutral`을 받아
  **영혼 인구가 0으로 읽히고 반경이 줄어든다** — 마커와 목록이 어긋난다

검증: 영혼 타워로 정원을 채운 은신 타워를 클릭했을 때 마커 반경이 N5 전후로 같은지.

### 정렬 순서는 **각 수혜자**의 것이다 ★

2차는 표시기가 수혜자 1개에 묶여 있어 `_owner.DepthSortOrder`가 자연히 수혜자였다.
N5는 표시기 하나가 여러 수혜자를 들고 도니 **소스의 순서를 전부에 먹이는 실수가 나기 쉽다** —
그러면 뒤쪽 타워의 구체가 앞쪽 타워를 덮는다. `Layout`이 `recipient.DepthSortOrder`를 쓴다.

### ⚠️ `SortingLayer.NameToID`를 정적 초기화자에 두면 안 된다 ★★ (플레이에서 터졌다)

2차 코드는 `BUILDING_SORTING_LAYER_ID`를 `static readonly` 필드 초기화자로 읽고 있었다.
**그때는 안 터졌고 N5에서 터졌다** — 코디네이터가 `TowerBuffOrbDisplay`를
**인스턴스 필드 초기화자**(`private readonly TowerBuffOrbDisplay _orbDisplay = new();`)에서
만들기 때문이다. 2차에서는 그리드 등록 때 런타임에 만들었으므로 static ctor가 늦게 돌았다.

```
UnityException: NameToID is not allowed to be called from a MonoBehaviour constructor
(or instance field initializer), call it in Awake or Start instead.
  TowerBuffOrbDisplay..cctor ()
  Rethrow as TypeInitializationException
  TowerBuffOrbCoordinator..ctor ()
```

**증상이 원인을 안 가리킨다.** 타입 초기화가 실패하면 `_orbDisplay`가 **null로 남고**,
첫 `LateUpdate`의 `ReleaseAll`에서 `NullReferenceException`이 난다 —
스택은 코디네이터만 가리키고 `SortingLayer`는 안 보인다. 콘솔을 위로 올려
**같은 프레임의 `TypeInitializationException`을 찾아야** 진짜 원인이 나온다.

→ 지금은 `BuildingSortingLayerId` 프로퍼티로 **첫 배치 때 한 번** 읽는다.
`Layout`은 어차피 런타임 경로라 생성자 제약을 안 받는다.

**이 프로젝트에서 `SortingLayer.NameToID`를 부르는 곳은 여기 한 군데다** — 다른 데서
새로 부를 일이 있으면 이 제약을 먼저 본다. 형제 격인 `MonsterStatusVfx`가 같은 형태로
필드 초기화자에서 만들어지면서도 무사했던 이유는 **정렬 레이어를 아예 안 만지기 때문이다.**

### 구체 높이는 **머리 기준**이다 — 발밑 기준을 뒤집었다 ★★ (플레이 피드백)

플레이에서 **"구체가 타워에서 너무 위쪽으로 뜬다"**. 상수를 낮추는 것으로는 안 됐다 —
**타워 스프라이트 높이가 균일하지 않다.**

| 타워 | 스프라이트 높이 | 발밑 기준 1.4의 머리 위 여유 |
|---|---|---|
| 버프·속성 타워 · 대공 | 1.200 | 0.200 |
| **일반 공격 타워** (활·석궁·머스킷) | **0.960** | **0.440** |

발밑에서 잰 고정 높이라 낮은 스프라이트에서 여유가 그만큼 늘어난다. 그리고
**버프를 받는 쪽은 대개 공격 타워**라, 가장 자주 보이는 곳이 두 배 이상 떠 있었다.

상수만 낮추면 공격 타워는 여전히 멀고 1.2 타워는 스프라이트에 파묻힌다.
→ 기준을 **경계 위쪽(`bounds.max.y`)** 으로 옮기고 `HEAD_CLEARANCE = 0.12`를 더한다.
모든 타워에서 눈에 보이는 간격이 같아진다.

**2차 문서가 적어 둔 "발밑 기준" 근거는 절반만 맞았다** — "몸통 중앙 기준은 스프라이트 크기가
다른 타워에서 높이가 갈린다"는 옳지만, **발밑 기준도 똑같이 갈린다.** 갈리지 않는 것은 머리뿐이다.

측정 스크립트는 `CoplayScripts/MeasureOrbHeadroom.cs`다 (임시 도구 — N8에서 정리).
씬에는 편집 모드에 타워 인스턴스가 없어 `TP_*` 프리팹에서 스프라이트 높이를 읽는다.

### 프리팹이 바뀌면 전량 반납한다 ★

시간 타워 → 영혼 타워로 선택을 옮기면 `_recipientOrbPrefab`이 바뀐다. **두 타워의 범위가 겹치면**
겹친 수혜자는 목록에 그대로 남아, 비교가 없으면 **이전 색 구체가 그 타워에 계속 떠 있다.**
`_activePrefab`을 기억해 다를 때 `ReleaseAll()`한다.

### 쓰는 자산 — 새로 만들지 않는다

`FX_BuffOrb_Time` · `FX_BuffOrb_Stealth` · `FX_BuffOrb_Soul` · `FX_BuffOrb_Enhancement` (M3).
오라 데이터의 `_recipientOrbPrefab`에서 읽으므로 **소스가 정해지면 색이 따라온다** —
색을 고르는 코드가 따로 없다.

### 새로 필요한 것 — 반대 방향 수집

`CollectRecipientAuras`는 "이 타워가 **받는** 오라"를 모은다.
여기서는 "이 오라가 **주는** 타워들"이 필요하다 — 소스 기준 수집을 새로 넣는다.

- `TowerAuraSystem`의 재진입 가드를 그대로 쓴다 (영혼 오라가 되짚어 올 수 있다)
- **`IsEffectiveOn`으로 거른다** — 효과 없는 타워에 구체를 띄우면 거짓 신호다 (설계 §2-4)
- 최대 6개 (반경 2 안의 칸 수)

### 2차 코드에서 바뀌는 것 (설계 §8-2)

| 항목 | 2차 (상시) | N5 (선택 기반) |
|---|---|---|
| 표시기 키 | 오라별 — 한 타워에 구체 여럿 | **수혜자 타워별 — 구체 하나** |
| 배치 | 호선 (`SPACING_RATIO` · `CURVATURE`) | **중심축 위 한 점** (머리 기준 여유 `HEAD_CLEARANCE 0.12` — 아래 ★★) |
| 크기 | 세기비 연동 (`TowerAuraOrbStrength`) | **고정** (`BASE_DIAMETER 0.31`) |
| 갱신 대상 | 씬의 모든 타워 | **선택된 오라 하나** |
| 직렬화 필드 | `_gridMap` · `_towerAuraSystem` | `_towerAuraSystem`만 (선택 판정은 Find) |

**그대로 쓰는 조각**: `ApplySortingOrder` · `Orb` 렌더러 캐시 · 풀 대여/반납.
`ResolveAnchor`는 `ResolveOrbPosition`으로 바뀌었다 — 기준이 발밑에서 머리로 옮겨졌다(아래 ★★).

### 클릭한 타워 자신에게는 구체를 띄우지 않는다 ★ (설계 §3-5)

**오라 4종 모두 소스 제외로 통일한다.** 예외 없음.

- 소스는 발밑 범위 마커로 이미 식별된다 — 구체를 얹어도 새로 알려주는 것이 없다
- 구체의 뜻이 "이 타워는 받는 쪽"으로 하나로 고정된다
- `TowerAuraSystem`의 수집 루프가 이미 `source == target`을 건너뛴다 —
  **따로 코드를 넣지 않아도 이 규칙이 지켜진다.** 반대로 소스를 넣으려면 예외를 새로 써야 했다

은신은 근거상 자기에게도 듣지만(`Tower.cs`의 `TryGetActiveAura(this)`),
**그 상태는 상시 반투명(N6)이 알린다** — 구체로 중복해 말하지 않는다.

### 정렬

`Building` 레이어, `order = tower.DepthSortOrder + 1`.
**Overlay로 올리면 안 된다** — 뎁스 정렬을 잃어 뒤쪽 구체가 앞쪽 타워를 덮는다 (설계 §6).

### 성능

- 선택된 타워 하나에 대해서만 돈다 — 2차처럼 모든 타워가 그리드를 훑지 않는다
- 렌더러는 **대여 시점에 한 번만** 찾는다 (매 프레임 `GetComponentsInChildren`는 할당이 생긴다)

### 완료 판정

- 시간 타워를 클릭하면 **범위 안 공격 타워들 머리 위에 노란 구체가 뜬다**
- 구체 색이 클릭한 타워의 색을 따른다 (4종 각각 확인)
- **한 타워에 구체가 하나만 뜬다** (호선이 남아 있지 않다)
- 버프 타워끼리는 구체가 안 뜬다 (시간·강화 기준)
- **영혼 타워를 클릭하면 인구가 부족한 타워에 뜬다** (정원 찬 타워는 안 뜸)
- **은신 타워를 클릭하면 범위 안 버프 타워에도 뜬다** (은신은 모두에게 듣는다)
- **클릭한 타워 자신의 머리 위에는 뜨지 않는다** (4종 모두 — 설계 §3-5)
- 인구를 옮기면 구체 목록이 그 자리에서 바뀐다
- **앞쪽 타워의 구체가 뒤쪽보다 위에 그려진다**
- 6개가 동시에 떠도 어지럽지 않다
- 선택을 풀면 전부 반납된다 (풀에 빌려준 채 남지 않는다)
- **범위가 겹치는 두 오라 타워를 번갈아 클릭해도 이전 색 구체가 남지 않는다**
  (색 판정은 겹치는 배치에서만 드러난다)
- 영혼 타워로 정원을 채운 은신 타워를 클릭했을 때 **마커 반경이 줄어들지 않는다**

### ⚠️ 영혼 타워 2개를 서로의 반경 안에 놓고 깜빡임을 확인한다

`TowerAuraSystem`의 재진입 가드 주석이 경고하는 상황이다 — 진짜 순환이 생기고
그리드 순회 순서에 따라 결과가 갈릴 여지가 있다.

**3차는 2차보다 위험이 낮다** — 선택된 타워 하나만 도므로 깜빡임이 생겨도 한 곳이다.
그래도 확인은 한다. 깜빡이면 히스테리시스, 그래도 안 되면 고정점 반복(별건).

**N5 구조에서는 볼 곳이 바뀌었다** — 구체 목록이 아니라 **마커 반경**을 본다.
수혜자 판정은 `IsEffectiveOn` → `HasSoulEffect` → `RealAssignedPopulation`(비재진입 경로)만 타므로
순회 순서에 안 흔들린다. 순서 의존이 남는 곳은 `TryGetActiveAura(source)` → `CanOperate` →
`ResolveModifiers` 하나뿐이고, **반경이 떨면 경계에 걸친 타워의 구체가 따라 깜빡인다.**

## N6 — 은신 반투명

**목표**: 은신 오라 안의 타워를 반투명하게 만든다. 선택과 무관한 **상시** 표시다.

- `SpriteRenderer.color`의 알파 조절 — VFX 프리팹으로는 안 된다
- 조건은 `Tower.TargetType == MonsterTargetType.None`
- **은신 타워 자신도 은신 대상이다**
- 알파 값은 실제로 놓고 정한다

**3차에서 값이 올라간 항목이다** — 선택 표시는 클릭해야 보이지만 반투명은 상시라
"이 타워는 지금 숨어 있다"를 평소에도 알린다.

### 구현된 모습 (as-built) ★

`TowerStealthFadeCoordinator` — **별개 MonoBehaviour.** `Systems/Composites`에 붙었고
**직렬화 필드가 0개**다(`GridMap`은 Find).

```csharp
// LateUpdate — 다른 색·알파 라이터(Building.SetHighlighted)보다 나중에 써야 한다
if (_gridMap == null || !HasStealthAuraTower()) { RestoreAll(); return; }
Sweep();   // TargetType == None인 타워를 흐리고, 아닌 것은 되돌린다
```

### 왜 `TowerBuffOrbCoordinator`에 얹지 않았나 ★

거기 `LateUpdate`는 **선택이 없으면 조기 반환**한다. 상시 표시를 그 뒤에 두면
**오라 타워를 클릭한 동안에만 반투명해지고**, `ReleaseAll()`이 선택을 풀 때마다 알파를 되돌린다.
근거가 하나 더 있다 — 은신 페이드는 `_towerAuraSystem`이 **전혀 필요 없다**
(`tower.TargetType`이 타워 자신의 `_auraSystem`을 쓴다). 필요 없는 참조에 묶으면
N8에서 씬마다 그걸 꽂아야 하는 이유가 하나 늘어난다.

### 알파만 덮어쓴다 — RGB는 남의 것이다 ★

타워 몸통 `SpriteRenderer.color`에는 이미 `Building.SetHighlighted`(선택·호버 틴트)가 쓴다.
색을 통째로 쓰면 서로 덮는다. **`Castle`에 붙은 `SpriteHoverFade`가 같은 문제를 이미 풀어 뒀고**
(주석: "하이라이트 등 다른 연출이 RGB를 바꿔도 충돌하지 않도록 알파만 덮어쓴다") 같은 형태를 썼다 —
알파만 쓰고, 값이 같으면 쓰지 않는다.

**원래 알파를 캐시하지 않고 1로 되돌린다.** `.color =` 전수 조사에서 타워 몸통 알파를 쓰는 것이
없었고(부활·비활성은 애니메이터 `Broken` 포즈다), 캐시는 "다른 라이터가 잠깐 바꾼 값을
원래 값으로 굳히는" 타이밍 위험만 남긴다.

### 렌더러는 하나다 (실측) ★

`Building._spriteRenderer`는 `GetComponentInChildren`으로 **첫 하나**만 잡고
`FogTintReceiver`는 `GetComponentsInChildren`으로 **전부** 칠한다 — 어느 쪽이 맞는지 재 봤다.

**타워 12종 + `BabyDragonTower` 모두 `SpriteRenderer`가 정확히 하나이고 알파가 1.00이다.**
새끼용만 자식(`Sprite`)에 있고 나머지는 루트다 → `GetComponent` 후 자식 폴백으로 충분하다.
체력바·인구 표시는 `SpriteRenderer`가 아니라서 함께 흐려질 걱정이 없다.
(조사 도구: `CoplayScripts/SurveyTowerRenderers.cs`, 결과 `output/vfx_check/tower_renderers.txt`)

### `TargetType`을 그대로 읽는다 — 재구성하지 않는다 ★★

중복 회피가 이유가 아니다. **소스 포함 규칙이 다르다** —
`CollectAuraRecipients`는 `source == target`을 건너뛰지만 **은신은 소스 자신도 대상**이다(설계 §9-1).
재구성하면 은신 타워 자신이 조용히 빠지는데, §3-5에서 소스 구체를 뺐으므로
**그게 자기 은신을 알리는 유일한 신호다.**

덤: 몬스터의 표적 판정과 같은 값을 쓰므로 "반투명한데 맞는다"가 구조적으로 생기지 않는다.

### 싼 사전 검사로 전수 스윕을 건너뛴다

`tower.TargetType`의 프레임 캐시는 **첫 독자가 비용을 낸다** — 전수 스윕이 타워마다
`ResolveModifiers`(전체 그리드 스캔)를 새로 유발할 수 있다.
그래서 **은신 오라를 가진 타워가 아예 안 지어졌으면 스윕을 건너뛴다.**

이 사전 검사는 **데이터만 본다**(`Data is ITowerAuraDataProvider` → `TowerAura.IsStealth`) —
`TryGetActiveAura`를 쓰면 인구·감전을 보려고 `CanOperate` → `ResolveModifiers`로 들어가
아끼려던 비용을 그대로 낸다. 은신 타워가 서 있는데 인구가 0인 경우는 스윕까지 가지만 흔하지 않다.

### 클릭은 알파와 무관하다 (확인) ★

설계 §9-1이 "알파가 너무 낮으면 클릭해서 인구를 못 넣는다"고 적어 뒀는데, **기술적으로는 아니다.**
건물 클릭 판정은 그리드 셀 기준이고, `SpriteHitTest`도 텍스처 알파가 아니라
**임포트 시점에 직렬화된 실루엣 폴리곤**을 쓴다(그 파일 주석: 스프라이트 팩이 non-readable 아틀라스다).
→ 완료 판정의 "반투명해도 클릭된다"는 구조적으로 보장된다. 남는 것은 **사람이 보고 찾을 수 있는지**뿐이고,
그게 `STEALTH_ALPHA` 값을 정하는 유일한 기준이다. **지금 `0.35`** (첫 `0.5`는 플레이에서 "더 흐리게"였다).
참고로 `SpriteHoverFade`의 호버 알파가 `0.4`다 — 상시 은신이 순간 호버보다 옅은 셈이지만,
둘이 같은 타워에 겹치지 않아(그쪽은 `Castle`에만 붙어 있다) 서로 비교되어 보이는 자리는 없다.

### `BabyDragonTower`도 포함한다 — N4와 의도적으로 갈린다 ★

N4는 범위 마커에서 새끼용을 **제외**했다(그쪽은 `BabyDragonRangeVfxDisplay`가 겹쳐 그리므로).
은신 반투명은 **포함**한다 — 은신이 실제로 걸리고(몬스터가 지나친다) 겹쳐 그리는 표시가 없다.
**새끼용 세션과 갈리는 지점이므로 N8 통합 검토에서 다시 본다.**

### ⚠️ 씬 배선을 YAML로 넣었다 (churn 회피) ★★

`Haneul_TowerEffectScene`은 **에디터 메모리와 디스크가 벌어져 있다** —
UI 프리팹 override의 `value:` **1364줄**이 디스크에는 `0`, 에디터에는 실제값이다.
에디터에서 씬을 저장하면 컴포넌트 13줄과 함께 그 1364줄이 커밋에 들어간다.

그래서 `add_component` → `save_scene`으로 만들어진 파일에서 **컴포넌트 블록만 골라
원본 YAML에 직접 넣었다.** 디스크 diff는 13줄뿐이다.

- Coplay `save_scene`은 여전히 `Assets/` 루트에 사본을 만들고 **활성 씬 경로까지 바꾼다.**
  `CoplayScripts/FixActiveScenePath.cs`로 경로를 되돌리고 사본을 지웠다
- **주의**: 그 스크립트는 `SaveScene`을 부르므로 **churn을 다시 쓴다.** 경로를 고친 뒤에는
  다시 돌리지 말고 YAML 파일을 마지막에 덮어써야 한다 (이 순서를 한 번 틀렸다)
- 에디터 메모리는 여전히 dirty다 — **누구든 에디터에서 씬을 저장하면 churn이 들어온다.**
  이건 내가 만든 상태가 아니라 이미 그랬던 것이고, 정리는 담당자 판단이다

### 완료 판정

- 은신 오라 안의 타워가 반투명해지고, 오라가 꺼지면 돌아온다 (인구를 빼서 확인)
- **은신 타워 자신도 반투명하다** (설계 §9-1 — 이게 유일한 자기 은신 신호다)
- **반투명 상태에서도 클릭해 인구를 배치할 수 있다** (구조적으로 보장 — 위 ★ 참고)
- 몬스터가 은신 타워를 지나쳐 간다 — **밤 웨이브를 한 번 돌려야 검증된다** (회귀 가드)
- 은신 타워를 클릭했을 때 범위 마커·수혜자 구체는 선명하다
- 은신 타워를 철거해도 남은 타워의 알파가 1로 돌아온다
- 은신 오라 안의 타워를 선택·호버해도 하이라이트 색과 싸우지 않는다 (알파만 쓰므로)
- `STEALTH_ALPHA`가 적당한가 — **더 흐리게 해도 클릭은 안 막힌다**(위 ★). 기준은 시야뿐이다

### 후보는 렌더 전에 절반이 걸러진다 ★

렌더는 비싸다. 아래 셋은 값만으로 판정된다 — 먼저 돌리면 렌더할 것이 줄어든다.

| 검사 | 걸린 것 |
|---|---|
| `looping` | `VFX_Buff_Loop` · `VFX_Pickup_Loop` · `VFX_Heal_Loop` — 명중은 터지고 끝나야 한다(§3-5) |
| 그리는 자식 수 0 | **`Projectile_V2_01_nature`** — 이름은 딱 맞는데 아무것도 안 그린다 |
| `HorizontalBillboard` | **하나도 없었다** — 이 세트에는 §2-1 함정이 없다 |

그 뒤 남은 후보만 렌더했다. 렌더에서 추가로 떨어진 것:
`V2_06_magic`(화면에 안 나옴) · `V2_08_energy`(마젠타, 색이 다름) ·
`V2_23_green`(너무 작고 단조) · `V1_24_green_explosion`(폭발로 읽힘, 비행에 부적합).

### 색은 단일 출처다 — 네 구간이 같은 값 ★

`DragonAttributePalette.ColorOf(DragonType.Life)` = **(0.498, 0.820, 0.310)**.
"머즐 또한 통일된 느낌"이 요구의 핵심이라, **발사·비행·명중·사거리 마커가 모두 이 한 값**을 쓴다.
초록을 네 번 박으면 미묘하게 갈린다.

`startColor`만 돌리면 `ColorOverLifetime`이 원본 색을 되살려 색이 반만 바뀐다(§3-3) —
`RebuildAuraMarkers`의 처리를 옮겨 와 `ColorOverLifetime`·`ColorBySpeed`까지 함께 돌렸다.

**색조만 끌어오고 채도·명도는 남긴다.** 원본의 흰 하이라이트가 통째로 초록이 되면 형태가
뭉개진다 — 그래서 채도 0(회색·흰색)은 건드리지 않고, 채도는 팔레트 값으로 상한만 둔다.
가공 결과를 다시 렌더해 확인했다(`life_built_result.png`) — 네 줄 모두 초록이고 형태가 남았다.

### 사거리 마커 — 생명 타워는 오라 타워가 아니다 ★★

요구: "발사체 타워이긴 한데 클릭했을 때 다른 버프 타워처럼 범위 반경 파티클이 뜨면 좋겠다."

생명 타워는 `_towerAura`가 비어 있다 — 그래서 `TryGetActiveAura`가 실패하고
N4·N5의 마커 경로에 아예 들어오지 못했다. **오라 데이터를 억지로 주는 방식은 쓰지 않았다** —
그러면 `ResolveModifiers`가 없는 오라를 계산하고 `IsEffectiveOn`이 판정에 끼어든다.

대신 `TowerData._attackRangeMarkerPrefab`을 새로 뒀고, `TowerBuffOrbCoordinator`가
**오라가 있으면 마커+구체, 없으면 사거리 마커만** 그린다.

- **반경은 `TowerAttack.EffectiveRange`** — `ShowAttackRangeIndicatorFor`가 쓰는 것과 같은 값이라야
  선과 파티클이 어긋나지 않는다. `TowerData`의 데이터 사거리를 쓰면 연구 보정에서 갈린다
- **선을 숨기지 않는다.** 새끼용 공격 범위가 이미 *"선이 정확한 판정 경계를 맡고, 전용 파티클은
  그 안쪽의 연출만 담당한다"*(`BuildingPlacementController` 주석)로 되어 있어 그 방식에 맞췄다.
  오라 타워에서 선을 숨긴 것은 마커가 선과 **같은 자리**라 두 겹으로 보였기 때문이고,
  공격 범위는 선이 판정 경계라는 별도 역할을 갖는다. **숨기길 원하면 한 줄이다**
- 마커 맥동은 `FX_BD_AttackRange_Life`에서 읽는다(0.800초) — 버프가 아니라 공격 범위이므로
  기존 4종의 `FX_BD_BuffRange_*`가 아니라 이쪽이다

### "5초짜리 둘"은 하나였다 — 하나는 안 그리는 루트다 ★★

문서가 "자식 수명 5초짜리 둘을 잘라낸다"고 적어 뒀다. 재 보니 **5초를 넘는 둘 중 하나는
루트 `VFX_Heal_Cast`이고, 그것은 렌더러가 꺼져 있어 한 픽셀도 안 그린다** — 화면에 안 나오므로
겹쳐 보일 수가 없다. 실제로 눈에 보이는 초과분은 **`Ring 01` 하나**였다.

**그리고 "둘"만 보면 부족했다.** 총 지속(지연 + 방출구간 + 입자수명)으로 재면 2초 간격에
거의 붙는 자식이 더 있었다.

| 자식 | 총 지속(원본) | 가공 후 | 비고 |
|---|---|---|---|
| `VFX_Heal_Cast` (루트) | 10.00초 | **그대로** | 렌더러 꺼짐 — 안 그린다 |
| `Ring 01` | 5.55초 | 1.00초 | 배율 0.173, 방출률 ×5.79 |
| `Glow 01` · `Glow 02` | 2.00초 | 1.00초 | 배율 0.500 |
| `Rainbow Flare 01` | 1.50초 | 1.00초 | 배율 0.667 |
| `Lens` | 1.25초 | 1.00초 | 배율 0.792 |
| `Round`·`Stretched`·`Stars 01·02` | 0.55~0.65초 | 그대로 | 예산 안 |

예산은 **간격의 절반(1초)** 으로 잡았다. 간격에 딱 맞추면 "항상 하나가 켜져 있는" 그림이 되고,
배속·연구 보정으로 간격이 줄면 바로 겹친다.

**수명을 줄일 때 방출률을 같은 비율로 올렸다** — 안 올리면 동시에 살아 있는 입자가 함께 줄어
흐려진다(작업노트 §3-9). `MinMaxCurve.constant`가 `constantMax`의 별칭인 함정(§3-10)도
모드별 분기로 피했다.

### 정렬 레이어가 갈려 있었다 (계획 밖) ★

원본 팩이 다르면 정렬 레이어가 갈린다. 기존 타워 머즐 6종이 전부 `Projectile`(id 1811136797)인 것을
실측 대조하고 맞췄다 — 세 구간이 같은 레이어에 서야 서로 가리는 순서가 예측된다.

**2차안에서 대상이 늘었다.** 1차안은 명중이 AAA_Vol2였어서 발사만 걸면 됐지만,
2차안은 **발사·명중 둘 다 Vefects**라 둘 다 걸어야 했다. 비행(`AAA_Vol2`)은 이미 `Projectile`이다.
→ **원본을 바꾸면 이 대상도 바뀐다.** 생성기가 매번 확인해 리포트에 찍는다.

**자식별 `sortingOrder`는 건드리지 않았다**(`Glow 01` −1, `Rainbow Flare 01` 20) —
그건 이펙트 내부 층 순서라 작가가 정한 값이다. 다만 `Rainbow Flare 01`의 20은
`Projectile` 레이어의 다른 투사체(대개 0) 위에 그려진다 — 눈에 걸리면 여기를 본다.

### 카메라 함정은 이 세트에 없다 (확인) ★

- `HorizontalBillboard` 자식이 **하나도 없다** — 작업노트 §2-1의 "한 픽셀도 안 그려짐"이 안 걸린다
- `Mesh` 렌더 자식 둘(`Projectile`·`Impact_Tower_Life` 루트)의 `startRotationX`가 **0도**다 —
  M0에서 겪은 90도 함정이 아니다. 메시 이름은 둘 다 **`Heart`** 다(힐 전용 자산이 맞다)

### ⚠️ 생성기를 다시 돌리면 GUID가 바뀐다

`Execute()`는 기존 복제본을 지우고 다시 복사하므로 **세 프리팹의 GUID가 새로 생긴다.**
같은 실행 안에서 `TD_LifeTower`와 `ProjectileVisual`을 다시 배선하므로 그 둘은 항상 맞지만,
**다른 곳에서 이 프리팹을 참조하게 되면 그때부터는 다시 돌리면 안 된다.**

### 완료 판정

- 밤에 손상된 아군 타워가 **초록 마법 발사체**를 맞고 회복된다 (하트가 아니다)
- 명중에서 **위로 솟는 꺾쇠**가 보인다 — "회복됐다"가 형태로 읽힌다
- 발사·비행·명중·사거리 마커 **네 구간의 초록이 같은 계열로 보인다**
- 적 공격 투사체와 색·형태가 구분된다
- 2초 간격 연속 발사에서 발사 연출이 겹쳐 쌓이지 않는다
- **발사·명중 연출이 타워에 가려지지 않는다** (정렬 레이어를 맞췄으므로)
- 명중 연출이 뒤집혀 땅을 향하지 않는다 (`_rotateImpactToTravelDirection false`)
- **생명 타워를 클릭하면 초록 사거리 마커가 뜬다** (선과 함께 — 새끼용 공격 범위와 같은 방식)
- **인구를 옮기거나 연구로 사거리가 바뀌면 마커가 따라 커진다** (유효 사거리를 쓰므로)
- 다른 타워(활·석궁 등)를 클릭하면 마커가 안 뜬다 (`_attackRangeMarkerPrefab` 미배선)
- 오라 타워를 클릭했을 때의 마커·구체 동작은 그대로다 (N4·N5 회귀 없음)

## 이력 상세 — 1차·2차에서 얻은 것

**3차에서도 유효한 측정·교훈이다. 다시 겪지 말 것.**

### 회전 보정 — `startRotationX = 0` (M0)

Hovl 마커는 자식 대부분이 Mesh 렌더 + `startRotationX: 90°`라
회전 0·정사영 카메라에서 **한 픽셀도 안 그려진다**(링 자식 전부 0픽셀).

| 보정 | 링 | 화살표·꼬리 |
|---|---|---|
| (a) `startRotationX=0` | 살아남 | **살아남** ← 채택 |
| (b) 루트 X −90 | 살아남 | **죽음** |

**전체 픽셀 수는 5,333 대 5,221로 비슷해 보였다.** 자식 단위로 재야 (b)가 화살표를
죽이는 것이 보인다 — 합만 보면 못 잡는다.

**새끼용 세션도 독립적으로 같은 결론에 도달했다**(`BuildBabyDragonRangeVfx` 227행).

### 맥동 평탄화 — 진폭과 빈도는 다른 축 (M2)

원인은 "주기 1초에 버스트 1회"라 입자가 같은 위상으로 태어나 같이 죽는 것이었다.

| 후보 | 변동폭 | 봉우리/초 |
|---|---|---|
| 원본 | 48% | 1.00 |
| 버스트 4등분 | 5% | **2.67** ← 진폭은 잡혔지만 더 어지러움 |
| **주기 ×3, 수명 ×12** | **7%** | **0.67** ← 채택 |

**변동폭만 재고 빈도를 안 재서 첫 시도가 "숫자상 성공"으로 보였다.**
지표를 하나만 잡으면 그 지표만 좋아진 답으로 수렴한다.

### ⚠️ 그 맥동 평탄화는 나중에 폐기됐다 (N4에서) ★

**위 표의 채택안(주기 ×3, 수명 ×12)이 실제 씬에서 너무 흐렸다.** 입자를 넓게 퍼뜨리면
변동폭은 잡히지만 순간 밝기가 그만큼 묽어진다. 마커는 새끼용과 같은 처리(원본 맥동 유지)로
다시 구웠다 — 설계 §4-0.

**교훈이 하나 더 붙는다: 굽는 판에서 잰 지표(변동폭·빈도)가 다 통과해도 "화면에서 밝은가"는
따로 봐야 한다.** M2는 그것을 안 봤다.

### 움직이는 자식에 수명을 곱하지 말 것 (M2)

수명 ×12를 걸면 움직이는 입자는 12배 멀리 간다. **출처가 `startSpeed` 하나가 아니다** —
fantasy 마커는 속도 0인데 `velocityOverLifetime` + `forceOverLifetime y=-2`로 움직여
**한없이 땅으로 꺼졌다**(낙하는 수명의 제곱에 비례).

`IsMoving`은 네 가지를 다 본다: `startSpeed` · `gravityModifier` ·
`velocityOverLifetime.enabled` · `forceOverLifetime.enabled`.

### 밝기·크기 지표는 위치 버그를 못 잡는다 (M2)

마커가 꺼지는 동안에도 변동폭·링 지름은 **전부 정상**이었다.
"얼마나 밝은가"와 "얼마나 넓은가"만 재고 **"어디에 있는가"를 아무도 안 봤다.**
→ 드리프트 검사(여러 시점의 세로 위치)를 넣었다.

### 가산 블렌드는 알파로 재면 안 된다 (M3)

셰이더가 `_Src=1 _Dst=1` 순수 가산이라 투명 배경에 구우면 알파가 0.03으로 읽힌다.
**세 번 연달아 틀렸다**: 임계 0.08 → "안 그려짐" / 임계 0.015 → 지름 0.4(실제 0.91) /
최대 알파 0.03 → "거의 투명".

**불투명 검정 배경 + 밝기(RGB 최대) 판정**으로 바꾸자 전부 제 값이 나왔다.

밝기를 올리는 손잡이도 색·알파가 아니라 **머티리얼 `_EmissionIntensity`**다.

### 시간 변화를 잴 때는 시드를 고정한다 (M2)

`useAutoRandomSeed = false` + 고정 시드. 안 그러면 인스턴스마다 위상이 달라
**시드 잡음을 시간 변동으로 오독한다**(링 지름이 4.03↔4.48로 흔들려 보였다).

### Building 레이어에는 뎁스 정렬이 있다 (M5)

작업노트 §4의 "정렬 레이어 안에 뎁스 정렬이 없다"는 **타워에는 해당하지 않는다.**
`Building.SetDepthSortOrder`가 `-(x+y)`를 넣고 `GridMap`이 세 경로에서 부른다.
→ 연출은 `tower.DepthSortOrder`를 따라가야 한다. **Overlay로 올리면 오히려 정렬을 잃는다.**

### Coplay `save_scene`이 씬을 복사한다 (M5)

씬 **이름**을 넘기면 원래 경로가 아니라 `Assets/` 루트에 **새 GUID로 사본**을 만든다.
원본은 변경 없이 남아 **"배선했는데 안 뜬다"**가 된다.

호출 후 `ls Assets/*.unity`로 확인할 것. 정리: 사본 내용을 원본 경로에 덮어쓰고 →
사본과 `.meta`를 지우고 → `open_scene`으로 원본을 다시 연다(원본 `.meta`를 건드리지 않아야 GUID가 산다).

### 컴파일 확인은 DLL 타임스탬프로 (M4·M5)

Coplay `check_compile_errors`는 캐시를 돌려줄 수 있다.
`Library/ScriptAssemblies/Assembly-CSharp.dll`이 **소스 수정 이후에** 재생성됐는지 본다.
