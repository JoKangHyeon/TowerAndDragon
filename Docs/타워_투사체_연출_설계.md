# 🎯 타워 투사체 연출 설계

작성일: 2026-08-20 · 최종 갱신: 2026-08-24 · 전체 현황: [구현 현황](./구현현황.md)

밤 전투에서 타워 종류마다 다른 투사체 연출(파티클 궤적 + 명중 이펙트)을 붙이기 위한 설계 문서입니다.
기획은 `기획종합_v2.md`가 우선합니다.

> 기본 투사체 풀링·`ProjectileVisual`·타워별 프리팹 배선은 구현됐습니다.
> 아직 확인되지 않은 항목은 [타워 투사체 연출 마일스톤](./타워_투사체_연출_마일스톤.md)의 상태를 따릅니다.
> 에셋(Hovl Studio Vol1·Vol2)은 이미 프로젝트에 임포트되어 있습니다.
> 실행 순서는 [타워 투사체 연출 마일스톤](./타워_투사체_연출_마일스톤.md)을 봅니다.

---

## 1. 한눈에 보는 전체 그림

```
[TowerAttack.Fire]
   │
   ▼
[PrefabPool.Spawn]  ← TowerData._projectilePrefab (타워별 전용 프리팹)
   │                  풀이 씬에 없으면 Instantiate로 fallback
   ▼
[Projectile.Launch] ──▶ [ProjectileVisual.OnLaunched]
   │                       궤적 파티클 Clear 후 Play
   │
   ▼ (MoveTowards로 타겟 추적)
[명중] ──▶ [AttackSO.Execute] 피해 적용
   │
   ├──▶ [ProjectileVisual.OnHit] 궤적 정지 + 명중 이펙트 스폰
   │        └─▶ [PrefabPool.PlayForSeconds] 수명 후 자동 반납
   │
   └──▶ [PrefabPool.Release] 투사체 본체 반납
```

**연출 범위**: 타워 7종의 투사체 본체 + 궤적, 명중 이펙트. + TimeTower 마법진(§4-4, 투사체 아님).

**범위 밖**: 발사(머즐) 이펙트 · **새끼용(`BD_*`)** · 몬스터.
뒤 둘은 연출을 안 바꿔도 §8의 코드 이관 영향은 받는다 — 옛 프리팹은 지우지 않고 그대로 둔다.

## 2. 현재 구조

### 2-1. 데이터

`TowerData`에 이미 투사체 필드가 있습니다.

```csharp
[Header("Projectile")]
[SerializeField] private GameObject _projectilePrefab;
[SerializeField] private float _projectileSpeed;

public bool HasProjectile => _projectilePrefab != null && _projectileSpeed > 0;
```

- `ElementalTowerData`·`BabyDragonData`가 `TowerData`를 상속하므로 같은 필드를 그대로 씁니다.
- **`MonsterData`는 `TowerData`를 상속하지 않고** 같은 이름의 필드를 따로 가집니다. `Projectile` 클래스만 공유합니다.

### 2-2. 지금 배선된 투사체 프리팹

| TowerData | 프리팹 | 속도 |
|---|---|---|
| TD_Arrow | ProjectileView | 10 |
| TD_CrossBow | ProjectileView | 10 |
| TD_Musket | ProjectileView | 10 |
| TD_Anti_Air | ProjectileView | 10 |
| TD_FireTower | Projectile_Fire | 10 |
| TD_IceTower | Projectile_Ice | 10 |
| TD_StoneTower | Projectile_Stone | 5 |
| TD_TimeTower | (없음) | 0 |

- 앞의 4종이 공용 `ProjectileView` 하나를 공유합니다 — 타워별 연출을 넣으려면 여기부터 분리해야 합니다.
- `TD_TimeTower`는 `_attack`이 비어 있어(`CanAttack == false`) 공격 자체를 하지 않습니다. 대상 아님.

### 2-3. 프리팹 구조

`Projectile_Fire`를 포함해 현재 투사체 프리팹은 전부 단일 GameObject입니다.

```
Projectile_Fire
├── SpriteRenderer (Sorting Order 1)
├── Light2D
└── Projectile
```

**프로젝트 코드 어디에도 `ParticleSystem` 사용 사례가 없습니다.** 이번이 처음입니다.

## 3. 지금 막혀 있는 것

1. **`Projectile.Update`가 명중 즉시 `Destroy(gameObject)`** → 궤적·명중 파티클이 재생 도중 잘려나갑니다.
2. **발사마다 `Instantiate`/`Destroy`** → 파티클 프리팹은 스프라이트보다 Instantiate 비용이 큽니다. 밤 웨이브에서 타워 여러 개가 동시에 쏘면 프레임 튐이 생깁니다.
3. **연출 훅이 없습니다** — `Projectile`에 발사/명중 시점을 시각 컴포넌트에 알릴 지점이 없습니다.
4. **`Projectile`이 진행 방향으로 회전하지 않습니다** — §5에서 별도로 다룹니다. 이번 작업의 필수 요구사항입니다.
5. **`_isLaunched`가 한 번 true가 되면 false로 안 돌아갑니다** — 풀링으로 재사용하려면 상태 초기화가 필요합니다.

## 4. 사용할 에셋 — Vol1 vs Vol2 (M5에서 확정)

> **두 팩 모두 이미 프로젝트에 임포트되어 있습니다** — `Assets/Imported/Hovl Studio/` (571 파일).
> 임포트 작업은 이미 끝난 상태입니다.

Downloads의 이펙트 패키지 4종을 비교했습니다.

| 패키지 | 프리팹 수 | 2D 지원 | 판정 |
|---|---|---|---|
| **AAA Stylized Projectiles Vol1** (Hovl) | 163 | **`Projectiles 2D/` 27종 전용** + 2D 데모 씬 + `HS_ProjectileMover2D` | **기본안** |
| AAA Projectiles Vol2 (Hovl) | 72 | 3D 기반 (파티클 자체는 렌더됨) | **M5에서 Vol1과 비교** (§4-6) |
| Unique Projectiles Vol 2 (Gabriel) | 180 | Demo2D 씬은 있으나 프리팹은 3D 공용 | 보조 |
| Archer Pack | 96 (VFX) | 없음. `.fbx` 화살 모델 기반 | 부적합 |

### 4-1. Vol1이 기본안인 이유

`2D Projectile 16 fire.prefab` 구조:

```
2D Projectile 16 fire
├── ParticleSystem ×3 (본체 + SubSmoke + SubSparks)
├── Rigidbody2D + CircleCollider2D    ← 2D 물리
└── HS_ProjectileMover2D
```

- **`Rigidbody2D` / `CircleCollider2D`** — 처음부터 2D판입니다. 다른 팩은 3D 컴포넌트를 걷어내야 합니다.
- **Mesh 파티클이 0개** — 전부 Billboard(0) / Stretched(1)입니다. 아이소 각도에 따라 실루엣이 변하는 변수가 없습니다.
- `m_RenderMode: 1`(Stretched Billboard)이 섞여 있어 진행 방향 늘림이 이미 잡혀 있습니다.
- 27종이 **`Projectile` / `Flash` / `Hit` 3종 세트로 짝이 맞습니다.** 우리 설계의 궤적 + 명중 이펙트 구조와 그대로 대응됩니다.

> **다만 "기본안"이지 확정이 아닙니다.** Vol2가 비주얼로 더 나을 수 있고,
> 그 판단은 아이소 화면에서만 가능합니다 — §4-6, M5 참조.

### 4-2. ⚠️ `HS_ProjectileMover2D`는 쓰지 않습니다

에셋에 딸려온 무버 스크립트는 우리 `Projectile`과 정면 충돌합니다.

| 항목 | HS_ProjectileMover2D | 우리 Projectile |
|---|---|---|
| 이동 | `rb.linearVelocity = forward * speed` (직진) | `MoveTowards`로 타겟 추적 |
| 명중 판정 | `OnCollisionEnter2D` (물리 충돌) | 도착 지점 도달 |
| 피해 | 없음 (연출 전용) | `AttackSO.Execute` |
| 수명 | `Start()`에서 `Destroy(gameObject, 5)` | 명중 시 반납 |

**작업 절차**: 각 프리팹을 복제한 뒤 복제본에서
`HS_ProjectileMover2D` · `Rigidbody2D` · `CircleCollider2D`를 **제거**하고,
우리 `Projectile` + `ProjectileVisual`을 붙입니다. **파티클 자식만 가져다 씁니다.**

### 4-3. 타워별 아트 방향 (기획 확정 2026-08-20)

각 타워가 **무엇처럼 보여야 하는지**입니다. 구체적인 프리팹 매핑은
[마일스톤 문서](./타워_투사체_연출_마일스톤.md)의 M6에 있고, 그쪽이 최신입니다.

| 타워 | 타워 성격 | 원하는 느낌 |
|---|---|---|
| TP_Arrow | 기본 화살 타워 | 일반 화살 |
| TP_CrossBow | 화살 타워 | 특수 화살 (일반과 구분) |
| TP_Musket | 공격 범위가 넓은 타워 | 둔탁해 보이는 총알 |
| TP_Anti_Air | 비행 적 전용 | 총알 |
| TP_FireTower | 불 속성 | 불 |
| TP_IceTower | 얼음 속성 | 얼음 화살 또는 총알 |
| TP_StoneTower | 공격력 강 · 공속 느림 | 메테오 |
| TP_TimeTower | 버프(주변 공속 +20%) | **마법진** — §4-4 참조 |

### 4-4. ⚠️ TimeTower는 투사체가 아닙니다

`TD_TimeTower.asset`은 `_attack: {fileID: 0}`이라 **공격을 하지 않습니다**(`CanAttack == false`).
`TowerAttack`이 아예 돌지 않으므로 `Projectile`·`ProjectileVisual`·`PrefabPool` 어느 것도 쓰이지 않습니다.

필요한 것은 **타워 발밑에 상시 떠 있는 오라 표시**입니다. 확인된 현재 상태:

- `TowerAuraDataSO`는 수치만 들고 있습니다 (`_radius: 2`, `_attackSpeedMultiplier: 1.2`). 시각 필드 없음
- `TowerAuraSystem`도 렌더링을 하지 않습니다
- 즉 **오라를 그리는 코드가 프로젝트에 전혀 없습니다.** 지금은 눈에 보이지 않는 버프입니다

이 작업은 성격이 달라 마일스톤 **M7로 분리**했습니다. 접근 두 갈래(프리팹 자식 vs 오라 시각화 컴포넌트)와
판단 근거는 그쪽에 있습니다.

### 4-5. 프리팹 저작 시 주의

- **원본은 `Assets/Imported/Hovl Studio/` 아래에 그대로 둡니다.** 외부 VFX를 가공한 타워용 복제본은
  `Assets/Imported/Prefabs/Projectile/Tower/`에 저장하며 원본을 덮어쓰지 않습니다.
- `Hit` 프리팹은 `ParticleSystem` ×5짜리도 있습니다. 아이소 타일 위에서 과한지 확인하고 필요하면 자식을 덜어냅니다.
- 라이선스: Hovl Studio 에셋은 readme에서 상업적 사용을 허용합니다 ("can be used in commerce, even demo scene files").

### 4-6. Vol2 — M5에서 Vol1과 비교 후 결정

Vol2의 `Projectile *` 프리팹이 **발사(Flash) · 투사체 · 명중(Hit)을 한 프리팹에 다 담고 있는 것은 맞습니다.**
`Projectile 4 fire.prefab`을 뜯어보면:

```
Projectile 4 fire
├── HS_ProjectileMover        ← hit / hitPS / flash / projectilePS / Detached 를 전부 참조
├── Rigidbody (3D)            ← Rigidbody2D 아님
├── SphereCollider (3D)       ← CircleCollider2D 아님
├── Light (3D)                ← Light2D 아님
└── Visuals
    ├── Fire · Glow · ShockWave · Conus  (ParticleSystem ×5, 그중 Mesh 2개)
    ├── [중첩 프리팹] Flash 4   ← 발사 이펙트
    └── [중첩 프리팹] Hit 4     ← 명중 이펙트
```

**파티클은 정상으로 보입니다.** 머티리얼이 `HS_Blend_CG.shadergraph`(URP Shader Graph)라
`Renderer2D`에서도 렌더됩니다. 프리팹 미리보기에서 보이는 것이 맞습니다.

3D 컴포넌트들의 실제 영향은 이렇습니다:

| 컴포넌트 | 실제 영향 |
|---|---|
| `Light` (3D) | **이것만** `Renderer2D`에서 무시됨 — 파티클이 아니라 **부가 조명**이라 없어도 그림은 그대로 |
| `Rigidbody` · `SphereCollider` | `HS_ProjectileMover`를 안 쓰면 아무 일도 안 함. 제거하면 끝 |
| Mesh 파티클 (`Conus.fbx` 등) | 렌더는 됨. 다만 3D 메시라 **회전 각도에 따라 실루엣이 달라짐** ← 유일한 실제 변수 |

**번들 구조는 이점이 되지 못합니다.** `hit`/`flash`/`Detached` 배선이 전부
`HS_ProjectileMover`의 필드에만 있는데, 그 스크립트는 `OnCollisionEnter`(3D 물리) 명중 판정 +
`rb.linearVelocity` 직진 이동이라 §4-2와 같은 이유로 우리 `Projectile`과 못 씁니다.
**스크립트를 떼는 순간 배선도 같이 날아가고**, `ProjectileVisual`에 다시 잡아야 합니다 —
Vol1과 작업량이 같아집니다.

**그래서 남는 쟁점은 하나입니다**: *3D Mesh 파티클이 아이소 직교 카메라에서 어떻게 보이는가.*
이건 문서로 판단할 수 없고 화면으로만 판단됩니다.
**M5 파일럿에서 Fire 하나를 Vol1판·Vol2판 둘 다 만들어 비교하고 채택합니다.**

| | Vol1 `2D Projectile 16 fire` | Vol2 `Projectile 4 fire` |
|---|---|---|
| ParticleSystem 수 | 3 | 5 (+ Flash·Hit 중첩) |
| **Mesh 파티클** | **0** | **2** |
| 물리 | `Rigidbody2D` · `CircleCollider2D` | `Rigidbody` · `SphereCollider` |
| 조명 | 없음 | `Light` (3D, 무시됨) |

참고로 카메라는 `orthographic: 1`, 렌더러는 `Assets/Settings/Renderer2D.asset`으로 확인했습니다.

### 4-7. Vol2의 "번들 구조"는 우리 설계에 이미 반영돼 있습니다

Vol2가 하려던 것과 우리 설계는 이렇게 대응됩니다.

| Vol2 (`HS_ProjectileMover`) | 우리 설계 |
|---|---|
| `projectilePS` | `ProjectileVisual._trailParticles` |
| `hit` + `hitPS` | `ProjectileVisual._impactPrefab` (§9) |
| `flash` | 이번 범위 밖 (머즐 이펙트) |
| `notDestroy: 1` (비활성화 재사용) | `PrefabPool` (§6) |
| `OnEnable`에서 `Clear(true)` → `Play(true)` | `ProjectileVisual.OnLaunched` (§9) |
| `Detached` (명중 후 자식 분리) | **채택 안 함** — §9의 경고 참조 |

`OnEnable`에서 `Clear` 후 `Play`하는 것은 Hovl도 같은 결론에 도달했다는 뜻입니다 —
§9에서 Clear를 강조한 이유(재사용 시 궤적이 늘어짐)가 실제 문제라는 방증입니다.

## 5. ⚠️ 발사 방향 — 필수 요구사항

**투사체와 이펙트가 적이 있는 방향을 향해야 한다.** 지금 `Projectile`은 회전을 전혀 하지 않아 이대로는 만족하지 못합니다.

### 5-1. 왜 그냥은 안 되는가

임포트할 프리팹은 **3D 전제**로 만들어졌습니다. `2D Projectile 16 fire`를 뜯어보면:

- 프리팹 루트 자식에 **Y축 90° 회전이 구워져 있습니다** (`m_LocalRotation: {y: 0.7071, w: 0.7071}`)
- 메인 파티클이 **Cone 이미터**(`type: 5`, `angle: 25`)라 **로컬 +Z 방향**으로 뿜습니다
- 에셋 readme 명시: *"Projectile should face forward in the Z direction for correct movement."*

우리 게임은 2D 아이소메트릭이라 **Z축 회전(`Quaternion.Euler(0, 0, angle)`)** 으로 화면상의 방향을 바꿉니다.
3D 전제의 +Z 전방과는 축이 다릅니다.

### 5-2. 해결

**`Projectile`에 방향 회전을 추가합니다.**

- `Launch` 시점과 이동 중(타겟이 움직이므로) 진행 방향으로 루트를 회전시킵니다
- 회전은 **Z축 단일 회전**입니다: `Quaternion.Euler(0, 0, Mathf.Atan2(dir.y, dir.x) * Mathf.Rad2Deg)`
- 매 프레임 갱신할지, `Launch` 때 한 번만 잡을지는 M5 파일럿에서 눈으로 보고 정합니다
  (추적 투사체라 타겟이 이동하면 방향이 바뀝니다)

**프리팹 쪽에서 축을 맞춥니다.**

- 임포트 프리팹의 자식에 구워진 Y축 90° 회전을 걷어내고, 파티클 방출이 **로컬 +X**를 향하도록 맞춥니다
  (`Atan2` 기준 0°가 +X이므로)
- Cone 이미터의 방향, `ParticleSystemRenderer`의 Stretched Billboard 정렬을 함께 확인합니다

### 5-3. 아이소메트릭 보정은 하지 않습니다

`IsometricMath.RADIUS_Y_RATIO`는 0.5입니다. 타일이 세로로 눌려 있어 **사거리 판정은 타원**을 씁니다
(`TowerAttack.IsWithinAttackRange`).

하지만 투사체 회전은 **화면상 실제 이동 방향**을 그대로 따르면 됩니다 —
`MoveTowards`가 월드 좌표에서 직선으로 가므로 화면에서도 직선이고, 그 각도가 곧 보이는 각도입니다.
여기에 타원 보정을 넣으면 오히려 궤적과 어긋납니다.

### 5-4. 명중 이펙트의 방향

`Hit *` 프리팹도 방향성이 있는 것이 섞여 있습니다(폭발형은 무관, 튀는 형태는 유관).
`ProjectileVisual.OnHit`에서 **명중 시점의 진행 방향을 이펙트에 전달**해 같은 각도로 스폰합니다.

## 6. `PrefabPool` — 프리팹 단위 GameObject 풀 (신규)

`Assets/Scripts/Util/PrefabPool.cs`

`SoundManager`와 같은 **정적 접근점** 패턴을 씁니다. 이유도 같습니다 — 호출자 대부분이 런타임에 Instantiate되는 프리팹(타워·몬스터·투사체)이라 씬 오브젝트를 `SerializeField`로 주입할 수 없습니다.

**씬에 없으면 fail-open**: `Instantiate`/`Destroy`로 그대로 동작합니다. 팀원 테스트 씬과 튜토리얼 씬에 새 필수 배선을 만들지 않습니다.

### API

```csharp
static GameObject Spawn(GameObject prefab, Vector3 position);
static void Release(GameObject instance);
static void PlayForSeconds(GameObject prefab, Vector3 position, float seconds);  // 명중 이펙트용
```

### 내부

- `Dictionary<GameObject, ObjectPool<GameObject>>` (프리팹 → 풀). `UnityEngine.Pool.ObjectPool<T>` 사용
- 인스턴스에 `PooledInstance` 마커 컴포넌트를 생성 시점에 붙여 원본 프리팹 키를 보관합니다.
  마커가 없는 인스턴스를 `Release`하면 `Destroy` — fallback 경로와 섞여도 안전합니다.
- `PlayForSeconds`의 지연은 **풀 자신의** `GetCancellationTokenOnDestroy()`로 돕니다.
  풀링된 오브젝트는 파괴가 아니라 반납이므로 그쪽 토큰을 쓰면 취소가 안 걸립니다.
- `[WiringOptional] GameObject[] _prewarmPrefabs` + `PREWARM_COUNT_PER_PREFAB`로 첫 발사 히칭 제거
- `OnDestroy`에서 `_current = null` (`SoundManager`와 동일)
- 프리팹 검증(`Projectile` 컴포넌트 유무)은 **풀 생성 시 1회**. 발사마다 `GetComponent` + 에러 경로를 타지 않습니다.

## 9. `ProjectileVisual` — 연출 담당 (신규)

`Assets/Scripts/Combat/ProjectileVisual.cs`, 투사체 프리팹 루트에 붙입니다.

```csharp
[SerializeField] private ParticleSystem[] _trailParticles;   // 궤적, 프리팹 자식
[WiringOptional]
[SerializeField] private GameObject _impactPrefab;           // 비우면 조용히 생략
[SerializeField] private float _impactLifetimeSeconds = DEFAULT_IMPACT_LIFETIME_SECONDS;
```

- **`OnLaunched()`**: `Clear(withChildren: true)` **후** `Play(true)`
  > Clear를 빼면 world-space 파티클이 재사용 시 직전 명중 지점에서 새 발사 지점까지 줄을 긋습니다.
- **`OnHit(launchPosition, hitPosition, direction, targetObject)`**:
  `Stop(true, StopEmittingAndClear)` 후 근거리 트레이서와 명중 이펙트를 재생합니다.
  명중 이펙트는 선택한 시각 위치에 **진행 방향 각도로** 스폰합니다(§5-4, §9-1~§9-2).

> **궤적은 떼어내지 않습니다.**
> `HS_ProjectileMover2D`는 명중 시 자식을 unparent해서 파티클을 마저 재생시키지만, 그러면 풀이 자식 하나가 사라진 오브젝트를 돌려받습니다.
> "명중 후에도 남는 연출"은 궤적 잔상이 아니라 **별도 명중 이펙트**가 담당합니다 —
> `VillagerDispatchSystem`의 `_conquestCompletionEffectPrefab` + `_conquestCompletionEffectLifetimeSeconds`와 같은 구조입니다.

### 9-1. Impact 위치 정책 — 몬스터 데이터가 아니라 발사체 연출이 선택

타워마다 어울리는 명중 위치가 다르므로 단일 `HitVfxAnchor`를 몬스터 데이터에 넣지 않습니다.
`ProjectileVisual`이 프리팹별로 다음 정책을 선택합니다.

| 정책 | 위치 | 용도 |
|---|---|---|
| `TargetOrigin` | 기존 논리 명중 위치 | 기본값. 기존 발사체 동작 보존 |
| `Body` | 대상 `SpriteRenderer.bounds.center` | 머스킷·화살처럼 몸통에 맞는 연출 |
| `Ground` | 대상 `SpriteRenderer.bounds.min.y` | 운석·균열·장판처럼 지면에서 시작하는 연출 |

대상 스프라이트를 찾지 못하면 모두 기존 논리 명중 위치로 폴백합니다. 이 위치 선택은
`AttackSO.Execute`·광역 피해 중심·타겟 판정에는 관여하지 않고 **Impact VFX의 스폰 위치에만** 적용합니다.
따라서 몬스터 데이터 에셋과 몬스터 프리팹의 일괄 수정이 없습니다.

### 9-2. 공격 투사체 타워 7종의 근거리 보조 트레이서 (v2 — 2026-08-24 개정)

아이소메트릭 화면에서 몬스터가 타워와 가깝거나 화면상 거의 수직으로 놓이면 투사체가 2~3프레임 만에
명중하고, `OnHit`이 궤적을 즉시 비워 비행 연출을 읽기 어렵습니다. 특정 타워의 문제가 아니므로
공격 투사체를 사용하는 타워 7종에 공용 보조 연출을 사용합니다.
아군 회복을 담당하는 Life 타워 투사체는 이번 보완 범위에서 제외합니다.

#### v1은 왜 부족했나 (다시 도입하지 말 것) ★

v1은 **방향(수직 여부)**으로 보정 대상을 골랐습니다. 이것이 틀린 축이었습니다.

- **"수직"은 원인이 아니라 증상입니다.** 수직이 안 보인 이유는 방향이 아니라 그 방향에서
  **선이 짧아지기** 때문입니다. `RADIUS_Y_RATIO = 0.5`에 FirePoint 높이(0.41월드)가 겹쳐
  상방 사격은 횡 대비 화면 길이가 **1:2.5**가 됩니다.
- `|dx| ≤ |dy| × 0.25`는 수직에서 **14° 원뿔**뿐이라 20~45°의 "위쪽 접근"은 보정을 0 받았고,
  경계에서 폭·밝기가 25% 튀는 **계단**이었습니다.
- 방향으로 고르니 **횡 근거리(옆 칸 = 57px)가 48px 게이트에 걸려 아무것도 못 받는** 구멍이 남았습니다.
- 폭·밝기 1.25배는 길이 0.4배를 보상하지 못합니다(발광 면적 0.5배).
- 밝기 배율은 실질 무효였습니다 — 코어가 이미 흰색이고 머티리얼이 가산이 아닙니다.

수치 근거와 나머지 원인(⑥ 밝기 무효, ⑦ 테이퍼 방향, ⑨ 배속, ⑩ 문서 불일치)은
**`Docs/타워이펙트_작업노트.md` 5-1**에 있습니다. 여기서 되풀이하지 않습니다.

#### v2 규칙

1. `Projectile`은 발사 위치를 보관하고 기존 속도·직선 이동·**피해 시점을 그대로 유지**합니다.
2. `ProjectileVisual`은 명중 시 발사점과 시각적 Impact 위치를 화면 좌표로 변환합니다.
3. **강도는 방향이 아니라 화면 길이 부족분으로 정합니다** (연속 램프, 계단 아님).

   ```
   t = 1 − clamp01(screenLength / REFERENCE_LENGTH_PIXELS)
   ```

   **`t`는 알파만 스케일합니다. 폭은 px 저작값 그대로 둡니다.**
   길수록 약해지고 길이가 충분하면 아예 나오지 않습니다.

   > ⚠️ 초안은 "`t`가 폭과 알파를 함께"였고 **측정에서 뒤집혔습니다.**
   > 낮은 `t`에서 폭까지 줄이면 선이 서브픽셀이 되어 통째로 사라집니다
   > (`t` 0.10 → 폭 0.86px → 그려진 픽셀 **0**). 근거는 작업노트 5-3-1 ③.

   측정으로 확정된 값: `REFERENCE_LENGTH_PIXELS = 280` ·
   `MIN_TRACER_SCREEN_LENGTH_PIXELS = 64` · `NEAR_TRACER_MAX_ORTHO_SIZE = 10`
   (근거: 작업노트 5-3-1 ②④⑥). **`MIN_EFFECTIVE_T`는 아직 미정이며 규칙 6에 함께 있습니다 —
   확정 3개만 보고 구현하면 가드 없이 출하됩니다.**
4. **선 폭은 px로 저작하고** 매 재생마다 카메라에서 월드 폭을 역산합니다.

   ```csharp
   float worldPerPixel = 2f * worldCamera.orthographicSize / worldCamera.pixelHeight;
   ```

   `Screen.height`가 아니라 `pixelHeight`입니다 — `WorldToScreenPoint`와 같은 픽셀 공간이어야
   레터박스·렌더 텍스처에서 게이트와 폭이 어긋나지 않습니다.
   `worldLength / screenLength`로 유도하면 **고치려는 퇴화 케이스에서 0으로 나눕니다.**
5. 길이가 `MIN_TRACER_SCREEN_LENGTH_PIXELS` 미만이면 **끝점(몬스터)을 고정하고 시작점을 뒤로 늘립니다.**
   방향은 종점−시작점이 아니라 **항상 `_travelDirection`**을 따릅니다 —
   그래야 `Ground` 정책이 상방 근거리에서 만드는 **부호 반전**(트레이서가 아래를 향하는 현상)이 풀립니다.
6. **줌 아웃 가드** — 3·4·5가 겹치면 최대 축소에서 모든 사격이 트레이서를 받습니다
   (ortho 18에서는 횡 최대 사격도 121px). 세 겹으로 막습니다.
   - `orthographicSize > NEAR_TRACER_MAX_ORTHO_SIZE`(= 10)면 건너뜀 —
     그 위에서는 횡 최대 사격에도 `t`가 붙기 시작하고 최소 길이가 타워 스프라이트의 2~3.5배가 됩니다
   - 5의 연장 길이에 월드 상한 — **허용 줌 범위 안에서는 물리지 않는 예비 가드입니다**
     (ortho 10에서 최소 길이 1.185월드 vs 상한 1.2). 실제로 동작하는 가드는 나머지 둘입니다
   - `t < MIN_EFFECTIVE_T`면 건너뜀 (풀 대여 폭증 방지).
     **이 가드는 선택이 아닙니다** — 기준 280px은 사거리 안 사격의 **70%**에 `t > 0`을 주므로,
     빠뜨리면 "보조 연출"이 상시 연출이 됩니다. 출발점은 0.2~0.3 (작업노트 5-3-1)
7. 트레이서는 흰색 코어와 타워별 색상의 글로우 두 줄이며, **몬스터 쪽이 밝고 타워 쪽으로 흐려집니다.**
   (v1은 반대였습니다. 5의 시작점 연장은 이 방향이라야 "화면 밖에서 들어온 섬광"으로 읽힙니다.)

   **이것은 선택이 아니라 3의 전제 조건입니다.** 총픽셀은 그대로인데 몬스터 쪽 밀도가
   34~38% → 62~64%로 1.7배가 되고, 무엇보다 **낮은 `t`에서는 현재 테이퍼가 몬스터 쪽을
   임계값 아래로 깎아 버려** 램프 자체가 무의미해집니다(작업노트 5-3-1 ⑤).
8. ~~머티리얼은 **가산 블렌딩**입니다.~~ **보류됐습니다 (2026-08-24).**

   > 이 규칙의 근거는 "밝기 배율이 클램프돼 무효"였는데, **v2는 밝기 배율을 아예 쓰지 않습니다**
   > (강도를 알파로만 표현합니다). 근거가 재설계에 흡수돼 사라진 것이며, 시간이 없어 미룬 것이 아닙니다.
   > 남은 이점은 측정 근거 없는 취향 문제이고, `Mat_Tracer_Tower_Near`는 팀원 전원이 받는
   > 머티리얼입니다. 자세한 판단은 작업노트 5-5.
9. 트레이서는 명중 뒤 독립적으로 남으므로 투사체 본체가 즉시 풀에 반납돼도 잘리지 않습니다.

보조 트레이서는 경로를 휘게 만들거나 투사체를 느리게 하지 않습니다.
공용 트레이서 프리팹 하나를 공유하되 `ProjectileVisual`이 넘기는 글로우 색과
Impact 위치 정책으로 타워별 성격을 보존합니다.

> ⚠️ **의도적인 동작 변경**: 긴 상방 사격(약 172px)은 v1에서 트레이서가 없었지만
> v2에서는 약하게 붙습니다. 원치 않으면 `REFERENCE_LENGTH_PIXELS`를 낮춰 되돌립니다.

#### 손대지 않는 것

- **사거리 판정** — `IsWithinAttackRange`는 `transform.position` 기준, 발사는 `_firePoint.position`
  기준이라 상방 0~0.41월드에 데드밴드가 있습니다. FirePoint 기준으로 바꾸면 사라지지만
  **밸런스가 바뀝니다.** 연출 문제를 밸런스로 풀지 않고 규칙 5(최소 길이 보장)로 흡수합니다.
- **피해 시점 · 투사체 속도 · 경로**
- **`rateOverDistance`** — 월드 거리당 방출이라 상방에서 그대로 절반이 됩니다.
  손실과 **같은 축**이라 올려도 비율이 안 바뀝니다. (v1 문서의 "3→12"는 7종 중 1종만 적용됐고,
  애초에 방향이 틀린 처방이었습니다.)

### 9-3. 타워별 설정

공용 근거리 트레이서:
`Assets/Imported/Prefabs/Projectile/Tower/Tracer_Tower_Near.prefab`

**타워에 트레이서를 켜는 방법**은 `WireNearTracerTuning.TRACER_ENABLED`에 한 줄 추가하고
스크립트를 다시 돌리는 것뿐입니다 — 코드 변경도 프리팹 손배선도 없습니다.
끄는 것은 그 줄을 빼면 됩니다.

값싼 이유는 `PlayNearTracer`가 `_nearTracerPrefab`이 널이면 그냥 빠져나오기 때문입니다.
분기도 플래그도 타워별 코드도 없습니다. 튜닝 참조는 꺼진 타워에도 남겨
"의도된 꺼짐"과 "배선 누락"을 구분합니다.

**트레이서는 기본이 꺼짐이고 머스킷에만 켜져 있습니다** (2026-08-24 정책 전환).
7종 전부에 붙였던 것이 처음 구현이었으나, 플레이 확인에서 **다른 타워는 트레이서 없이도
근거리에서 잘 보인다**는 것이 드러났습니다. 트레이서는 머스킷 문제를 풀려고 만든 장치입니다.

| 타워 | Impact 정책 | 트레이서 | 글로우 계열 |
|---|---|---|---|
| **Musket** | `Body` | **켜짐 ★** | 오렌지 |
| Arrow | `Body` | 꺼짐 | 파랑 |
| CrossBow | `Body` | 꺼짐 | 밝은 노랑 |
| AntiAir | `Body` | 꺼짐 | 전기 청록 |
| Fire | `Ground` | 꺼짐 | 주황·빨강 |
| Ice | `Ground` | 꺼짐 | 얼음 청록 |
| StoneMeteor | `Ground` | 꺼짐 | 보라 |

Impact 정책과 글로우 색은 **꺼진 타워도 유지합니다** — 나중에 켤 때 그대로 살아납니다.

**튜닝값은 프리팹에 두지 않습니다.** v1은 `48 / 0.1 / 0.25 / 1.25 / 1.25`를 7개 프리팹에 복제해
한 값을 고치려면 7곳을 고쳐야 했습니다. v2는 `NearTracerTuningSO` 하나에
기준 길이 · 최소 길이 · 폭(px) · 수명 · 줌 상한 · `MIN_EFFECTIVE_T`를 모으고,
프리팹은 **그 SO 참조와 글로우 색만** 갖습니다.

> ⚠️ **구현 순서**: `_verticalScreenRatio` · `_verticalWidthMultiplier` ·
> `_verticalBrightnessMultiplier` 세 필드는 **SO가 생기고 7개 프리팹이 이관된 뒤에** 지웁니다.
> 먼저 지우면 유니티가 직렬화 값을 조용히 버립니다.
> `ProjectileImpactPlacement`의 "새 값은 항상 끝에만 추가한다" 주석과 같은 규율입니다.

#### 저장소가 갈립니다 ★

코드는 메인, **프리팹·머티리얼은 `Assets/Imported`(팀 공유 private 저장소)**입니다.
특히 가산 블렌딩 변경은 팀원 전원이 그대로 받는 머티리얼을 바꿉니다.
`git -C Assets/Imported commit`을 따로 하지 않으면 팀원 화면에서만 구버전이 돕니다.
파일별 대조표는 `Docs/타워이펙트_작업노트.md` 5-4에 있습니다.

#### 배속은 미결입니다

`ProjectileTracerVisual.Update`(페이드)와 `ProjectilePool.ReleaseEffectAfterAsync`(반납)는
**독립된 두 시계**이고 지금은 같은 값을 받아 우연히 일치합니다.
unscaled로 간다면 `UniTask.WaitForSeconds`에도 `ignoreTimeScale: true`를 함께 줘야 합니다 —
**둘 다거나 둘 다 아니거나.** 3배속에서 트레이서가 게임 시간으로 3배 오래 남아 겹치는 문제가 있어
**unscaled로 확정했습니다(2026-08-24)** — `Update`는 `Time.unscaledDeltaTime`,
반납은 `UniTask.WaitForSeconds(..., ignoreTimeScale: true)`입니다. `ignoreTimeScale`은
트레이서에만 줍니다 — 명중 이펙트는 게임 시간에 묶여야 배속에서 전투와 함께 빨라집니다.
겹침 여유 근거는 작업노트 5-5.

## 12. 구현 후 검증 절차

1. 컴파일 에러 0
2. `SampleScene` 플레이 → 밤 진입 → 타워 종류별 투사체가 각각 다른 연출로 날아가는지
3. **재사용 검증** — 같은 타워가 연속 발사할 때 궤적이 직전 명중 지점에서 늘어지지 않는지 (§9 Clear 누락 확인)
4. **몬스터 투사체 확인** — 원거리 몬스터가 성·타워를 공격할 때 null 없이 동작하는지.
   §8 풀 통일이 깨지면 여기서 먼저 터집니다.
5. `PrefabPool`이 없는 씬(팀원 테스트 씬)에서도 투사체가 정상 발사되는지 (fail-open)
6. Profiler로 밤 웨이브 중 GC Alloc 비교 (풀링 전/후)
7. **파티클 정렬** — 임포트한 프리팹의 `ParticleSystemRenderer` Sorting Order는 전부 **0**이고,
   기존 투사체 `SpriteRenderer`는 **1**입니다. `IsometricMath.ComputeDepthSortOrder` 기준 아이소 뎁스에서
   파티클이 타일·건물 뒤로 숨지 않는지 프리팹마다 확인해야 합니다.
8. **발사 방향** (§5) — 타워를 기준으로 **동서남북 네 방향**에 몬스터가 왔을 때 각각 확인합니다.
   한 방향만 보면 축이 뒤집혀 있어도 모릅니다.
   - 투사체 본체가 적을 향하는가
   - 궤적 파티클이 뒤로 흘러가는가 (앞으로 뿜으면 Cone 방향이 반대)
   - 명중 이펙트가 같은 각도로 뜨는가
9. `Tutorial` 씬도 확인 — 배선 누락 이력이 있는 씬입니다
