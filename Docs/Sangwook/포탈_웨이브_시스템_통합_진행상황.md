## 데이터 계층과 책임 경계 (지금도 그대로)

| 타입 | 책임 | 하지 않는 것 |
|---|---|---|
| `WaveDefinitionSO` | 한 밤에 실행할 포탈별 적 편성 전체 | 날짜·주기·난이도 계산 |
| `PortalWaveData` | 특정 포탈의 시작 지연 + 루트 편성 목록 | — |
| `RouteWaveData` | 그 포탈의 루트 하나에 배정된 스폰 그룹 | — |
| `SpawnGroupData` | 어떤 적을 몇 마리, 어떤 간격으로 | — |
| `Portal` | 씬의 공격로 하나(스폰 지점·경로·지형) | 날짜·주기·웨이브 선택·밤 종료 판단 |
| `WaveManager` | 웨이브 실행의 **단일 오케스트레이터** | 웨이브 선택 |

**핵심: 날짜와 주기를 웨이브 데이터에 넣지 않았습니다.**
`WaveDefinitionSO`에 `DayIndex`/`CycleIndex`를 두지 않고, 오늘 실행할 웨이브를 고르는 일은
별도 진행 시스템에 맡겼습니다. 당시 주기당 일수가 `[미정]`이라 공식을 데이터에 굳히지 않으려던
판단이었고, 결과적으로 나중에 `WaveCycleScheduleSO` + `WaveCycleProgression`이 그 자리에
그대로 들어왔습니다(주기당 7일 확정).

## 지연 시간 3종의 의미 구분

- `PortalWaveData.StartDelay` — 밤 시작 후 그 포탈 편성이 처음 실행되기까지
- `SpawnGroupData.DelayBeforeGroup` — 포탈 안에서 그 그룹이 시작되기 전
- `SpawnInterval` — 같은 그룹 안 개별 적 사이의 간격

`DelayAfterGroup`은 `DelayBeforeGroup`과 의미가 겹쳐 **의도적으로 두지 않았습니다.**

## 실행 규칙

- 서로 다른 포탈의 편성은 **병렬**(`UniTask.WhenAll`), 한 포탈 안의 그룹은 **순차**.
- 비활성·봉인 포탈은 실행 대상에서 제외.
- 웨이브가 지정한 포탈이 씬에 없으면 **조용히 무시하지 않고 오류 로그를 남깁니다.**

## 완료 이벤트를 둘로 나눈 이유

- `AllSpawnsCompleted` — 예약된 적을 전부 생성한 상태
- `AllMonstersDefeated` — 생성이 끝나고 생존 적도 0인 상태

**두 이벤트를 하나로 합치면 마지막 적을 생성하는 순간 밤이 끝납니다.**

## 보스를 분기로 하드코딩하지 않는다
보스 여부를 `WaveManager` 안의 `if`로 처리하지 않고, 웨이브 데이터와 `MonsterData`·프리팹 조합으로
표현합니다. 현재도 보스는 "주기 마지막 날 웨이브에 들어간 몬스터"일 뿐 특별 분기가 없습니다.

## 당시 예측했고 실제로 그렇게 된 것

- **포탈 상태 확장**: `bool IsActive` → Locked/Active/Sealed. 현재 `SetSpawnActive` + `Seal()`로 구현.
- **저장**: "낮 시작 체크포인트 저장을 우선하고, 밤 도중 저장은 별도 이슈" →
  현재 세이브가 정확히 그렇습니다(낮에만 저장 가능, 밤은 저장 대상 아님).
- **스폰 예고 UI**: "UI가 `WaveManager`의 비동기 작업을 직접 조사하지 않게" →
  현재 `PortalWavePreviewRenderer`가 `WaveRoutePlanner`의 결과를 읽습니다.

## 아직 유효한 것

- **오브젝트 풀링**: 초기엔 `Instantiate`/`Destroy`를 유지하고, 프로파일링에서 병목이 확인되면
  생성 책임을 팩토리로 추출해 교체한다 — **여전히 미적용**.
- `SpawnGroupData`가 `MonsterPrefab`과 `MonsterData`를 각각 참조합니다. 잘못된 조합이 반복되면
  둘을 묶는 `MonsterDefinitionSO` 도입을 검토합니다.
