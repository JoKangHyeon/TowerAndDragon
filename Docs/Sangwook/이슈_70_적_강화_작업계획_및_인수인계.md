## 1. 문서 목적

이 문서는 적 강화 시스템의 확정된 요구사항, 현재 작업 트리 상태, 진행 중인
데이터 구조, 남은 구현 순서와 검증 기준을 한곳에 정리한 인수인계 문서다.
다른 개발 환경이나 다른 AI 에이전트가 작업을 이어받을 때 이 문서와 실제
코드를 함께 확인하면 별도의 대화 기록 없이 작업을 재개할 수 있어야 한다.

상세 게임 기획의 최종 기준은 `Docs/기획종합_v2.md`이며, 이 문서는 이슈 #70의
코드 작업 범위만 보충한다. 기획 문서의 `[미정]` 항목을 이 문서에서 임의로
확정하지 않는다.

## 2. 이슈 요구사항

이슈 본문의 원래 요구사항은 다음과 같다.

- 적의 기본 데이터 위에 체력, 기본 보호막, 공격력, 이동 속도 보정을 적용한다.
- 적 생성에는 생성 간격과 생성 수 보정을 적용한다.
- 어떤 페널티가 적용됐는지 확인할 수 있어야 한다.
- 적의 수와 능력치를 전역에서 조율하는 관리 계층이 필요하다.

대화 과정에서 원래 이슈 문구 중 "일차에 따라 적이 강해진다"의 해석을 다음과
같이 명확히 했다.

- 일차, 주기 또는 웨이브 진행 자체는 적 능력치를 자동으로 강화하지 않는다.
- 각 일차는 미리 작성된 `WaveDefinitionSO`를 선택할 뿐이다.
- 게임 처음부터 끝까지 기본 적 종류, 등장 순서, 기본 생성 수와 기본 스탯은
  데이터에 명시되어 있다.
- 기본 데이터 위에 추가되는 적 수와 스탯 강화의 유일한 원인은 점령이다.

따라서 일차별 스탯 배율, 주기별 자동 난이도 곡선과 웨이브 진행 기반 자동
보정은 구현 범위에 포함하지 않는다.

## 3. 확정된 설계 원칙

### 3.1 기본 데이터와 점령 강화 분리

기본 웨이브와 기본 몬스터 데이터는 다음 에셋에 유지한다.

- `WaveDefinitionSO`: 포탈별 적 종류, 순서, 기본 생성 수와 간격
- `MonsterData`: 체력, 보호막, 공격, 이동 속도 등 기본 스탯
- `AttackSO`, `DamageEffectSO`: 기본 공격과 피해량

점령 강화는 `ConquestChunkCostTable`의 각 청크가 참조하는 별도
`EnemyEnhancementProfileSO`에 저장한다. 런타임 계산은 기본 데이터와 점령
강화를 읽어 최종 실행 값을 만들지만, 공유 ScriptableObject 원본은 수정하지
않는다.

### 3.2 강화 대상

각 강화 규칙은 대상 `MonsterData`를 명시한다. 프리팹이 아니라
`MonsterData`를 식별자로 사용하는 이유는 다음과 같다.

- 기본 스탯의 원본이 `MonsterData`다.
- 표현용 프리팹이 교체돼도 강화 규칙을 유지할 수 있다.
- 같은 프리팹에 다른 데이터를 주입하는 경우도 구분할 수 있다.
- UI에서 몬스터 이름의 스트링테이블 키를 가져오기 쉽다.

현재 1차 구현에서는 대상 몬스터 지정을 필수로 두는 방향을 권장한다. 향후
"해당 바이옴의 모든 몬스터" 규칙이 필요해지면 명시적인 대상 범위 enum을
추가한다. 단순히 null을 전체 대상으로 암묵 해석하면 데이터 누락과 전체 적용을
구분하기 어렵다.

### 3.3 스탯 보정

각 스탯은 가산과 곱연산을 모두 지원한다.

```text
최종 스탯 = (기본 스탯 + 모든 가산 보정의 합)
           × 모든 배율 인자의 곱

배율 인자 = 1 + MultiplierBonus
```

예를 들어 `MultiplierBonus = 0.2`는 `×1.2`, `0`은 변화 없음이다. 배율 필드의
중립값을 0으로 사용하면 새로 생성된 Unity 직렬화 구조체의 기본값이 안전하다.

점령 효과가 같은 몬스터와 스탯에 여러 번 누적될 때 가산값은 합산하고,
배율 보너스는 각각 `1 + bonus`로 변환한 후 곱한다. 잘못된 최종값을 막기 위한
최소값과 음수 허용 정책은 Resolver에서 명시적으로 검증해야 한다.

대상 스탯은 다음과 같다.

- 최대 체력
- 기본 보호막
- 공격력
- 이동 속도
- 생성 간격

### 3.4 특정 몬스터 생성 수 증가

생성 수 보정은 특정 `MonsterData`의 총 생성 수를 증가시키는 정수 가산값이다.
웨이브 실행 전에 `WaveDefinitionSO` 안에서 대상 `MonsterData`와 일치하는
`SpawnGroupData`를 찾고 런타임 실행 그룹을 만든다.

```text
원본 SpawnGroupData.SpawnCount = 10
점령 SpawnCountBonus = 3
런타임 SpawnCount = 13
```

원본 `SpawnGroupData.SpawnCount`를 직접 변경하지 않는다. ScriptableObject를
직접 변경하면 다음 웨이브에 값이 남거나 에디터 에셋이 오염되고, 같은 에셋을
사용하는 다른 씬과 테스트에도 영향을 준다.

같은 `MonsterData`가 한 포탈 웨이브의 여러 생성 그룹에 반복 등장할 때 그룹마다
보너스를 전부 더하면 증가량이 증폭된다. 현재 1차 구현은 보너스를
`(Portal, MonsterData)` 기준 총 추가 수량으로 취급하고, 웨이브 데이터 순서상
첫 번째 일치 그룹에 전부 배정한다. 스탯과 생성 간격 보정은 일치하는 모든
그룹에 적용한다. 향후 순차 또는 균등 분배가 필요하면 `WaveManager`의 런타임
그룹 생성 정책만 교체한다.

### 3.5 바이옴 범위

기존 통합 설계에 따라 점령한 청크의 `DominantTerrain`이 강화 대상 바이옴을
결정한다. 강화는 같은 `TerrainType`을 가진 포탈에서 생성되는 대상 몬스터에만
적용한다. 다른 바이옴 포탈의 동일 몬스터에는 적용하지 않는다.

`PortalDirection`과 `TerrainType`의 대응은 코드에서 하드코딩하지 않는다.
씬의 `Portal` 컴포넌트에 지정된 `TerrainType`을 사용한다.
`Portal.TerrrainType` 공개 프로퍼티의 오타는 실제 연결 작업에서
`Portal.TerrainType`으로 수정했다.

## 4. 목표 아키텍처

```text
밤 시작
  → DailyWaveController가 현재 일차의 WaveDefinitionSO 선택
  → EnemyEnhancementResolver가 Portal.TerrainType과
    SpawnGroupData.MonsterData를 기준으로 불변 런타임 그룹 생성
  → WaveManager가 최종 생성 수와 간격으로 런타임 그룹 실행
  → BaseMonster에 계산된 런타임 스탯 주입

밤 종료
  → 모든 진행 중 원정의 DaysProgressed 증가
  → 완료 원정의 청크 점령·주둔지·보상 이벤트 확정
  → 청크의 DominantTerrain과 EnemyEnhancementProfileSO 조회
  → EnemyEnhancementManager에 바이옴별 영구 누적
  → 다음 밤 웨이브부터 강화 적용
```

책임은 다음처럼 분리한다.

| 구성 요소 | 책임 |
| --- | --- |
| `ConquestChunkCostTable` | 청크별 비용, 보상과 강화 프로필 참조 |
| `EnemyEnhancementProfileSO` | 한 점령지가 부여하는 몬스터별 강화 규칙 목록 |
| `EnemyEnhancementManager` | 점령으로 얻은 강화 상태를 바이옴·몬스터별로 영구 누적하고 조회 |
| `EnemyEnhancementResolver` | 기본 웨이브와 강화 스냅숏을 결합하는 순수 계산 |
| 런타임 웨이브 데이터 | 최종 생성 수, 간격과 최종 몬스터 스탯 보관 |
| `WaveManager` | 계산 완료된 런타임 계획을 실행하고 생존 적을 추적 |
| `BaseMonster` | 계산된 체력·보호막·속도·공격 보정을 각 컴포넌트에 주입 |
| UI | 점령 예정 효과와 현재 누적 효과를 조회하여 표시 |

`EnemyEnhancementManager`는 일차나 주기에 따른 난이도 곡선을 관리하지 않는다.
이 이슈에서 전역 관리자의 의미는 점령으로 획득한 강화 효과의 단일 런타임
원본이라는 뜻이다.

### 5.3 후속 작업 이전 컴파일 오류 — 해결 완료

> 아래 5.3~5.5는 2026-07-21 중간 작업 상태를 남긴 역사 기록이며 현재 상태가

당시 Coplay MCP로 확인한 Unity 컴파일 오류는 두 개였다.

```text
Assets/Scripts/Managers/ConquestManager.cs(67,25):
CS1061: ConquestChunkCostTable에 ResolveEnemyScaling 정의가 없음

Assets/Scripts/Managers/ConquestManager.cs(224,57):
```

원인은 `ConquestChunkCostTable.ResolveEnemyScaling()`을
`ResolveEnemyEnhancementProfile()`로 교체했지만 `ConquestManager`의 구형 호출
두 곳을 아직 이전하지 않았기 때문이다.

오류가 있는 흐름:

- `ConquestManager.PreviewEnemyScaling()`
- `ConquestManager.ApplyEnemyScaling()`

단순히 메서드 이름만 바꾸면 반환 타입이 달라져 다음 오류가 이어진다.

- `ConquestManager.ApplyEnemyScaling()`
- `ConquestUIExample.RebuildEnemyScalingSlots()`

후속 작업에서 모든 참조를 새 프로필 경로로 이전하고
`EnemyScalingModifier.cs`와 `.meta`를 삭제했다.

### 5.5 후속 작업 이전 신규 타입의 부족한 부분 — 해결 완료

당시 신규 세 타입은 인스펙터 직렬화 골격만 있고 런타임에서 읽을 API가 없었다.

- `EnemyEnhancementProfileSO`에 `IReadOnlyList<EnemyEnhancementRule>` 조회가 없음
- null 목록, null 대상, 잘못된 생성 수와 배율을 검사하는 검증이 없음

기존 `EnemyScaling` 수치는 점령 UI 테스트를 위한 임시 데이터였으므로 보존할
필요가 없다. 새 프로필 에셋을 만든 뒤 구형 직렬화 데이터를 정리해도 된다.

않는다.

## 6. 권장 데이터 API

신규 타입은 최소한 다음 읽기 계약을 제공해야 한다. 실제 네이밍은 프로젝트
코딩 규칙을 따른다.

```csharp
public readonly struct EnemyStatModifier
{
    public float AdditiveBonus { get; }
    public float MultiplierBonus { get; }
    public float Multiplier => 1f + MultiplierBonus;

    public float Apply(float baseValue) =>
        (baseValue + AdditiveBonus) * Multiplier;
}
```

여러 점령 효과를 합칠 때 하나의 `Apply`를 순서대로 호출하면 가산값까지 앞선
배율의 영향을 받아 결합 순서에 따라 결과가 달라질 수 있다. 따라서 누적 상태는
가산 합과 배율 곱을 별도로 보관하는 것이 안전하다.

```text
AccumulatedAdditive += incoming.AdditiveBonus
AccumulatedMultiplier *= 1 + incoming.MultiplierBonus
Final = (Base + AccumulatedAdditive) × AccumulatedMultiplier
```

`EnemyEnhancementRule`은 최소한 다음 정보를 읽을 수 있어야 한다.

- `TargetMonster`
- `SpawnCountBonus`
- `MaxHealth`
- `ShieldAmount`
- `AttackPower`
- `MoveSpeed`
- `SpawnInterval`

`EnemyEnhancementProfileSO`는 규칙 목록을 외부에서 수정할 수 없도록
`IReadOnlyList<EnemyEnhancementRule>`로 제공한다.

## 7. 구현 순서

### 1단계 — 컴파일 복구와 데이터 계약 완성

1. 신규 세 타입에 읽기 API를 추가한다.
2. null 목록과 잘못된 데이터를 안전하게 처리한다.
3. `ConquestManager`의 구형 `ResolveEnemyScaling` 호출을 제거한다.
4. 구형 누적 상태를 임시로 유지하지 말고 새 관리자 계약으로 이전할 방향을
   확정한다.
5. `ConquestUIExample`의 구형 미리보기 타입도 프로필 기반으로 이전한다.
6. 모든 구형 참조를 제거한 후 `EnemyScalingModifier.cs`를 삭제한다.
7. Coplay MCP로 컴파일 오류 0을 확인한다.

컴파일만 빠르게 통과시키기 위해 구형 필드와 신규 필드를 동시에 유지하면 두 개의
강화 원본이 생긴다. 짧은 호환 기간이 꼭 필요한 경우가 아니라면 완전 이전을
권장한다.

### 2단계 — 순수 누적 상태와 Resolver

Unity 씬과 `MonoBehaviour`에 의존하지 않는 타입을 먼저 구현한다.

- 바이옴과 `MonsterData`별 누적 강화 상태
- 가산 합과 배율 곱 결합
- 특정 몬스터 규칙 필터링
- 최종 스탯 계산
- 생성 수와 생성 간격 계산
- 잘못된 값의 하한 처리

이 단계의 계산기는 EditMode 테스트가 가능해야 한다. 공유 SO에 쓰기 작업을 하지
않고 입력을 읽어 새 결과 값만 반환한다.

### 3단계 — EnemyEnhancementManager

전역 런타임 관리자를 추가한다.

- `(TerrainType, MonsterData)` 기준 누적 상태 보관
- 점령 완료 프로필 적용
- 바이옴별 현재 강화 상태 조회
- 현재 적용 중인 강화가 바뀌었음을 알리는 이벤트
- 밤 시작 시 사용할 불변 스냅숏 생성

저장·불러오기 방식은 기획상 아직 `[미정]`이므로 이 이슈에서는 런타임 동안만
유지한다. 향후 저장 시스템 도입 시 `RunData` 또는 전용 저장 DTO로 이전할 수
있도록 상태 객체를 Unity 오브젝트와 분리한다.

### 4단계 — 점령 연결

점령 완료 시 다음 순서로 처리한다.

1. 청크의 `DominantTerrain` 조회
2. `ConquestChunkCostTable.ResolveEnemyEnhancementProfile()` 호출
3. 프로필이 없으면 강화 없이 정상 완료
4. 프로필이 있으면 `EnemyEnhancementManager`에 해당 바이옴 강화 적용
5. 상태 변경 이벤트 발행

`ConquestManager`는 점령 절차와 청크 데이터 조회만 담당하고, 최종 누적 상태의
원본은 `EnemyEnhancementManager`에 둔다.

### 5단계 — 런타임 웨이브 계획 — 완료

`WaveManager`가 `WaveDefinitionSO`를 읽은 직후 런타임 그룹을 구성하는 해석
계층을 추가했다.

현재 구현 타입:

- `EnemyEnhancementSnapshot`
- `ResolvedEnemyStatModifier`
- `WaveManager.RuntimePortalWave`
- `WaveManager.RuntimeSpawnGroup`

`RuntimeSpawnGroup`은 최소한 다음을 가진다.

- 원본 몬스터 프리팹
- 원본 `MonsterData`
- 최종 생성 수
- 최종 생성 간격
- 최종 몬스터 스탯 또는 스탯 보정 스냅숏

`DailyWaveController`는 현재 일차의 기본 웨이브를 선택한다. `WaveManager`는
`EnemyEnhancementManager`에서 포탈 바이옴의 프로필 목록을 받아 Resolver에
전달하며, 진행 중 웨이브의 수치가 바뀌지 않도록 시작 시 한 번만 계산한다.

### 6단계 — 몬스터 스탯 주입 — 완료

`BaseMonster.Setup()`이 기본 `MonsterData`뿐 아니라 계산된 런타임 스탯을
받도록 확장됐다. 기존 테스트 코드 호환을 위해 중립 스냅숏을 사용하는 기존
오버로드도 유지한다.

- `Health.Initialize(finalMaxHealth)`
- `MonsterShield.Initialize(finalShieldAmount)`
- `MonsterMovement.SetSpeed(finalMoveSpeed)`
- `MonsterAttack.Initialize(..., attackModifier)`

공유 `MonsterData`를 복제하거나 수정하지 않는다.

공격력 적용은 `AttackSO`와 `DamageEffectSO` 에셋 원본을 수정하지 않는다.
`AttackContext`에 런타임 공격 보정 정보를 싣고 `DamageEffectSO.Apply()`에서
기본 피해와 결합한다. 투사체는 이미 `AttackContext`를 보관하므로 같은 보정이
원거리 공격까지 전달된다.

현재 `MA_CloseRange`와 `MA_Ranged`는 각각 `DamageEffectSO`가 하나이므로 현재
데이터에서는 공격 전체에 한 번 적용된다. 향후 한 공격에 피해 효과를 여러 개
넣으면 현재 구현은 각 피해 효과에 보정을 적용하므로, 그때 합산 정책을 다시
확정해야 한다.

### 7단계 — UI

두 UI 목적을 구분한다.

1. 점령 전: 선택한 청크를 점령하면 추가될 강화 프로필 표시
2. 현재 상태: 이미 점령해 누적된 바이옴·몬스터별 강화 표시

기존 `ConquestUIExample`의 스폰/공격 두 슬롯을 프로필 규칙 목록 기반으로
확장한다. 신규 표시 문자열은 코드에 직접 넣지 않고 스트링테이블 키를 사용하며
상수에는 `_LOC_KEY` 접미사를 붙인다.

체력, 보호막, 이동 속도와 생성 간격 아이콘이 필요하지만 프로젝트에 없다면
생성형 도구로 만들지 않고 팀에 요청한다. 텍스트만으로 검증 가능한 임시 UI와
최종 아트 UI를 구분한다.

### 8단계 — 데이터와 씬 연결

1. 테스트용 `EnemyEnhancementProfileSO`를 최소 두 개 만든다.
2. 서로 다른 `MonsterData`를 대상으로 지정한다.
3. `Data_ConquestChunkCostTable.asset`의 대상 청크에 프로필을 연결한다.
4. 기존 임시 `EnemyScaling:` 직렬화 데이터를 제거하고 에셋을 저장한다.
5. `EnemyEnhancementManager` 참조를 테스트 씬에 연결한다.
6. 서로 다른 `TerrainType` 포탈 두 개 이상이 실제로 적을 생성하는 테스트
   웨이브를 준비한다.

현재 7일치 웨이브 데이터는 주로 한 포탈 편성이므로 바이옴 격리 검증에는
부족할 수 있다. 정식 밸런스 웨이브를 불필요하게 바꾸지 말고 전용 테스트
웨이브를 두는 편이 안전하다.

## 8. 테스트 계획

현재 프로젝트에는 이 기능을 위한 자동 테스트 폴더와 어셈블리가 없다. 필요하면
`Assets/Tests/EditMode`와 `Assets/Tests/PlayMode` 및 대응 asmdef를 추가한다.

### 8.1 EditMode

- 프로필이 없으면 기본 생성 수와 스탯이 그대로 유지된다.
- 대상 `MonsterData` 규칙이 다른 몬스터에 적용되지 않는다.
- 한 바이옴 강화가 다른 바이옴 포탈에 적용되지 않는다.
- 가산 보정이 올바르게 합산된다.
- 배율 보정이 `1 + bonus` 인자의 곱으로 누적된다.
- 가산과 배율을 함께 적용한 최종값이 공식과 일치한다.
- 생성 수 보너스가 대상 몬스터에만 적용된다.
- 여러 그룹 분배 결과가 결정적이다.
- 생성 수가 음수가 되지 않는다.
- 생성 간격과 이동 속도 등 하한이 필요한 값이 안전하게 제한된다.
- 계산 전후 `WaveDefinitionSO`, `SpawnGroupData`, `MonsterData`, `AttackSO`의
  직렬화 값이 바뀌지 않는다.
- 같은 프로필을 여러 번 적용하면 영구 누적 상태가 정확하다.

### 8.2 PlayMode 및 수동 검증

- 점령하지 않은 상태에서 기본 웨이브와 기본 스탯으로 동작한다.
- 점령 완료 후 같은 바이옴 포탈의 대상 몬스터 생성 수가 증가한다.
- 다른 바이옴 포탈과 다른 몬스터는 기본값을 유지한다.
- 최종 체력과 보호막이 실제 컴포넌트에 반영된다.
- 이동 속도가 실제 이동에 반영된다.
- 근접 공격과 투사체 공격 모두 같은 규칙으로 강화된다.
- 생성 간격 변경이 실제 생성 타이밍에 반영된다.
- 다음 날에도 점령 강화가 유지된다.
- 일차가 바뀌는 것만으로 능력치가 자동 상승하지 않는다.
- 점령 예정 UI와 현재 누적 UI가 실제 계산과 일치한다.
- 비활성 포탈과 기존 웨이브 전멸 판정이 회귀하지 않는다.

각 구현 단계에서 다음을 반복한다.

- Coplay MCP `check_compile_errors`: 컴파일 오류 0
- Coplay MCP 플레이 테스트
- 필수 씬·프리팹 참조 누락 확인
- `git diff --check` 통과

## 9. 완료 기준

다음 조건을 모두 만족하면 이슈 #70을 완료로 판단한다.

- 적 스탯은 원본 `MonsterData`, `AttackSO`와 효과 SO를 변경하지 않고 각

- 점령 예정 강화와 현재 누적 강화를 UI 또는 검증용 표시에서 확인할 수 있다.
- 강화는 다음 날과 이후 웨이브에도 런타임 동안 유지된다.
- 자동 테스트와 수동 플레이 검증을 통과한다.
- Unity 컴파일 오류가 0이다.
- `git diff --check`를 통과한다.

7. 현재 첫 일치 그룹 수량 배분 정책을 바꿀 필요가 있는지 팀에 확인한다.
8. 실제 밸런스 프로필을 추가하기 전에 대상 몬스터와 수치를 확정한다.
9. 자동 EditMode 테스트와 PlayMode 테스트를 추가한다.
10. 저장 시스템이 확정되면 런타임 누적 프로필을 저장 데이터에 연결한다.
11. 사용자 소유의 씬·몬스터·공격 데이터 변경을 확인 없이 되돌리지 않는다.
12. 코드 수정 후 Coplay MCP 컴파일, 테스트 씬 플레이와 `git diff --check`를
    실행한다.

작업 재개 시 가장 먼저 할 일은 현재 테스트 프로필의 수량 증가가 수동 플레이
시나리오에서도 점령 확정 이후의 다음 밤에 적용되는지 확인하고, 그 시나리오를
자동 테스트로 고정하는 것이다.
