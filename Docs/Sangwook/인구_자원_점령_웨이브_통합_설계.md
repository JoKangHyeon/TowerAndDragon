## 1. 결론 요약

인구는 식량·목재처럼 지불하면 사라지는 일반 자원이 아니라, 생산 시설,
타워와 점령 원정에 배치하고 다시 회수하는 공용 인력 풀이다. 전체 인구의
원본은 하나의 `PopulationManager`가 관리하고, 각 사용처는 관리자가 발급한
할당 상태만 사용한다.

```text
MaxPopulation = AssignedPopulation + AvailablePopulation
```

- `[확정]` `MaxPopulation`은 플레이어가 보유한 살아 있는 전체 인구다.
- `[확정]` 별도의 `CurrentPopulation`은 만들지 않는다.
- `[확정]` 인구는 할당 시 소모되지 않고 사용할 수 없는 상태가 된다.
- `[확정]` 할당 해제 시 가용 인구로 돌아온다.
- `[확정]` 점령 완료 보상으로 `MaxPopulation`이 증가한다.
- `[확정]` 식량 부족으로 사람이 사망하면 `MaxPopulation`이 감소한다.
- `[확정]` 점령 원정에 할당된 인구도 기아로 감소하며, 감소 순서는 가장 마지막이다.
- `[확정]` 생산량의 소수점은 버림 처리한다.
- `[확정]` 점령 완료로 증가한 인구는 완료된 날부터 유지비를 낸다.
- `[확정]` 비활성화된 타워의 인구는 타워를 수리하는 인력으로 남는다.
- `[확정]` 점령 적 강화는 바이옴별로 영구 누적되어 해당 바이옴의
  포탈에만 적용된다.

구현 순서는 인구 코어를 먼저 확정한 뒤 점령·생산과의 계약을 연결하고,
타워, 일차별 웨이브, 유지비 순서로 진행한다. `#16 인구 시스템`은 개별
구현 이슈가 아니라 하위 기능을 최종 검증하는 통합 이슈로 사용한다.

## 3. 목표 시스템 경계

```text
CycleManager
  └─ DailySettlementManager
       ├─ ProductionManager
       ├─ ConquestManager
       ├─ PopulationUpkeepSystem
       ├─ ResourceManager
       └─ PopulationManager

PopulationManager
  ├─ 생산 시설 PopulationAllocation
  ├─ 타워 PopulationAllocation
  └─ 점령 원정 PopulationAllocation

ConquestManager
  └─ BiomeEnemyScalingState
       └─ WaveResolver
            └─ WaveManager
                 └─ Portal(TerrainType)
```

각 시스템의 책임은 다음과 같이 제한한다.

| 시스템 | 책임 | 책임 밖의 내용 |
|---|---|---|
| `PopulationManager` | 전체 인구, 할당·회수, 인구 증감, 불변식 | 생산량, 타워 공격, 원정 진행 |
| `ResourceManager` | 자원 보유량, 획득·소비, 변경 이벤트 | 인구 예약, 생산 시점 결정 |

| `ConquestManager` | 원정 시작·진행·완료, 점령 보상과 페널티 등록 | 인구 원본, 자원 원본 |
| `WaveResolver` | 오늘의 기본 웨이브와 영구 보정 결합 | 적 생성 및 전멸 판정 |
| `WaveManager` | 해석된 웨이브 실행, 적 생성·추적 | 점령 페널티 누적, 날짜 선택 |
| `Portal` | 방향, 바이옴, 경로, 스폰 위치, 활성 상태 | 웨이브 선택, 강화 계산 |

## 4. 인구 시스템 설계

### 4.1 핵심 상태

`PopulationManager`가 다음 값을 단독으로 관리한다.

- `MaxPopulation`: 현재 살아 있는 전체 인구
- `AssignedPopulation`: 모든 할당의 합
- `AvailablePopulation`: `MaxPopulation - AssignedPopulation`

`AvailablePopulation`은 별도 원본으로 저장하지 않고 파생값으로 계산하는
방식을 권장한다. 별도로 저장하면 할당 실패나 예외 발생 시 값이 어긋날 수
있다.

항상 다음 조건을 만족해야 한다.

```text
MaxPopulation >= 0
AssignedPopulation >= 0
AssignedPopulation <= MaxPopulation
AvailablePopulation >= 0
각 할당의 Assigned <= Capacity
```

### 4.2 할당 모델

각 사용처는 정수를 직접 증감하지 않고 `PopulationAllocation`을 사용한다.

권장 정보:

- 최대 배치 가능 인구 `Capacity`
- 현재 배치 인구 `Assigned`
- 사용처 분류 `PopulationAssignmentType`
- 소유자 참조
- 충원율 `Assigned / Capacity`
- 할당 변경 알림

권장 사용처 분류:

- `Tower`
- `Production`
- `Conquest`

`Building` 부모 클래스에 인구를 직접 넣지 않는다. 모든 건물이 인구를
사용한다고 확정되지 않았고, 점령 원정은 건물이 아니기 때문이다.

### 4.3 관리 API

외부 시스템은 다음 의미의 API만 사용한다.

- 할당 등록
- 인구 추가 배치 시도
- 인구 회수 시도
- 한 사용처의 전체 인구 반환
- 최대 인구 증가
- 기아 인구 감소 적용
- 현재 인구 상태 조회

할당과 자원 소비를 함께 수행하는 작업은 중간 실패 시 한쪽만 반영되지
않도록 사전 검증 후 한 번에 확정해야 한다.

### 4.4 변경 이벤트

UI와 관련 시스템이 인구 상태를 직접 폴링하지 않도록 변경 이벤트를
제공한다.

이벤트에는 최소한 다음 결과가 포함되어야 한다.

- 변경 후 최대 인구
- 변경 후 할당 인구
- 변경 후 가용 인구
- 변경된 할당
- 변경 원인

변경 원인은 할당, 회수, 점령 보상, 기아, 사용처 제거 정도를 구분할 수
있어야 한다. 사용자에게 표시할 문구는 코드에 직접 넣지 않고 스트링테이블
key를 사용한다.

## 5. 기아 및 유지비 규칙

### 5.1 유지비 계산

- `[확정]` 인구 한 명은 매일 식량 1을 소비한다.
- `[확정]` 유지비 기준은 배치 여부와 관계없이 `MaxPopulation` 전체다.
- `[확정]` 점령 완료로 증가한 인구는 완료된 날부터 유지비에 포함한다.
- `[확정]` 식량이 부족하면 식량을 0으로 만들고 부족량만큼 인구 감소를
  시도한다.

### 5.2 정산 순서

아침 정산은 이벤트 구독 순서에 맡기지 않고 하나의 조정자가 명시적으로
실행한다.

```text
1. 생산 시설별 생산량 계산
2. 생산 자원 지급
3. 점령 원정 진행 및 완료 처리
4. 점령 완료 인구 보상 적용
5. 인구 유지비 계산
6. 식량 차감
7. 부족 식량만큼 기아 처리
8. 정산 완료 알림
```

### 5.3 기아 감소 우선순위

기아는 다음 순서로 처리한다.

```text
가용 인구
  → 타워 배치 인구
  → 생산 시설 배치 인구
  → 점령 원정 배치 인구
```

- `[확정]` 점령 원정에 할당된 인구도 기아 대상이며 다른 모든 인구보다
  나중에 감소한다.
- `[확정]` 같은 분류 안에서는 등록된 할당 순서대로 한 명씩 순환 감소시켜
  결과를 재현 가능하게 만든다.
- `[권장]` 향후 플레이어 우선순위 UI가 추가되면 순환 정책을 명시적 보호
  우선순위 정책으로 교체한다.

감소 가능한 최대 인구는 다음과 같다.

```text
KillablePopulation = MaxPopulation
ActualPopulationLoss = min(FoodShortage, MaxPopulation)
```

식량 부족이 전체 인구보다 크면 실제 감소량은 `MaxPopulation`으로 제한한다.
모든 인구가 사망한 뒤에도 남은 부족량은 추가 인구 감소로 이월하지 않으며,
식량은 0으로 처리하고 다음 날 다시 유지비를 계산한다.

## 6. 생산과 자원 관리

### 6.1 생산량

생산 시설의 실제 생산량은 충원율을 반영한다.

```text
StaffingRatio = AssignedPopulation / PopulationCapacity
ProductionAmount = floor(BaseProductionAmount * StaffingRatio)
```

- 인구 0%: 생산 중단
- 인구 50%: 기본 생산량의 50%, 소수점 버림
- 인구 100%: 기본 생산량 전부 생산

기본 생산량, 필요 인구와 생산 자원 종류는 데이터 에셋에서 설정하고 코드에
시설별 수치를 하드코딩하지 않는다.

### 6.2 정식 자원 관리자

`TempResourcePool`은 테스트용이므로 정식 시스템의 원본으로 확장하지 않는다.
정식 `ResourceManager` 또는 동등한 관리자는 다음 책임을 가져야 한다.

- 자원 종류별 현재 보유량
- 획득 가능 여부 및 획득 처리
- 지불 가능 여부와 원자적인 소비 처리
- 음수 방지
- 자원 변경 이벤트
- 아침 생산과 유지비에서 사용할 공용 API

인구는 `ResourceManager`의 소비 자원에 포함하지 않는다. UI에서 함께
표시할 수는 있지만, 내부 거래 의미는 분리한다.

### 6.3 비용 데이터 조정

현재 `ResourceCost.Population`은 점령에서 소비 자원과 예약 인구를 한데
묶는다. 장기적으로 다음처럼 분리하는 것을 권장한다.

```text
ExpeditionRequirement
  ├─ RequiredPopulation
  └─ ResourceCost
       ├─ Food
       ├─ Wood
       ├─ Stone
       └─ Ore
```

기존 `ConquestChunkCostTable` 에셋의 직렬화 데이터를 잃지 않도록 구조 변경
시 데이터 이전 계획을 함께 세운다.

## 7. 점령 시스템 연결

### 7.1 원정 시작

원정 시작은 다음 조건을 모두 먼저 검증한다.

- 점령 가능한 청크인가
- 필요한 가용 인구가 있는가
- 필요한 자원을 보유했는가
- 동일 청크에 진행 중인 원정이 없는가

모든 검증이 끝난 뒤 다음 변경을 한 번에 확정한다.

```text
자원 실제 소비
→ 원정 인구 할당
→ ConquestExpedition 생성
```

중간 단계에서 실패하면 자원과 인구 모두 변경 전 상태로 유지해야 한다.

### 7.2 진행과 완료

원정 진행 중 인구는 가용 인구에서 제외되지만, 기아 감소 순서의 마지막에
도달하면 해당 원정의 할당 인구도 감소한다. 필요 인구 미달 원정의 중단·실패
처리는 점령 시스템 확립 시 별도 정책으로 연결한다.

원정 완료 시:

```text
원정 인구 전원 반환
→ 청크 점령 상태 적용
→ 시야 및 주둔지 처리
→ 점령 보상만큼 MaxPopulation 증가
→ 해당 TerrainType 적 강화 영구 누적
```

완료된 날의 유지비 계산 전에 인구 보상을 적용한다.

### 7.3 취소와 예외 처리

`[미정]` 원정 취소 기능과 환급 규칙은 현재 기획에서 확정되지 않았다.
다만 시스템적으로 씬 종료, 런 리셋 또는 잘못된 대상 제거 시 할당 인구가
유실되지 않도록 전체 반환 경로는 준비해야 한다.

## 8. 타워 인구 연결

### 8.1 타워 데이터

`[구현]` `TowerData`에 타워 종류별 최대 필요 인구인
`PopulationCapacity`를 추가했다. 현재 배치 인구는 런타임 상태이므로
`TowerData`에 저장하지 않고 `TowerPopulation`의 할당에서 관리한다.

### 8.2 공격 속도

```text
StaffingRatio = AssignedPopulation / PopulationCapacity
EffectiveAttackInterval = BaseAttackInterval / StaffingRatio
```

- 충원율 0%: 공격하지 않음
- 충원율 50%: 공격 간격 2배
- 충원율 100%: 기본 공격 간격

### 8.3 상태 분리

현재의 단일 공격 활성화 값으로는 파괴 복구와 인구 부족을 함께 표현할 수
없다. 최소한 다음 상태를 분리한다.

- 전투 가능한 물리 상태
- 현재 충원율
- 유효한 공격 데이터 존재 여부

최종 공격 가능 여부는 세 상태를 조합해 계산한다. 이렇게 해야 인구 0인
타워가 복구 코드 때문에 다시 공격하는 문제를 막을 수 있다.

### 8.4 비활성화와 인구 유지

- `[확정]` 체력이 0이 되어 비활성화된 타워의 인구는 반환하지 않는다.
- `[확정]` 해당 인구는 타워를 수리하는 인력으로 해석한다.
- `[확정]` 플레이어가 인구를 직접 빼거나 타워를 철거할 때만 반환한다.
- `[권장]` 철거와 오브젝트 파괴 경로에서 중복 반환되지 않도록 할당 자체에
  해제 완료 상태를 둔다.

## 9. 바이옴별 영구 적 강화

### 9.1 확정 규칙

- 점령한 청크의 `TerrainType`이 강화 대상 바이옴을 결정한다.
- 같은 `TerrainType`에 연결된 포탈에서 등장하는 적만 강화한다.
- 강화는 그날만 적용되지 않고 현재 플레이 전체에 영구 누적된다.
- 전체 적뿐 아니라 특정 종류의 적 수와 스탯만 강화할 수 있다.
- 일차별 기본 웨이브와 점령 영구 강화는 별도 데이터로 유지한다.

### 9.2 포탈과 TerrainType 연결

`Portal`은 인스펙터에서 다음 씬 정보를 제공한다.

- `PortalDirection`
- `TerrainType`
- 스폰 위치
- 지상 이동 경로
- 메인 성
- 활성 상태

`PortalDirection`과 `TerrainType`의 대응을 코드에서 `switch`로 하드코딩하지
않는다. 맵 구성이 바뀌어도 씬 데이터만 수정할 수 있어야 한다.

### 9.3 바이옴별 누적 상태

현재 단일 누적값을 바이옴별 상태로 변경한다.

```text
Grass   → 누적 강화 상태
Rock    → 누적 강화 상태
Volcano → 누적 강화 상태
Desert  → 누적 강화 상태
Snow    → 누적 강화 상태
```

점령 완료 시 청크의 `DominantTerrain`에 해당 점령지의 강화 프로필을
합산한다. 런타임 동안 유지하고, 저장 시스템이 도입되면 `RunData` 또는
전용 저장 데이터에 직렬화한다.

### 9.4 강화 프로필

현재 `EnemyScalingModifier`의 전체 스폰 수·공격력 두 필드만으로는 요구를
표현할 수 없다. 데이터 기반 강화 항목은 다음 확장을 지원해야 한다.

- 대상 `MonsterData`
  - 대상이 없으면 해당 바이옴의 모든 적
  - 대상이 있으면 해당 적 종류만 적용
- 스폰 수 가산
- 최대 체력 배율
- 공격력 배율
- 이동 속도 배율
- 방어막 배율

실제 수치와 어떤 점령지가 어떤 적을 강화하는지는 데이터에서 설정한다.
`[미정]` 배율 합산 방식이 단순 합산인지 곱연산인지는 밸런스 데이터 작성
전에 확정해야 한다.

### 9.5 런타임 적용

공유 ScriptableObject인 `WaveDefinitionSO`, `SpawnGroupData`, `MonsterData`와
`AttackSO`를 런타임에 직접 수정하지 않는다.

```text
일차별 기본 WaveDefinitionSO
  + Portal.TerrainType
  + 해당 바이옴의 영구 강화 상태
  = 런타임 웨이브 계획
```

스폰 수 보정은 런타임 웨이브 계획에만 반영한다. 체력·공격력·이동 속도·
방어막 보정은 적 생성 시 기본 `MonsterData`와 런타임 보정값을 조합해 각
적 인스턴스에 주입한다.

## 10. 일차별 웨이브 시스템

### 10.1 기본 일정

별도의 웨이브 일정 데이터가 현재 일차에 실행할 `WaveDefinitionSO`를
선택한다. 주기당 일수와 보스 상세는 기획서에서 `[미정]`이므로 일정 구조는
데이터로 교체 가능하게 만들고 공식은 하드코딩하지 않는다.

### 10.2 실행 흐름

```text
밤 시작
→ 현재 일차의 WaveDefinitionSO 선택
→ 활성 포탈 조회
→ 포탈 TerrainType별 영구 강화 조회
→ 런타임 웨이브 계획 생성
→ WaveManager 실행
→ 모든 적 전멸
→ 밤 종료
→ 다음 낮 정산
```

### 10.3 책임 조정

- `WaveTestStarter`는 테스트 전용으로 유지하거나 실제 진행 컨트롤러로
  교체한다.
- `WaveManager`가 `ConquestManager`를 직접 참조해 강화값을 계산하지 않게
  한다.
- 별도 `WaveResolver` 또는 동등한 계층이 기본 데이터와 강화 상태를
  결합한다.
- 적 생성 수가 0 미만이 되지 않도록 최종 결과를 검증한다.

- `TowerAttack`: 충원율 기반 공격 간격과 상태 분리
- `BaseMonster`: 런타임 스탯 보정 주입
- `MonsterAttack`, `Health`, `MonsterMovement`, `MonsterShield`: 런타임 보정값 수용
- `WaveManager`: 해석된 런타임 생성 수와 적 보정값 사용
- 인구·자원 UI: 변경 이벤트 구독

## 13. 검증 계획

### 13.1 인구 코어

- 가용 인구보다 많이 배치할 수 없다.
- 사용처 최대치보다 많이 배치할 수 없다.
- 0 미만으로 회수할 수 없다.
- 회수 후 가용 인구가 정확히 복구된다.
- 사용처 제거 시 한 번만 전체 반환된다.
- 점령 인구는 타워와 생산 인구가 모두 감소한 뒤 마지막으로 감소한다.
- 기아 후에도 모든 인구 불변식이 유지된다.

### 13.2 생산과 유지비

- 0%, 50%, 100% 충원 생산량이 정확하다.
- 소수점 생산량이 버림 처리된다.
- 생산 자원 지급 후 유지비가 차감된다.
- 점령 완료 인구가 완료 당일 유지비에 포함된다.
- 식량 부족량과 실제 감소 가능 인구의 경계가 정확하다.

### 13.3 타워

- 타워 건설 시 `Tower` 할당이 한 번 생성된다.
- 낮에 선택한 타워의 인구를 배치·회수할 수 있다.
- 타워 철거 시 배치 인구가 반환되고 할당이 제거된다.
- 인구 0인 타워가 공격하지 않는다.
- 50% 충원 타워의 공격 간격이 2배다.
- 100% 충원 타워가 기본 간격으로 공격한다.
- 비활성화된 타워의 인구가 반환되지 않는다.
- 인구 0인 타워가 복구되어도 공격하지 않는다.
- 철거 시 인구가 한 번만 반환된다.

### 13.4 점령

- 원정 시작 시 자원만 소비되고 인구는 예약된다.
- 원정 실패 시 자원과 인구가 모두 유지된다.
- 완료 시 원정 인구가 반환된다.
- 완료 시 인구 보상과 바이옴 강화가 한 번만 적용된다.
- 점령 인구가 기아 감소 순서의 마지막에 처리된다.
- 기아로 원정 필요 인구가 부족해진 경우를 점령 시스템이 감지할 수 있다.

### 13.5 웨이브와 적 강화

- 일차별로 지정한 기본 웨이브가 선택된다.
- 점령하지 않은 바이옴은 기본 편성을 유지한다.
- 점령한 바이옴과 같은 `TerrainType`의 포탈만 강화된다.
- 다른 바이옴 포탈에는 강화가 적용되지 않는다.
- 특정 `MonsterData` 대상 보정이 다른 적에 적용되지 않는다.
- 강화가 다음 날과 이후 웨이브에도 누적 유지된다.
- 기본 SO와 `MonsterData` 에셋 값이 런타임에 변경되지 않는다.

각 단계마다 다음 검증을 수행한다.

- Unity 컴파일 오류 0
- EditMode 테스트 통과
- 관련 PlayMode 테스트 통과
- 테스트 씬 플레이 검증
- 프리팹·씬의 누락 참조 확인
- `git diff --check` 통과

## 14. 남은 팀 확인 사항

다음은 구조를 막지는 않지만 실제 밸런스 데이터 작성 전에 확정해야 한다.

- `[미정]` 향후 플레이어 우선순위 UI를 제공할지
- `[미정]` 기아로 점령 원정의 필요 인구가 부족해졌을 때 원정을 중단·실패
  중 어느 상태로 처리할지
- `[미정]` 원정 취소 및 자원 환급 규칙
- `[미정]` 적 스탯 배율의 합산·곱연산 규칙과 상한
- `[미정]` 각 점령지가 강화할 특정 적 종류와 실제 수치
- `[미정]` 주기당 일수와 보스 웨이브 일정
- `[미정]` 저장·불러오기 범위와 바이옴별 강화 상태 직렬화 방식

이 항목들은 임의로 확정 구현하지 않고, 데이터 구조가 변경에 견딜 수
있도록 경계를 분리해 둔다.

## 15. 협업 시 주의사항

- 인구 시스템 담당자는 #61의 공개 API를 먼저 공유한다.
- 연동 작업자는
  [인구 시스템 연동 가이드](./인구_시스템_연동_가이드.md)의 생명주기와
  실패 복구 체크리스트를 확인한다.
- 점령 담당자는 인구를 직접 차감하지 않고 예약·반환 API를 사용한다.
- 생산 담당자는 충원율을 조회하되 전체 인구 값을 직접 수정하지 않는다.
- 자원 담당자는 인구를 일반 소비 자원으로 처리하지 않는다.
- 웨이브 담당자는 점령 상태를 직접 수정하거나 기본 SO에 영구 보정값을
  기록하지 않는다.
- 씬·프리팹을 동시에 수정하는 작업은 머지 전에 담당 씬을 명확히 나눈다.
- 기존 사용자 변경인 `FarmField`, `Portal`, 인구 테스트 씬을 덮어쓰지
  않는다.
- 기획 `[미정]` 값은 팀 확인 전 테스트용 데이터임을 명시하고 확정값처럼
  사용하지 않는다.
